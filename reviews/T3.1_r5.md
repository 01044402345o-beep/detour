# T3.1 5회차 검토 — 준비 판정 재시도

2026-11-23. 대상은 `pwa.ts`, `sw.ts`, `messages.ts`, Settings의 재판정 연결 및 관련 테스트다. `T3.1_fix_r2.md`와 `phase3_e2e.md`를 대조했다. 이 보고서만 작성했으며 기존 소스·증거를 수정하지 않았다.

## 결론

이벤트 기반 일회성 판정이 실패했을 때 재시도와 설정 진입 재판정을 추가하는 방향은 타당하다. 캐시 확인 기준은 완화되지 않았고, 정상 경로에서 무한 반복이나 지속적인 네트워크 요청을 만드는 코드는 없다. 다만 **8초 타임아웃이 하위 비동기 작업을 취소하지 않아 실제 요청 동시 실행 1개를 보장하지 못하는 Low 1건**이 남는다.

## R5-L01 — 타임아웃된 ready/활성화 대기가 남아 나중에 요청이 몰림 (Low)

- **위치:** `app/src/sw/pwa.ts:54–84` (`waitActivated`, `readStatusFromWorker`), `:108–125` (`withTimeout`, `checkOnce`).
- **문제:** `withTimeout`은 외부 Promise를 null로 완료할 뿐 `readStatusFromWorker()`를 중단하지 않는다. 서비스 워커 준비가 8초보다 오래 걸리면 재시도마다 같은 `navigator.serviceWorker.ready`에 새 대기가 남는다. ready가 나중에 완료되면 이미 타임아웃된 호출도 활성화 대기와 `postMessage`를 진행해 여러 프리캐시 검사를 동시에 요청한다. 상태 갱신은 직렬화되어도 실제 하위 작업은 직렬화되지 않는다.
- **근거/재현:** 현재 TypeScript 모듈을 메모리에서 변환해 실제 `defaultPwaDeps.readStatus`를 사용했다. 등록만 대역으로 바꾸고, ready를 보류한 서비스 워커·MessageChannel·가짜 시계를 주입했다. 40초 진행 후 ready를 해제하자 다음 결과가 나왔다(파일 생성 없음).

  ```json
  {
    "before": {"elapsedMs":40000,"pendingReadyReads":4,"sends":0},
    "after": {"sends":4,"maxConcurrentStatusRequests":4}
  }
  ```

  실제 브라우저 부하 재현은 아니지만, 현재 함수의 타임아웃 이후 실행 경로를 직접 확인한 결과다. 워커는 요청마다 52개 항목을 `matchPrecache`로 확인하므로 이 예에서는 최대 208개의 캐시 조회가 중복 발생한다. 기존 “동시 실행 1개” 테스트는 타임아웃 전 첫 응답을 해제하며, 무응답 테스트는 이전 하위 작업이 뒤늦게 재개되는 조건을 검사하지 않는다.
- **영향/심각도:** 느린 설치·활성화에서 불필요한 대기와 캐시 조회가 누적되는 자원 관리 문제다. 60회 예약 제한이 있어 단독 자동 재시도는 무한하지 않고, 늦은 응답이 이미 완료된 외부 Promise를 다시 완료할 수 없으므로 이전 응답의 상태 덮어쓰기 문제는 아니다. 이 한정된 영향으로 Low로 판정한다.
- **권장 수정안:** 판정별 취소 신호 또는 만료 플래그를 하위 함수에 전달하고, ready/활성화 await 이후 만료 여부를 검사해 후속 요청을 보내지 않도록 한다. 활성화 리스너와 응답 타이머·MessagePort도 성공/실패/취소 시 정리한다. ready를 여러 타임아웃 동안 보류한 뒤 해제하는 회귀 테스트에서 만료된 판정이 요청을 보내지 않는지 확인한다.

## 원인 분석 타당성

- **확인된 사실:** 기존 코드는 등록·최초 준비·controllerchange 때만 판정하고, null 응답 이후 독립적인 재시도가 없었다. 응답 대기가 시간 초과한 뒤 이벤트가 더 없으면 카드가 계속 숨겨질 수 있으므로 재시도 도입의 근거는 충분하다.
- **확정할 수 없는 사실:** 최초 실패 trace가 없어 그 실패가 등록 지연, 응답 시간 초과, 다른 환경 문제 중 무엇인지는 확정되지 않았다. 수정 기록이 이를 명시한 점은 적절하다.
- 수정 기록의 경로 a(제어권 변경 이벤트는 먼저 왔지만 이후 별도 이벤트 없이 controller가 생김)와 경로 c(활성 워커가 불완전한 프리캐시 수를 돌려줌)는 테스트 대역으로 만든 방어 조건이다. 현재 브라우저/Workbox의 최초 설치에서 실제 발생했다는 증거는 아니다. 따라서 “세 원인 경로를 직접 재현”은 **세 가정에 대한 단위 테스트**로 해석해야 하며 실제 간헐 실패의 원인 재현으로 표현해서는 안 된다.
- 수정 후 오프라인 120/120 및 전체 75/75 통과는 회귀 증거이고, 원래 실패가 영구히 사라졌다는 증명은 아니다. 작성자도 이 한계를 명시했다.

## 재시도·배터리·성능·종료 조건

| 항목 | 확인 |
|---|---|
| 자동 예약 | 타이머는 하나만 유지하고 지연은 1·2·3·5초, 이후 5초다. 준비 완료 시 중지하며 예약 60회 후에도 중지한다. 추가 이벤트가 없다면 최초 확인 1회 + 자동 재시도 60회다. |
| 최대 시간 | 문서의 “약 5분”은 대기 간격 합계 291초를 뜻한다. 확인 자체가 매번 8초 걸리면 최초 포함 61회 × 8초를 더해 약 **779초(13분)**이며, 백그라운드 타이머 지연은 이를 더 늘릴 수 있다. 5분을 전체 실행 시간의 상한으로 보면 안 된다. |
| 추가 이벤트 | 등록·제어권 변경·활성화 알림은 유한한 외부 사건이고 판정 자체가 이 이벤트를 다시 발생시키지 않는다. Settings는 mount 때만 횟수를 초기화하며 일반 렌더링마다 초기화하지 않는다. 정상 사용에서 자기 자신을 반복 호출하는 무한 루프는 발견하지 못했다. |
| 준비 완료 후 | 예약은 취소된다. 이후 명시적인 새 이벤트에 따른 확인은 가능하지만 상시 polling으로 이어지지 않는다. |
| 비용 | 상태 확인은 로컬 Cache Storage 조회다. 타일·음성·사용자 기록을 다운로드하거나 캐시하는 경로는 추가되지 않았다. 실패 중인 백그라운드 탭도 상한까지 확인할 수 있으나 자동 실행 횟수는 제한된다. 배터리 무영향을 실측한 것은 아니다. |
| 동시성 | 외부 판정 Promise와 상태 반영은 직렬화되고 이벤트 중복은 rerun 하나로 합쳐진다. 단, 타임아웃 후 남는 하위 작업은 R5-L01 참조. |

## 판정 정확성

- 준비 완료는 계속 `matchPrecache`의 실제 적중 수와 전체 수가 일치하고 전체 수가 양수일 때만 설정된다. 타이머 만료·재시도 횟수·활성화 메시지만으로 true를 설정하지 않는다.
- 활성화 알림은 재확인 요청으로만 쓰인다. 알림과 clientsClaim의 완료 순서에 의존해 준비 완료를 단정하지 않고, 페이지 쪽에서 활성화 대기 및 controller 존재를 확인한다.
- null/오류 때 이전 판정을 유지하는 기존 정책은 그대로다. 이번 수정이 캐시 삭제 이후까지 준비 상태를 지속적으로 보증하는 기능을 추가한 것은 아니다.
- SW의 프리캐시 범위, OSM 미캐시, 업데이트 적용·제한 수용 정책에는 이번 변경으로 새 문제가 생긴 근거를 찾지 못했다. R1~R4의 닫힌 항목은 다시 열지 않는다.
