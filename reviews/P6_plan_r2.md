## H — 병렬 구현 전 보완

### R2-H-01 패치 원본은 보존되지만 공용 사전의 동시 갱신은 여전히 안전하지 않음

- 근거: task.md:372-373·389·430. 각 worker가 `node app/scripts/i18n-patch.mjs <패치>`로 공용 en/ja/zh.json을 읽고 병합하고 쓴다. 프로세스 하나 안에서 동기식으로 처리해도 다른 worker 프로세스와는 원자적 작업이 아니다. 잠금·단일 실행 큐·coordinator 직렬 적용 계약이 없다.
- 구체적 실패: A와 B가 같은 사전 D를 읽고 각각 D+A, D+B를 쓰면 A 키가 사라질 수 있다. 세 언어 파일을 차례로 저장하는 사이 테스트가 읽으면 언어별 키 집합도 달라진다. 마지막 재적용은 최종 누락을 복구하지만 이미 수행한 worker 타입 검사·테스트의 성공/실패를 신뢰할 수 있게 만들지는 않는다.
- 실제 연결: `app/src/i18n/index.ts:18-29`는 en.json에서 MessageKey와 JA/ZH 타입을 도출하므로 새 키가 유실되면 화면 타입 검사도 실패한다. `index.test.ts:25-61`은 키 동일성뿐 아니라 문자열·영어 fallback 금지·언어 문자·placeholder 동일성까지 검사한다. 패치 파일만 만들고 적용을 마지막까지 미루는 것으로는 각 worker 검증 조건을 충족하지 못한다.
- 수정 방향: 패치는 각 worker 단독 소유로 유지하되 공용 사전 갱신은 coordinator 큐로 직렬화하고, 검사 중 갱신을 막는 검증 구간까지 정의한다. 또는 T6.0에서 새 키 계약을 먼저 모아 적용·동결한 후 화면 병렬 작업을 시작한다. worker 스크립트 적용을 유지하려면 모든 호출이 따르는 프로세스 간 잠금과 테스트용 일관된 사전 snapshot 전략을 명시한다. 단순 atomic rename만으로 read-modify-write 유실은 해결되지 않는다.
- T6.0 완료 조건에 실제 3개 언어 패치 예제의 중첩 병합·반복 적용·기존 키 보존·충돌 감지와 기존 i18n 검사를 연결한다. hardcodeCheck는 JSON 패치를 검사하지 않으므로 이를 대신할 수 없다(`hardcodeCheck.test.ts:121-135`, `index.test.ts:25-61`). `photo.*`의 공통 라이선스명/저작자 등은 data/photos.ts에 두고, 번역 키에는 현지화된 표시 문구를 둬 기존 언어 문자 검사를 불필요하게 완화하지 않는다. 기존 번역의 정확한 문구를 바꿀 때 `index.test.ts:111-116` 같은 기대값 갱신도 coordinator 소유로 명시하면 된다.
