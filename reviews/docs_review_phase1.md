# Phase 1 문서 변경 교차 검증 — Codex

2026-11-23. `prd.md` v0.4와 `task.md`의 지정 변경을 T1.2 R1, T1.5 R1·R2 판정/R3 검토, T1.6 R1·R2 판정 및 T1.1·T1.3 관련 판정과 대조했다. 코드 계약 확인을 위해 `tts.ts`, `events.ts`, `useAppStore.ts`, `types.ts`, `downtown.json`도 읽었다. 이 보고서와 별도 T1.2 R2 보고서 이외의 소스·문서는 수정하지 않았다.

## DOC-M-01 — TTS 초기화 시점이 확정된 소비자 계약과 다름

- **위치:** `task.md:200` T2.0 ListenButton, `:226` T2.4.
- **문제:** T2.4는 “첫 사용자 탭에서 `tts.init()`을 호출한 뒤 상태에 따라 안내”라고 적고, 공용 ListenButton의 마운트 시 init 요구는 빠졌다. T1.5 R3가 종료 조건으로 전제한 계약은 **마운트 시 init 및 완료 결과 반영**이다. 현재 문구는 탭 핸들러에서 init을 기다린 뒤 speak하는 구현으로 읽힐 수 있다. 또한 홈·문장·직원 화면까지 사용하는 공용 버튼 계약을 연습 화면에만 적었다.
- **근거:** `reviews/T1.5_r2_verdict.md:48-50`, `reviews/T1.5_r3.md` 마지막 문단. `tts.init()`은 목록이 비면 최대 2초 기다리고, `speak()`는 사용자 활성화를 확인하며 동기로 실행한다. 기존 판정은 발화 전에 await하지 않도록 명시했다. 현재 task 문구가 실제 브라우저 실패를 이미 일으켰다는 뜻은 아니지만, 핵심 듣기 흐름의 소비자 구현을 잘못 유도한다.
- **권장 수정:** T2.0 공용 ListenButton에 “마운트 시 `init()` 호출 및 완료 상태 반영, 사용자 탭에서는 await 없이 동기 `speak()`, 화면 이탈 시 정리”를 명시한다. T2.4의 첫 탭 init 문구는 이 공용 계약 참조로 바꾼다. requesting 중 취소/직원 화면 버튼과 15초·8초·8초는 그대로 유지한다.

## DOC-M-02 — 확인 전 배지 규칙이 코스와 메뉴 없는 장소를 포괄하지 못함

- **위치:** `task.md:215` T2.2 확인일 표시, `:218` T2.3의 `verified:false` 조건, `:294` T4.1a; `app/src/types.ts:41`, `:70`.
- **문제:** T2.3에만 “`verified:false` 정보가 있는 장소”의 확인 전 배지가 추가됐다. T2.2는 여전히 정류장 목록에 확인일을 표시하라고 한다. 현재 `verified`는 메뉴 속성이고 장소에는 없으므로, 메뉴 없는 으능정이·전시관은 T2.3의 조건도 명확히 적용할 수 없다. 네 장소의 `checkedAt`은 모두 실제 확인 전 자리표시 날짜다.
- **근거:** `reviews/T1.1_r1_verdict.md:75-77`은 **네 곳의 날짜가 자리표시 값**임을 밝히고 T2.2에서도 확인일로 단정하지 말라고 이관했다. `downtown.json`에는 네 장소 모두 `2026-11-10`, 메뉴에만 `verified:false`가 있다. Phase 2 배포·영상 녹화는 T4.1 현장 검증보다 먼저다.
- **권장 수정:** 코스 목록과 장소 상세 모두에 적용되는 확인 상태 판정 규칙을 정한다. 최소한 현장 확인 전 네 장소 모두 확인 전 예시 정보로 표시하고, 메뉴 없는 장소도 포함한다. 메뉴의 verified를 장소 영업시간/주소의 확인 여부로 간주하지 않도록 명시한다. 장소 확인 상태 필드가 필요하면 coordinator가 데이터 계약 변경을 별도로 배정하고, 실제 확인 뒤에만 날짜/상태를 갱신한다.

## DOC-L-01 — 내 기기 제보 건수의 데이터 출처가 누락됨

- **위치:** `task.md:235` T2.6, `:243` E2E 6.
- **문제:** anchor `ssd`와 최근 500건 안내는 반영됐지만 **제보 건수는 `reports` 기준**이라는 판정 요구가 빠졌다. “내 기기 기록은 최근 500건”만 읽으면 구현자가 `events`의 `report_sent` 건수로 제보를 계산하거나 제보에도 500건 한도를 적용할 수 있다.
- **근거:** `reviews/T1.6_r1_verdict.md` 지표 판단 및 coordinator 후속은 reports가 이벤트 500건 절단 대상이 아니고 제보 건수는 `reports.length`라고 명시한다. E2E의 한 번 제보 후 +1만으로는 기록 절단 뒤 차이를 발견하지 못한다.
- **권장 수정:** “이벤트 기반 지표는 보관된 최근 500건 기준, 내 기기 제보 건수는 `reports.length` 기준”으로 구분한다. `topPhrases`의 재생 횟수/주문 문장 제외와 다음 방문 분포의 분모도 리포트 구현 설명에 적으면 좋지만, 이 권장 사항은 별도 미해결로 집계하지 않는다.

## DOC-L-02 — T4.3 실측 목록에 일부 이관 시나리오·판정 기준이 빠짐

- **위치:** `task.md:297-302` T4.3.
- **문제:** 권한 응답 시간·voiceschanged 시점·interrupted 순서·userActivation 지원 여부는 추가됐지만, “권한 최초 요청/재방문 각각 requesting→listening”, “칩 연속 탭 후 재생 표시 정상”, “콜드 스타트 한국어 음성 검출”, “오프라인에서 실제 STT 실패→직원 화면 완주”가 구체적 시나리오로 남지 않았다. 지원 여부나 이벤트 도착 시각만 적는 것으로 사용자 경로의 동작까지 검증되지는 않는다.

- **권장 수정:** 위 네 시나리오의 실행 조건·결과를 T4.3에 명시한다. 15초 적정성은 권한 팝업 응답 시간만이 아니라 onstart까지 재고, 칩 연속 탭은 이벤트 순서와 재생 표시를 함께 기록한다. iOS 미검증 정책은 유지한다.
