## takeout: 단일 boolean vs 장소별 맵 — **단일 boolean 유지가 맞음**

**근거**
- `task.md:180` T1.6 persist 필드는 `takeout`이고 장소별 맵을 요구하지 않습니다. `task.md:182`는 "`switchPlace`와 문장 생성 시 `takeout:false` 장소면 `takeout=false`로 강제"만 요구합니다.
- PRD F-05는 "장소가 바뀌면 주문을 비울지 확인"이므로 **활성 주문은 늘 한 장소**입니다(`switchPlace`·`enterPlace`가 `cart`를 `{}`로 교체, `useAppStore.ts:205–211`). 활성 주문이 하나면 포장 여부도 하나면 됩니다. 장소별 맵은 이미 비워진 주문의 선택을 기억하는 데만 쓰여 의미가 없습니다.
- 목업 `mockup/index.html:479`의 `takeout:{ssd:true,gwc:false}`와 `cart:{ssd:{},gwc:{}}`는 장바구니까지 장소별로 두는 시연용 상태입니다. `task.md` Phase 2 머리말(목업과 PRD 충돌 시 PRD 우선)과 F-05의 "전환 시 비우기"에 따라 목업의 장소별 구조는 채택하지 않습니다. 목업 `:494, :652`의 `S.takeout[pid] && P(pid).takeout` 조합은 우리 쪽 `effectiveTakeout(takeout, place)`(`useAppStore.ts:100`)과 의미가 같습니다.
- 목업의 ssd 기본값 `true`(포장)는 PRD·task.md 어디에도 근거가 없는 시연 상태이므로 store 기본값 `false`(매장)를 유지합니다. 매장으로 두면 문장에 "포장해 주세요"가 빠질 뿐 잘못된 요청은 생기지 않으므로, 안전한 쪽입니다.
- **Phase 2 연결 조건 (coordinator → T2.x 전달):** 화면은 `takeout[pid]`를 쓰지 말고 `useAppStore.takeout`과 `effectiveTakeout(takeout, currentPlace)`를 씁니다. 주문·직원·연습 화면의 문장 생성은 반드시 `effectiveTakeout` 결과를 넘깁니다.

**A-1 (nit, 권장): 장소 전환 시 takeout 초기화**
`enterPlace`가 포장 가능한 장소 사이에서는 이전 장소의 선택을 승계합니다(`useAppStore.ts:209`). 주문이 비워진 새 장소에서 사용자가 고르지 않은 "포장"이 이어지면 문장이 사용자 의도와 달라질 수 있습니다. `enterPlace`에서 실제로 장소가 바뀌는 경우(`currentPlaceId !== place.id`) `takeout: false`로 초기화하기를 권장합니다. 테스트: 포장 가능한 A에서 포장 선택 → B(포장 가능)로 전환 → `takeout === false`.

## M-01 — 이벤트·제보 저장 경계가 추가 필드를 제거하지 않음 → **타당, M 유지**

**근거**
- `useAppStore.ts:256–257` `logEvent`는 `{ ...event, t: now() }`로 입력을 그대로 펼칩니다. TypeScript의 초과 속성 검사는 객체 리터럴에만 적용되므로, `const r = { type:'practice_done', src:'phrase', score, transcript }` 같은 변수를 넘기면 컴파일이 통과하고 `transcript`가 localStorage에 저장됩니다.
- 복원(`useAppStore.ts:163`)도 `filter(isAppEvent)`라 객체를 다시 만들지 않으므로 추가 필드가 그대로 남습니다. reports(`:154–161`)도 마찬가지입니다.
- T1.6 "개인정보·인식 원문 없음", F-15 "인식 원문은 기록하지 않음", 7장 "인식 결과를 저장하지 않습니다"는 명시 요구입니다. 연습 화면이 STT 결과와 점수를 한 객체로 다룰 가능성이 높아 실제로 생길 수 있는 경로이고, 지켜야 할 곳은 저장 경계입니다. → M 유지.
- `screen`·ID가 임의 문자열이라 원문이 ID 자리에 들어갈 수 있다는 지적도 타당합니다. 데이터 ID는 모두 소문자·숫자·하이픈입니다(`downtown.json`: `ssd`, `gwc-1`, `downtown-halfday` 등).

**수정 지침**
1. `events.ts`에 `toAppEvent(v: unknown): AppEvent | null` 추가. 종류별 허용 필드만으로 **새 객체를 구성**하고 필드 값도 검증합니다(M-04 포함).
   - 공통: `t`는 유한한 수.
   - ID(`placeId`, `phraseId`)와 `screen`: `/^[a-z0-9][a-z0-9_-]{0,63}$/` 일치(선택 필드는 없으면 생략, 있는데 형식이 틀리면 **이벤트 전체 폐기**).
   - `score`: 유한한 수, 0 ≤ score ≤ 100. 범위 밖이면 이벤트 폐기.
   - `src`: `'order' | 'phrase'`, `kind`: `REPORT_KINDS`.
   - `isAppEvent`는 `toAppEvent(v) !== null`로 재정의하거나 제거합니다.
2. `logEvent`: `const e = toAppEvent({ ...event, t: now() }); if (e) set(...)`. 폐기 시 기록하지 않습니다(throw하지 않음).
3. 복원: `raw.events.map(toAppEvent).filter(nonNull).slice(-MAX_EVENTS)`.
4. reports도 `{ kind, t, placeId? }`만으로 재구성하고 placeId에 같은 ID 형식 검사를 적용합니다. `addReport`의 placeId도 같은 검사(틀리면 placeId 생략).
5. 테스트: (a) `transcript`·임의 필드가 붙은 변수로 `logEvent` → persist JSON 문자열에 `transcript`와 원문 문자열 없음. (b) 추가 필드가 있는 저장값 복원 → 필드 제거됨. (c) 한글 문장을 `screen`/`phraseId`로 넘김 → 기록되지 않음. (d) reports 추가 필드 제거.

## M-03 — 메모리 대체 후 초기화해도 다음 실행에 옛 기록이 복원됨 → **타당, M 유지**

**근거**
- `safeStorage.ts:37–39, 63–66`: 실행 도중 한 번이라도 쓰기에 실패하면 `local`을 영구히 버립니다. 이후 `clearEvents`/`resetData`(`useAppStore.ts:267–268`)는 메모리에만 반영되고 localStorage에는 실패 직전 스냅숏이 남아, 다음 실행 때 지운 기록·제보·주문이 되살아납니다.
- task.md T1.6 "초기화 가능", S12 "기록 초기화"는 사용자가 지웠다고 믿는 기능입니다. 되살아나면 기능 약속을 어기는 것이고 7장의 개인정보 신뢰에도 맞지 않습니다. 대체 경로는 드물지만 일단 들어가면 결과가 확정적이므로 M 유지.

**수정 지침 (M-02·M-03 공통, `safeStorage.ts`)**
1. 상태를 `local: Storage | undefined`(접근 가능 핸들)와 `writable: boolean`으로 분리합니다. probe 쓰기 실패 시 `local`은 유지하고 `writable = false`.
2. `getItem`: `local`이 있으면 읽기를 시도합니다(읽기 예외일 때만 `local = undefined`). 쓰기 불가 상태여도 읽은 값을 메모리에 복사합니다.
3. `setItem`: 메모리에 쓴 뒤 `local`이 있으면 `setItem`을 시도합니다. 실패하면 **`local.removeItem(k)`를 시도**(옛 스냅숏 제거 + 공간 확보)하고 `setItem`을 한 번 더 시도합니다. 그래도 실패하면 `writable = false`. 어느 경우든 localStorage에 **옛 값이 남지 않게** 하는 것이 핵심입니다.
4. `removeItem`: `writable`과 무관하게 `local`이 있으면 항상 `local.removeItem`을 시도합니다.
5. `mode`는 `'local' | 'read-only' | 'memory'`로 확장하거나, 기존 두 값을 유지하고 `writable`이 false면 `'memory'`로 보고합니다(소비자는 현재 없음, 택1 후 주석에 명시).
6. 영구 반영 실패를 호출 측에 돌려주는 API는 이번에 도입하지 않습니다(UI 소비자 없음, 3번으로 되살아남이 막힘).
7. 테스트:
   - `getItem`은 기존 JSON을 반환하고 `setItem`은 항상 Quota 예외를 던지는 저장소에서 시작 → `lang`·북마크·주문 복원.
   - local에 place_view 1건 저장 → 이후 쓰기 실패 → `resetData()` → 쓰기 가능한 새 wrapper/store 생성 → events 0건, cart 비어 있음.
   - 쓰기 실패 직후 원본 저장소에 해당 key가 남지 않음(또는 최신 값).

## M-05 — 다른 장소 인자로 setTakeout을 부르면 현재 장소의 매장 고정이 풀림 → **타당, L로 조정**

## M-06 — 손상 복원 시 cart와 currentPlaceId가 맞지 않음 → **부분 타당, L**

**근거**
- 정상 persist는 `cart`와 `currentPlaceId`를 같은 스냅숏에 함께 쓰고, 모든 수량 변경은 현재 장소에만 일어나므로(`canEdit`) 둘이 어긋난 상태는 **저장소 손상으로만** 생깁니다. 정상 사용 흐름의 결함이 아니라는 점에서 부분 타당입니다.
- 그래도 생기면 `switchPlace`가 `cartCount(s.cart, s.currentPlaceId)`만 보므로 남은 주문을 확인 없이 지웁니다(`:227–231`). F-05 "비울지 확인"을 어기고, 기존 테스트도 복원 뒤의 동작은 검증하지 않습니다. → L.

**수정 지침**
1. `merge`(또는 `sanitizePersisted` 뒤 정규화 단계)에서 **단일 활성 주문 불변식**을 복구합니다.
   - `currentPlaceId`가 문자열이면 `cart`를 `{ [currentPlaceId]: cart[currentPlaceId] }`만 남깁니다(없으면 `{}`).
   - `currentPlaceId`가 null이고 비어 있지 않은 장소가 **정확히 하나**면 `currentPlaceId`를 그 장소로 복구합니다.
   - null이고 둘 이상이면 `cart = {}`로 비웁니다(어느 주문이 맞는지 알 수 없으므로 정책으로 명시).
   - 복원된 `takeout`은 장소 정보가 없어 그대로 두며, 문장 생성 시 `effectiveTakeout`이 방어합니다(주석으로 명시).
2. 보조 방어: `switchPlace`의 확인 조건을 "어느 장소든 수량이 남아 있으면"(전체 cart 합계)으로 바꿉니다.
3. 테스트: `{cart:{ssd:{m1:2}}}`(currentPlaceId 없음) 복원 → `currentPlaceId === 'ssd'` → `switchPlace(gwc)`가 `needsConfirm:true` → 취소 시 주문 유지, 확인 시 비움. 두 장소 cart + null 복원 → cart 비움. currentPlaceId와 다른 장소의 cart → 제거.
