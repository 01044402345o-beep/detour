# T1.2 다국어 사전 검토 R1

- 검토일: 2026-11-23 / 검토자: Codex
- 범위: `app/src/i18n/` 사전 3개, 번역 함수, 직원 고정 문구, 언어 이름, 하드코딩 검사 및 테스트.
- 기준: `task.md` T1.2 및 Phase 2 E2E 5, `prd.md` v0.3 1.3·F-04·F-08·F-09·F-11·7장, `mockup/index.html` 사전. 운영자 리포트(S13)는 한국어 고정이라는 coordinator 결정을 적용했다.
- 수정한 파일은 이 보고서 하나뿐이다. 아래 재현은 소스 문자열을 메모리에서 검사했으며 앱 파일을 변경하지 않았다.

## M-1 — 운영자 리포트의 한국어 고정 계약이 사전·검사에 반영되지 않음

- **위치:** `app/src/i18n/en.json:208`, `ja.json:208`, `zh.json:208`의 `operator.*`; `index.test.ts:79`; `hardcodeCheck.ts:18`, `hardcodeCheck.ts:49`.
- **문제:** 기관용 S13 문구를 세 언어 사전에 제공하고 `operator.sampleBadge`를 다국어 필수 키로 검사한다. 반면 한국어 운영자 문구 정의와 해당 영역의 검사 예외가 없다. 이후 화면이 제공된 번역 키를 사용하면 언어 전환에 따라 S13도 바뀌고, 한국어를 직접 넣으면 현재 검사에 걸린다. 아직 S13 화면은 없으므로 현재 렌더링 오류라는 뜻은 아니다.
- **근거:** coordinator의 명시적 결정 및 Phase 2 E2E 5의 한국어 고정 영역 유지 기준. `findHardcoded('const A=()=> <h1>운영자 리포트</h1>', 'src/screens/Operator.tsx')`가 위반 1건을 반환함을 재현했다.
- **권장 수정:** 운영자 본문을 별도 한국어 상수 모듈로 제공하고 이를 고정 영역 예외·테스트에 반영한다. `operator.*`의 세 언어 사전 요구와 해당 필수 키 테스트는 제거/이전한다. 관광객 설정 화면의 진입 링크 `settings.operatorReport`는 다국어로 유지해도 된다. 화면 전체를 무조건 제외하기보다는 지정된 한국어 문구 모듈을 사용하게 하고, Phase 2에서 언어 전환 전후 S13 본문 불변을 확인한다.

## M-2 — 흔한 영어 UI 작성 방식이 하드코딩 검사를 우회함

- **위치:** `app/src/i18n/hardcodeCheck.ts:18`, `:59`, `:77`, `:101`, `:167`; `hardcodeCheck.test.ts`의 규칙 및 저장소 검사.
- **문제:** 영어는 일부 JSX 위치의 직접 리터럴만 검사한다. 지역 변수, 배열·함수 호출을 통해 표시되는 문구 및 submit 버튼의 `value`는 놓친다. 또한 `.ts`는 `screens/`, `ui/`만 검사하고 `data/`, `domain/`은 디렉터리 전체를 제외하여, 한국어 콘텐츠라는 제한보다 예외 범위가 넓다.
- **근거:** 아래 세 소스 모두 `findHardcoded(source, 'src/screens/X.tsx')`가 `[]`를 반환했다.

  ```tsx
  const A = () => { const label = 'Show to staff'; return <button>{label}</button> };
  const B = () => <input type='submit' value='Pay now' />;
  const C = () => <p>{['Open', 'Closed'].join(' / ')}</p>;
  ```

  `isScanned('src/hooks/useToast.ts')`도 `false`다. 이는 T1.2의 “예외 목록 밖 하드코딩 문구 없음”을 검사 통과만으로 보장하지 못하며, Phase 2 E2E 5에서 언어 전환 후 남는 영어를 놓칠 수 있다. 현재 앱은 빈 화면 골격이므로 실제 화면에 이 누락이 이미 발생했다는 주장은 아니다.
- **권장 수정:** 화면 문자열의 허용 작성 규칙을 명시하고 변수·배열·표시용 호출 인자 및 버튼 `value`의 검사를 보강한다. 모든 런타임 TS/TSX를 후보로 삼되 비가시 기술 문자열은 용도별로 제외하고, 한국어 콘텐츠 예외는 실제 데이터/생성 모듈로 좁힌다. 위 반례와 hook/helper의 toast 문구를 회귀 사례에 추가한다. 정적 분석이 해결하지 못하는 경로는 Phase 2에서 각 언어의 실제 표시 문구를 검증해야 한다.

## L-1 — params 전체 생략 시 미치환 자리표시자에 경고가 없음

- **위치:** `app/src/i18n/index.ts:60-70`, `index.test.ts:131`.
- **문제:** `params`가 선택 인자이고 `if (!params) return value`로 조기 반환한다. 따라서 `t('ja', 'menu.items')`는 `{count}点`를 경고 없이 반환한다. 일부 인자만 누락하면 경고하지만 객체 전체를 빠뜨리는 경우는 더 조용하게 실패한다.
- **근거:** T1.2의 자리표시자 사용 계약과 현 테스트의 “빠진 params는 자리표시자를 남기고 경고한다” 동작이 전체 생략에는 적용되지 않는다. 사전 간 자리표시자 일치 테스트는 호출부의 누락을 검출하지 못한다.
- **권장 수정:** 인자 객체가 없어도 자리표시자를 검사하여 개발 모드에서 경고하고 전체 생략 사례를 추가한다. 가능하면 키별 필수 params를 타입으로 제한한다. 문자열 자체에는 영어 fallback을 추가하지 않는다.

## L-2 — 일반 요청에 대한 직원 응답도 영어·일본어에서 주문으로 단정

- **위치:** `app/src/i18n/en.json:164`, `ja.json:164`; `staffKo.ts`의 `STAFF_REPLY_KEYS.yes`.
- **문제:** `reply.yesBody`가 영어는 “Your order is understood.”, 일본어는 “注文が伝わりました。”이다. 일반 문장 카드에서 직원이 ‘네’를 눌러도 같은 매핑을 쓰면 길 묻기 등 요청을 주문으로 표현한다. 중국어 “店员明白了。”는 이 문제가 없다.
- **근거:** PRD F-10은 주문과 일반 요청을 구분하고 `staffKo.ts`도 `noteOrder`/`noteRequest`를 분리했으나 응답 본문은 주문에 한정되어 있다. 목업에서 이어받은 문구지만 PRD 우선 기준에서는 일반 요청 경로도 지원해야 한다.
- **권장 수정:** 영어 “The staff understood your request.”, 일본어 “スタッフに伝わりました。”처럼 두 경로에 쓸 수 있는 문구로 바꾸거나 주문/일반 요청 응답 키를 구분한다.

## 통과 및 조정 타당성

- 각 언어는 문자열 잎 키 **196개**이며 세 언어의 키 집합·자리표시자 이름 및 출현 수가 같다. 빈 값이 없고 ja/zh가 en 값을 그대로 복제한 항목도 없다. `cd app; npx vitest run src/i18n` 결과 **2개 파일 / 24개 테스트 통과**.
- 비제휴 고지에는 독립 정보 안내, 가게와 비제휴, 공식 주문 서비스가 아님이 모두 포함된다. 음성 고지에는 앱의 음성·인식 결과 미저장과 브라우저 음성 서비스 처리 가능성이 모두 포함된다. 인식 일치도 및 발음 점수가 아니라는 설명, 가격/총액 확인 필요 문구도 세 언어에서 의미가 유지된다. 총액을 계산대에서 확인하라는 표현은 PRD 의미를 훼손하지 않는다.
- `settings.privacy`는 음성 미저장과 기기 내 이용 기록 저장을 구분하며 PRD 우선 규칙에 맞는다. 마이크 사용 전 고지의 실제 노출 시점은 T2 화면 연결 때 검증할 사항이다.
- `understood` → `result.closeMatch`는 직원의 이해를 보장하던 문구를 인식 결과의 일치 설명으로 바꾸므로 F-09에 맞다. 다만 낮은 점수에도 무조건 표시하지 않도록 화면에서 조건부 사용해야 한다.
- `tip`의 “짧게 들렸다” → “일치하지 않았다” 변경은 편집거리 기반 검사에서 알 수 없는 발음 특성을 단정하지 않으므로 타당하다. 일본어·중국어에서 추가로 명백한 중대 오역은 발견하지 않았다. 최종 자연스러움 검수는 T4.2 원어민 검수에 남는다.
- 목업 `at`는 en=`AT`, ja/zh=빈 문자열이며 실제 `t('at')` 호출이 없다. 이를 제거하는 것은 빈 문자열 금지에 맞고 현재 목업 기능을 잃지 않는다.
- 직원 안내 2종과 응답 버튼 4종은 `STAFF_KO`에서 한국어 고정, 손님용 응답은 `STAFF_REPLY_KEYS`에서 번역 키로 매핑된다. 언어 이름의 자국어 표기와 배지는 고정하는 것이 합리적이다. 이 추가 예외 및 운영자 고정 영역은 Phase 2 E2E 기준에도 명시해야 한다.

## 영어 fallback 없음 정책의 잔여 위험

현재 구현은 누락 키를 영어로 대체하지 않고 키 문자열을 반환하며 개발 모드에서 경고한다. 이는 요구사항에 맞으며, 초기 언어 미선택 상태의 `DEFAULT_LANG='en'`은 선택한 ja/zh의 누락 번역을 영어로 대체하는 fallback과 다르다. 다만 production에서는 누락 키가 조용히 기술 문자열로 노출되고 `pickL10n`은 불완전한 런타임 데이터에 방어 처리가 없다. 정적 `MessageKey`·동일 키 검사·콘텐츠 스키마 검증을 유지하고 동적 키 단언을 피하며, Phase 2 E2E에서 고지/오류/응답 경로까지 실제 문구를 확인하는 것이 적절하다. 현재 사전의 누락 결함으로 별도 집계하지 않았다.

단위 테스트 통과가 Phase 2 화면의 언어 전환 또는 한국어 고정 영역 유지까지 증명하지는 않는다. E2E는 task 단위 실행 금지 규칙에 따라 실행하지 않았다.
