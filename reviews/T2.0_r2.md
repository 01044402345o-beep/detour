## 미해결 항목

### T2.0-R2-L01 — 포커스 후보 필터가 비활성·CSS 숨김 요소를 포함함 (R1 M01 잔여)

- **위치:** `app/src/ui/overlay.ts:48`~`:53` (`FOCUSABLE`, `focusableIn`), `:57` 이하 `trapTab`.
- **문제:** `[hidden]` 조상만 제외하므로 `display:none`·`visibility:hidden`인 버튼은 후보에 남는다. 선택자 OR 분기 때문에 `<button disabled tabindex="0">`도 `[tabindex]`로 다시 들어오고, `tabindex="-2"` 같은 음수도 -1이 아니라는 이유로 포함된다. 첫 요소에서 Shift+Tab을 눌렀는데 마지막 후보가 숨김/비활성 버튼이면 preventDefault 후 focus가 실패해 순환이 동작하지 않는다. 마지막 실제 요소 뒤에 숨김 후보가 있으면 실제 마지막 요소도 끝점으로 인식하지 못한다.
- **근거/확인:** 별도 파일을 쓰지 않고 Node+jsdom에서 실제 `overlay.ts`를 import해 후보 목록을 검사했다. visible, `style="display:none"`, disabled+tabindex=0, tabindex=-2 버튼을 넣었을 때 **네 개 모두 반환**됐다. 이는 판정서의 “비활성 아니고 보이는 요소” 조건을 충족하지 않는다. 기존 테스트는 일반 disabled 버튼만 검사하므로 통과한다.
- **권장 수정안:** 후보 수집 뒤 `tabIndex >= 0`, 실제 disabled 상태(`:disabled`, disabled fieldset 포함), inert/hidden 조상 및 렌더 가시성을 걸러낸다. 실제 브라우저에서 숨김 버튼을 처음/끝에 둔 Tab·Shift+Tab 회귀 검사를 추가하고, disabled+tabindex 및 음수 tabindex도 검사한다. jsdom은 레이아웃을 계산하지 않으므로 실제 가시성 검증과 jsdom 단위 테스트를 구분해야 한다.

### T2.0-R2-L02 — 겹친 시트의 활성 순서와 시각 순서가 다르고, 아래 시트가 비활성화되지 않음 (신규)

- **위치:** `app/src/ui/Sheet.tsx:22`, `:43`~`:57`, `app/src/ui/overlay.ts:21`~`:26`, `app/src/styles/ui.css`의 `.ui-sheet-dim`.
- **문제:** stack은 effect가 실행된 열림 순서로만 관리되고, 포털 DOM의 순서나 시트별 z-index를 맞추지 않는다. JSX에서 A 다음 B를 선언하고 **B만 열었다가 A도 열면**, A가 stack 맨 위여서 focus·Esc·Tab을 받지만 DOM에서는 뒤의 B가 위에 그려진다. 사용자가 보는 시트와 키보드로 조작하는 시트가 달라진다. 또한 lockBackground는 overlay 바깥 형제만 inert 처리하므로 아래 시트 자체는 계속 접근 가능한 상태이며, 두 dialog가 모두 aria-modal=true로 남는다.
- **근거/확인:** 소스상 stack.push와 DOM 표시 순서를 연결하는 처리가 없고 두 dim은 동일한 위치·쌓임 규칙을 쓴다. 실제 helper의 2중 lock 검사는 main=true, 아래 시트 inert=false, status=false를 반환했다. 기존 겹침 테스트는 A→B 순서로 열고 B→A 순서로 닫는 경우의 main inert 카운터와 Esc만 확인한다. 역순 열림·아래 시트 접근성·순서와 다른 닫힘은 검사하지 않는다. 시각 쌓임 결과는 소스 분석이며 이번 검토에서 브라우저 캡처로 재현하지는 않았다.
- **권장 수정안:** 겹침을 지원한다면 활성 스택과 시트 z-index/DOM 순서를 일치시키고, 맨 위를 제외한 시트의 dim 또는 dialog를 inert 처리한다. 포커스 복귀도 현재 최상단 시트가 있으면 그 안으로, 전부 닫혔으면 살아 있는 원래 opener로 복구한다. B→A 열림, 위/아래 시트 각각 닫기, 아래 시트 탐색 차단을 추가 검증한다. 겹침을 지원하지 않기로 한다면 동시에 하나만 열리도록 공용 API에서 제한하고 usage의 겹침 지원 설명을 바꾼다.

## inert·토스트 안전성

- main·탭바의 기존 inert 존재 여부를 보관하고 마지막 release에서만 복원하는 카운터는 일반적인 A→B→B 닫힘→A 닫힘 순서에서 정상이다. release 중복 호출 방지도 있다.
- 현재 ToastProvider의 role=status는 overlay의 형제이며, lockBackground에서 명시적으로 제외한다. 토스트는 문자열 표시이고 포커스 가능한 컨트롤이 없으므로 이 예외가 키보드 배경 조작 경로를 만들지는 않는다. helper 실행으로 status에 inert가 붙지 않는 것도 확인했다.
- 따라서 **현재 토스트 DOM 구조에서 inert로 토스트를 숨기는 회귀는 발견하지 못했다.** 실제 스크린리더가 aria-modal 바깥 live region을 읽는지는 별도 실기기 확인 사항이며, 이번 테스트로 낭독까지 보장했다고 주장하지 않는다.
- 겹친 시트의 문제는 위 R2-L02에 집계했으며 같은 원인을 중복 건수로 세지 않았다.
