## L — 보완 요청

### L-01. 새 로더 테스트가 원본 URL 객체를 직접 변경해 모의 함수를 복원하지 않는다

- 위치: `app/src/screens/Lang/introMedia.test.ts:8–12`.
- `vi.stubGlobal('URL', Object.assign(URL, { createObjectURL: create, revokeObjectURL: revoke }))`는 원래 전역 URL 생성자 자체에 모의 함수를 먼저 넣는다. `vi.unstubAllGlobals()`가 복원하는 참조도 이미 변경된 같은 객체여서 원래 메서드(또는 원래 없던 상태)는 돌아오지 않는다.
- 따라서 이 파일의 afterEach 뒤에도 해당 함수가 남는다. 현재 테스트는 매번 같은 mock을 다시 설치하고 Vitest 파일 격리가 있어 이번 191개 실행에서 실패하지 않았지만, 이 환경에 추가되는 테스트가 실제 URL 동작이나 지원 여부를 검사하면 잘못된 환경을 보게 된다. 앱 배포 코드 결함은 아니다.
- 요청: 두 속성의 원래 descriptor를 저장하고 afterEach에서 각각 복구하거나 원래 없었다면 삭제할 것. 원본 객체를 미리 변경하지 않는 대체 생성자를 stub하는 방법도 가능하다. Lang.test.tsx의 currentTime descriptor 복구와 같은 원칙으로 처리하면 된다.

## 오프라인·모바일·라이선스와 검증 한계

- 추가 자산 4개 합계 **967,080B(약 0.97MB)**. MP4는 기본 2MiB 개별 사전 캐시 제한 아래다. 기존 dist/sw.js에 영상·정지 그림 3개의 revision 항목이 있다. PRECACHE_STATUS는 전체 manifest의 matchPrecache 결과로 판단하므로 새 자산도 준비 완료 조건에 포함된다. 다운로드 실패는 최초 설치/준비 완료를 지연시킬 수 있지만 새로 준비 완료를 오판하는 경로는 발견하지 못했다.
- muted·playsInline, 전체 fetch → blob URL, 미디어 오류/실제 play 거부 → 정지 그림 경로가 있다. blob 재생은 SW의 Range 응답에 직접 의존하지 않는다. unmount/StrictMode에서 늦게 도착한 URL도 해제한다. fetch 자체 abort는 없고 failed 후 blob은 unmount까지 남으나 현재 파일 크기로 중대 메모리 결함을 단정할 근거는 없다.
- 실제 iOS Safari·Android/저전력 모드·메모리 회수·오프라인 재접속은 이번 R2에서 직접 시험하지 않았다. 모바일 viewport와 jsdom play/pause mock은 실기기 디코딩·자동 재생 정책을 입증하지 않는다. 작동 중인 현재 play 요청의 AbortError는 retry/fallback 없이 무시하므로 해당 실기기 시나리오에서 재생이 멎지 않는지 확인할 가치는 있으나 이번 검토에서 발생을 재현하지는 못했다.
- 테스트는 onError 이벤트, unmount 후 매우 늦은 별도 fetch 완료, 실제 seeking/seeked·readyState 변화를 모두 모사하지 않는다. StrictMode 검사는 같은 가짜 URL 문자열의 호출 수 비교여서 서로 다른 URL 각각의 정확한 소유권까지 입증하지 않는다. 위 잔여 범위를 앱 결함으로 추정해 별도 M 지적하지 않았다.
- 제공된 원본 LICENSE의 구분(코드 MIT, Markdown CC BY-NC, 문서를 따라 상업·의뢰 영상을 제작할 추가 허락)과 CREDITS가 일치한다. 직접 렌더한 결과물에 문서의 CC BY-NC를 그대로 붙이지 않은 것도 원문 FILMS YOU MAKE와 맞는다. MIT.txt의 일반 저작권 자리표시자는 함께 보존된 상위 LICENSE의 실제 권리자 고지로 보완된다. 원본 폴더는 git 미포함이므로 향후 엔진 소스를 별도 전달하면 두 고지 파일도 같이 전달해야 한다.
