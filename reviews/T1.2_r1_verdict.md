## M-1 — 운영자 리포트 한국어 고정이 사전·검사에 반영되지 않음 → **타당, M 유지**

## M-2 — 흔한 영어 작성 방식이 하드코딩 검사를 우회함 → **부분 타당, M 유지(보강 범위 축소)**

**근거**
- `hardcodeCheck.ts:101–130`은 라틴 문자 리터럴을 JSX 자식이나 보이는 속성에 **직접** 있을 때만 잡습니다. Codex의 반례 세 개(지역 변수 `label`, `<input type="submit" value=…>`, `['Open','Closed'].join()`)가 모두 통과하는 것을 코드로 확인했습니다. `VISIBLE_ATTRS`(`:59–69`)에 `value`가 없습니다.
- `isScanned`(`:77–82`)는 `.ts`의 경우 `screens/`·`ui/`만 검사하므로 `hooks/`·`lib/`의 한국어·영어 토스트 문구도 빠집니다.
- T1.2 완료 조건 "예외 목록 밖 하드코딩 문구 없음(검사 스크립트)"은 Phase 2 작업자 여럿이 화면을 쓸 때 쓰는 **관문**입니다. 영어는 작업자가 가장 흔히 실수로 남기는 언어라, 지금의 구멍은 실제로 생길 가능성이 높습니다 → M 유지.
- 다만 정적 분석으로 모든 데이터 흐름(변수 → 표시)을 완전히 추적하라는 요구는 과합니다. className·라우트·이벤트 이름 같은 라틴 기술 문자열과 구분할 수 없어 오탐이 커집니다. 남는 구멍은 Phase 2 E2E 5(3개 언어 실제 표시)가 맡습니다. 또 `data/`·`domain/` 디렉터리 예외는 실제로 한국어 콘텐츠·한국어 문장 생성 모듈만 있어, 지금 좁힐 필요는 없습니다(새 파일이 생기면 그때 재검토). 이 두 점에서 부분 타당입니다.

**수정 지침 (오탐을 낮게 유지하는 3가지)**
1. `VISIBLE_ATTRS`에 `value`를 더합니다. 단 `<input>`의 `type`이 `submit`/`button`/`reset`이거나 `<button>`·`<option>`일 때로 한정하고, 그 밖의 `value`(폼 상태값)는 제외합니다. 판단할 수 없으면 `value`에 라틴 문장형(2번 규칙)이 오면 위반으로 처리합니다.
2. **문장형 라틴 리터럴 규칙**: 검사 대상 파일 안의 **모든 위치**(변수 초기값, 배열 요소, 함수 인자, 객체 값)에서 다음 패턴의 문자열을 위반으로 잡습니다.
   - `/^[A-Z][a-z']+(?:[  ][A-Za-z'’]+)+[.!?…]?$/` (대문자로 시작하고 공백으로 나뉜 단어가 2개 이상) — `'Show to staff'`, `'Pay now'`를 잡습니다.
   - 또는 끝이 `.`/`!`/`?`이고 공백을 포함하는 라틴 문자열.
   - 한 단어(`'Open'`)나 소문자·하이픈 식별자(`'btn-primary'`, `'place_view'`)는 잡지 않습니다. 단어 하나짜리 영어 노출은 E2E 5로 넘깁니다(지침에 명시).
   - 예외: `BRAND_TERMS`, `ALLOWED_LITERALS`, `console.*`·`Error(...)` 인자(개발자용), 타입·import 위치(기존 규칙).
3. **검사 범위 확장**: `isScanned`를 "`src/` 아래 모든 `.ts`·`.tsx`(EXEMPT_PATHS 제외)"로 넓힙니다. 새로 들어오는 `.ts`(`store/`, `speech/`, `hooks/` 등)에는 CJK 규칙과 2번 문장형 규칙만 적용되므로 오탐이 거의 없습니다. 확장 후 현재 저장소 전체 검사(`hardcodeCheck.test.ts`의 저장소 테스트)가 통과해야 하며, 걸리는 기존 문자열이 있으면 사전으로 옮기거나 개발자용(`console`/`Error`)인지 확인합니다.
4. 규칙 주석(`:5–11`)을 갱신하고 "정적 검사가 못 잡는 경로(한 단어 영어, 동적 조합)는 Phase 2 E2E 5가 맡는다"를 적습니다.
5. 회귀 테스트: Codex 반례 A(변수)·B(submit value) → 위반. C(`['Open','Closed']`)는 한 단어라 **통과가 의도임**을 테스트 이름으로 명시. `src/hooks/useToast.ts`의 `toast('저장했어요')`·`toast('Saved to your list.')` → 위반. 오탐 방지: `className="flex gap-2"`, `navigate('/place/ssd')`, `logEvent({ type: 'place_view' })`, `console.warn('Missing key x.')` → 통과.

## L-1 — params 객체를 통째로 빠뜨리면 경고가 없음 → **타당, L 유지**

**근거**
- `index.ts:66` `if (!params) return value;`가 자리표시자 검사를 건너뜁니다. 그래서 `t('ja','menu.items')`는 `{count}点`을 경고 없이 화면에 내보냅니다. 일부만 빠뜨린 경우(`:69`)보다 더 조용히 실패합니다. 화면에 `{count}`가 그대로 보일 뿐 기능 손상은 작으므로 L.

**수정 지침**
1. 조기 반환을 없애고, `params ?? {}`로 치환 루프를 항상 돌립니다(빠진 이름마다 개발 모드 경고, 자리표시자는 그대로 둠 — 영어 fallback 없음 유지).
2. 키별 필수 params 타입 제한은 이번에 도입하지 않습니다(선택 사항, 사전 타입에서 템플릿 리터럴로 추출하는 비용 대비 효과가 작음).
3. 테스트: `t('ja','menu.items')`가 `{count}点`을 반환하고 `console.warn`이 1회 호출됨(DEV). 자리표시자가 없는 키를 params 없이 부르면 경고 없음.

## L-2 — "네" 응답 본문이 일반 요청에서도 "주문이 전달됨"으로 표시 → **타당, L 유지**

**근거**
- PRD F-10은 일반 문장에서 연 직원 화면을 "외국인 손님의 요청입니다"로 구분하고(`staffKo.ts`의 `noteOrder`/`noteRequest`), F-11의 응답 버튼 4종은 두 경로 모두에서 씁니다(task.md Phase 2 E2E 3: 일반 경로에서도 응답 "네"까지 완주). 그런데 `reply.yesBody`가 en "Your order is understood.", ja "注文が伝わりました。"로 주문에 한정되어 있습니다. 길 묻기 같은 일반 요청에도 "주문"이라고 표시되므로 의미 오류입니다. zh "店员明白了。"는 경로와 무관한 표현이라 문제가 없습니다.
- 목업에서 가져온 문구지만, task.md T1.2의 "PRD 우선" 규칙에 따라 고칩니다. 표시가 어색할 뿐 흐름이 막히지는 않으므로 L.

**수정 지침**
1. 키를 나누지 않고 두 경로 공용 문구로 바꿉니다(가장 단순하고, `STAFF_REPLY_KEYS` 계약이 바뀌지 않음).
   - en `reply.yesBody`: "The staff understood you."
   - ja `reply.yesBody`: "スタッフに伝わりました。"
   - zh: 유지.
2. 다른 응답 본문도 같은 기준으로 점검합니다. `soldBody`("Please choose something else.")는 품절 응답이 주문 맥락에서만 의미가 있어 유지합니다(F-11 "품절이면 주문 수정으로 연결"). `wait`·`pay`는 경로와 무관한 표현이라 유지.
3. ja 문구의 자연스러움 최종 확인은 T4.2 원어민 검수에 남깁니다.
4. 테스트: 필요 없음(문구 변경). 기존 키 집합·자리표시자 테스트 통과만 확인.

## Codex의 통과 판정 — 동의

- 세 언어 키 집합·자리표시자 일치, 빈 값 없음, ja/zh가 en을 복제하지 않음, 영어 fallback 없음(`t()`가 키 문자열 반환 + DEV 경고), `DEFAULT_LANG='en'`은 언어 미선택 시 기본값이지 fallback이 아님 — 모두 T1.2 완료 조건과 맞습니다.
- 비제휴·음성 처리·가격/총액 확인 필요·인식 일치도 문구, `settings.privacy` 교체(PRD F-08·7장), `result.closeMatch`·`tip` 표현 조정(F-09: 발음 정확도를 단정하지 않음)은 타당합니다. `result.closeMatch`를 낮은 점수에서는 표시하지 않는 조건은 T2.4 화면 몫입니다.
- 직원 고정 문구(`STAFF_KO`)와 손님 언어 매핑(`STAFF_REPLY_KEYS`), 언어 이름의 자국어 표기 고정은 PRD 1.3과 맞습니다.
- 목업의 `at` 키 제거(빈 문자열 금지, 호출부 없음)는 타당합니다.
- production에서 누락 키가 키 문자열로 노출되는 위험은 정적 `MessageKey` 타입과 키 집합 테스트로 막히므로 별도 결함으로 세지 않습니다(Codex와 같은 판단).

## 실기기·E2E 이관

T1.2 지적은 모두 단위 테스트로 검증할 수 있어 T4.3으로 넘길 것은 없습니다. 언어 전환 후 실제 표시(한 단어 영어 잔존, S13 불변)는 Phase 2 E2E 5가 맡습니다.
