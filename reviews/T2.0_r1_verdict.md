## M01 — 타당, L로 조정 (이번 라운드 필수)

**근거**
- `Sheet.tsx:29–41`은 열릴 때 시트에 focus를 주고 Esc만 처리합니다. Tab 순환도, 배경 차단도 없습니다. 그런데 `:56`에서 `aria-modal="true"`를 선언하므로 선언과 실제 동작이 다릅니다.
- 시트는 `#app-overlay`에 포털로 그려집니다. 이 자리는 `AppRoutes.tsx`의 `main.app-view`·TabBar와 **같은 부모(app-frame) 아래 형제**입니다. 배경을 차단할 지점이 분명하므로 고치기 쉽습니다.
- 심각도 조정 이유:
  - PRD 7장 접근성 요구(174행)는 터치 44px, 대비 4.5:1, 글씨 크게입니다. 키보드 조작은 명시 요구가 아닙니다.
  - 시연 기기는 터치 전용 안드로이드 크롬입니다. Tab 키로 빠져나가는 일은 시연 경로에서 일어나지 않습니다.
  - 다만 TalkBack처럼 `aria-modal`을 온전히 따르지 않는 화면 낭독기에서는 스와이프로 배경(주문 비우기 확인 중의 메뉴 버튼 등)에 닿을 수 있습니다.
  - 그래서 L로 낮추되, 주문 비우기 확인 시트(T2.3)와 ReportSheet(T2.6)가 모두 이 공용 계약을 쓰므로 병렬 작업 전에 고칩니다.

**수정 지침**
1. 시트가 열려 있는 동안 배경에 `inert`를 겁니다. `#app-overlay`의 형제(`main.app-view`, 탭바)에 effect로 `inert` 속성을 설정하고, 닫힐 때 원래 값으로 되돌립니다. React 19는 `inert` 불리언 속성을 지원합니다.
   - 시트가 여러 개 겹칠 경우에 대비해 모듈 단위 열림 카운터로 관리합니다. 마지막 시트가 닫힐 때만 해제합니다.
   - inert는 키보드와 화면 낭독기 탐색을 함께 막으므로, 이것이 핵심 수정입니다.
2. Tab/Shift+Tab 순환을 추가합니다. 시트 안의 포커스 가능 요소 중 `disabled`가 아니고 보이는 것들 사이에서 마지막에서 Tab이면 첫 요소로, 첫 요소(또는 시트 컨테이너)에서 Shift+Tab이면 마지막 요소로 보냅니다. 포커스 가능 요소가 없으면 시트 컨테이너에 그대로 둡니다. 기존 Esc 처리와 같은 keydown 핸들러에 넣습니다.
3. 닫힐 때 포커스 복귀(`:39`)는 지금처럼 유지합니다. inert를 해제한 **다음에** 복귀시킵니다(inert 요소에는 focus가 가지 않음).
4. 테스트(`components.test.tsx`):
   - 열림 시 `app-view`와 탭바에 `inert`가 있고, 닫힘 시 없어짐.
   - 두 시트가 겹쳤다가 하나만 닫히면 `inert`가 유지됨.
   - 마지막 요소에서 Tab → 첫 요소, 첫 요소에서 Shift+Tab → 마지막 요소(`fireEvent.keyDown`으로 핸들러 동작 검증. jsdom은 실제 Tab 이동을 하지 않으므로 핸들러가 `preventDefault` 후 focus를 옮기는 것을 확인).
   - 포커스 가능 요소가 없으면 dialog에 focus 유지.
5. usage에 "Sheet가 열린 동안 배경은 inert, 화면 task가 배경 요소에 inert를 직접 걸지 말 것"을 적습니다.

**근거**

**수정 지침**
1. 라우터 계약 테스트(경로 → 화면 키, 리다이렉트, screen_view 횟수, 앱 틀 wide·탭바)는 실제 화면과 분리합니다. `AppRoutes.test.tsx`에서 `vi.mock('./screens', …)`로 13개 키 모두를 테스트용 화면(`<section data-testid={"screen-"+key} />`)으로 바꿉니다. 그러면 화면 task가 무엇을 하든 이 테스트는 영향을 받지 않습니다.
2. 실제 화면 연결은 영향이 적은 존재 검사만 남깁니다. 별도 `screens.test.ts`에서 `SCREENS`의 13개 키가 `SCREEN_KEYS`와 같은지, 각 화면 모듈의 `default`가 함수인지(`await import('../screens/Home')` 등) 확인합니다. 렌더링이나 내용 검사는 하지 않습니다.
3. `toBeEmptyDOMElement()` 단정은 삭제합니다. "빈 화면으로 열림"은 T2.0 R2 수정 보고서에 "T2.0 종료 시점 13개 placeholder가 빈 section임"이라는 검증 기록으로 남깁니다(현재 placeholder 소스로 확인 가능).
4. usage 보강: "`router/*.test.*`와 `App.test.tsx`는 T2.0 소유. 화면 task는 자기 `screens/<이름>/` 안의 테스트만 추가하고 라우터 테스트를 고치지 않는다. 화면 루트의 `data-testid="screen-<key>"`는 E2E가 쓰므로 유지(권장 → 필수)."
5. `App.test.tsx`도 같은 문제(실제 화면 내용에 의존)가 있으면 같은 방식으로 고칩니다.

## L01 — 타당, L 유지

**근거:** `Sheet.tsx:11`에서 `title?`가 선택 사항입니다. 제목이 없으면 `:57`의 `aria-labelledby`가 빠지고, 다른 이름 수단도 없어 이름 없는 dialog가 됩니다. 이때 `:62`에는 빈 `<h2>`가 남습니다. 지금 모든 사용처와 테스트가 title을 넘기므로 현재 장애는 아닙니다.

**수정 지침**
1. props를 판별 유니온으로 바꿉니다. `({ title: ReactNode; label?: undefined } | { title?: undefined; label: string }) & { open; onClose; children? }`. 제목 없는 형태는 번역된 `label`(→ `aria-label`)이 필수입니다.
2. title이 없으면 `<h2>`를 렌더하지 않습니다.
3. 테스트: title 형태는 `getByRole('dialog', { name: <title> })`, label 형태는 `getByRole('dialog', { name: <label> })`. `<Sheet open onClose={…} />`처럼 이름이 없는 호출이 타입 오류인지는 `// @ts-expect-error`로 확인합니다.
4. usage: "Sheet는 `title` 또는 `label`(t()로 번역) 중 하나 필수".

## L02 — 타당, L 유지

**근거:** `navState.ts:15`는 `src === 'phrase' && phraseId`가 거짓이면 `{ src: 'order' }`를 돌려줍니다. 그래서 빈 문장 ID가 **현재 주문**으로 바뀝니다. 직원 화면(T2.5)은 src로 "주문입니다/요청입니다" 안내와 주문 목록 노출을 정하므로(F-10), 문장 하나를 보여 주려던 화면에 장바구니 내용이 뜰 수 있습니다. 반면 같은 입력을 직접 `parsePhraseInput`에 넘기면 null(`:23`)이 되어 두 경로가 서로 다르게 동작합니다. 정상 데이터 ID를 넘기는 경로에서는 생기지 않으므로 L입니다.

**수정 지침**
1. 타입을 판별 유니온으로 바꿉니다: `export type PhraseInputState = { src: 'order' } | { src: 'phrase'; phraseId: string };`
2. `phraseInput`은 src를 바꾸지 않습니다. `phraseInput('order') → { src:'order' }`, `phraseInput('phrase', id) → { src:'phrase', phraseId: id }`(값 그대로). 검증은 받는 쪽 한 곳에서만 합니다.
3. `parsePhraseInput`의 phrase 조건을 `isValidId(phraseId)`(`domain/events.ts`, 이용 기록과 같은 ID 형식)로 강화합니다. 빈 문자열과 형식이 틀린 값은 모두 null입니다.
4. 테스트: `parsePhraseInput(phraseInput('phrase', ''))` → null, `phraseInput('phrase','')`의 src가 `'phrase'`로 유지됨, `'SSD-1'`이나 한글 문장 → null, `'ssd-1'` → 그대로.
5. usage: "null이면 받는 화면이 처리(직접 진입·새로고침·잘못된 ID). 실제 문장이 데이터에 있는지는 받는 화면이 `downtown.json`에서 찾아 확인하고, 없으면 같은 null 처리로. 새로고침해도 history state가 남을 수 있으니 'state 없음 = 새로고침'으로 가정하지 말 것".
