## 항목별 검토

### H-01 — 배포 URL E2E와 main 병합 게이트가 순환한다

- **위치:** task 0.3(36행), T0.3/Phase 0 E2E(65~69행), T3.3/Phase 3 E2E(190~194행).
- **문제:** 규칙은 phase E2E 통과 후에만 main에 병합·push하게 하지만, T0.3 완료 및 Phase 0 E2E는 main 배포가 먼저 있어야 가능하다. Phase 3도 아직 main에 없는 PWA 변경을 배포 URL에서 검증해야 main으로 올릴 수 있다. 기존 배포를 대상으로 통과시키면 새 변경을 검증하지 않은 채 출시하게 된다.
- **근거:** PRD 8장 배포와 9.2의 phase E2E는 함께 충족해야 한다. 현재 순서로는 최초 배포에 예외가 필요하고, 후속 phase는 테스트한 코드와 출시 코드가 달라질 수 있다.
- **권장 수정안:** 후보 커밋을 고정하고 `/detour/` base의 production build preview에서 phase E2E → 같은 커밋 main 병합·배포 → 배포 URL smoke 검증 순서를 명시한다. 실제 Pages 환경에서만 가능한 검증은 배포 후 단계로 분리하고 실패 시 출시 완료를 취소한다. T0.3 초기 배포도 이 순서로 정의한다.

### H-02 — Phase 4 수정본의 재배포·E2E가 없어 실기기 점검이 이전 버전을 검증할 수 있다

- **위치:** Phase 4 전체(198~206행), 0.3(36행).
- **문제:** T4.1은 JSON을 갱신하지만 T4.2 검수 결과의 수정 담당·대상·검토 완료 조건이 없다. Phase 4 E2E 및 최종 배포 task도 없다. 공통 규칙대로라면 Phase 4 전체 완료 전 main 반영이 없으므로 T4.3·T4.5는 Phase 3의 미검증 콘텐츠로 수행될 수 있다. 반면 이를 기다리면 최종 배포 완료를 선언할 명시적 검증이 없다.
- **근거:** PRD 9.1은 현장 검증 반영 → 배포 → 실기기 QR 점검 → 리허설 순서다. 11장은 주소·좌표 확정 후 도보 시간·총거리 재검증도 요구하지만 T4.1에는 이 후속 작업이 빠져 있다.
- **권장 수정안:** 현장·번역 결과 수령 → 담당자가 데이터/사전/수사 테스트 수정 및 검토 → 도보 시간·총거리 재검증 → 최종 후보 phase E2E → 배포 → 동일 배포 버전 실기기·리허설 순서로 재편한다. 최종 커밋/배포 ID와 점검 결과를 기록하고, 연락처 확정 후 앱에 표시하는 담당도 배정한다.

### M-01 — 병렬 묶음 A의 공유 계약이 PRD 데이터 타입만으로는 부족하다

- **위치:** T0.2(63행), T1.2~T1.6(84~130행), 0.2(28~31행).
- **문제:** T1.2의 `useT()`는 언어 상태 접근이 필요하고 T1.6이 이를 동시에 만든다. T1.4는 T1.3의 수사 규칙을 사용하지만 공유 함수 시그니처·정규화 계약이 없다. T0.2에서 확정하는 PRD 8.1 타입에는 store 액션, 음성 결과, 채점 결과, 생성 문장 전달 계약이 없다. 서로 다른 worker가 각자 정의하면 중복 구현 또는 통합 시 타입 변경이 필요하다.
- **근거:** PRD 9.2는 서로 영향이 없는 task의 병렬 실행이다. 폴더만 나눠도 런타임·인터페이스 의존성은 남는다. 선언된 출력 객체의 `words[]`도 구체 타입이 확정되지 않았다.
- **권장 수정안:** T0.2 뒤에 최소 공유 계약 확정 단계를 두어 언어 getter/setter, 수사 변환 함수, 결과 타입·store 액션을 고정한다. T1.2가 언어를 인자로 받고 연결을 후속 통합 task로 미루는 방식도 가능하다. 이후 각 모듈은 계약 fixture로 독립 테스트하고 실제 상호 연결 검증을 Phase 1 종료 조건에 넣는다.

### M-02 — 병렬 묶음 C는 수정 범위와 측정 대상이 동시에 바뀐다

- **위치:** T3.1~T3.3(182~192행), 0.2(30~31행).
- **문제:** T3.2 소유 파일은 사실상 정해지지 않았고 화면 담당과 조율하라고만 되어 있다. 번들 최적화는 T3.1이 수정하는 Vite 설정·의존성·로딩 구조와 겹칠 수 있다. T3.1은 동시에 설정 화면·업데이트 토스트를 요구하지만 이 파일은 소유하지 않는다. PWA 변경 전 T3.2 결과로 완료 체크하거나 T3.3이 먼저 배포 점검하면 최종 빌드의 증거가 아니다.
- **근거:** 파일 비중복 규칙과 같은 묶음 동시 실행 규칙을 현재 소유권으로 보장할 수 없다. 성능 측정은 출시할 빌드가 확정된 뒤 유효하다.
- **권장 수정안:** PWA 구현·UI 연결 → 빌드 고정 → 성능/접근성 측정·수정 → 최종 배포 점검 순서를 설정한다. QR 이미지 생성처럼 독립 작업만 병렬화한다. `vite.config.ts`, 패키지/lock 파일, SW 등록 파일, Settings·Toast 연동 파일, 아이콘과 QR SVG의 정확한 담당 경로를 지정한다.

### M-03 — 공용 통합·테스트 파일과 체크박스 갱신의 담당이 빠져 있다

- **위치:** 0.1~0.2(12~31행), T1.3/T1.4(88·108행), T2.0~T2.6(141~168행), phase E2E 정의.
- **문제:** T1.3/T1.4는 소스 파일만 소유해 요구된 단위 테스트 파일을 새로 만들 권한이 없다. T2.0은 빈 라우트까지만 만들고 종료하므로 실제 화면 import/라우터 연결 책임이 남는다. 일반 문장/주문을 연습·직원 화면에 전달하는 상태와 `screen_view`·`place_view` 등의 발생 위치도 배정되지 않았다. 제보 시트를 여러 화면에서 여는 연결, Playwright 테스트 파일, 각 worker의 task.md 체크·검토 문서 작성도 소유 목록 밖이다.
- **근거:** 0.2는 소유 파일 밖을 읽기 전용으로 정한다. coordinator 요청 경로는 있지만 이 모든 통합을 누가 언제 완료해야 하는지는 task 완료 조건에 없다.
- **권장 수정안:** 각 task에 colocated `*.test.ts(x)` 및 자기 검토 파일을 허용하고, task.md 변경·커밋은 coordinator 한 명에게 맡긴다. T2.0에서 화면 export·라우트 전달·일시적 연습 상태 계약을 미리 고정하거나 별도 통합 task를 둔다. 공통 제보 시트·이벤트 연결과 E2E 작성/실행 담당 및 경로를 배정한다.

### M-05 — 다국어 검사 규칙이 PRD 예외와 충돌하고 목업의 잘못된 고지를 복사할 수 있다

- **문제:** '하드코딩 문구 없음'/'모든 화면 문구 전환'은 PRD에서 고정한 한국어 학습 문장과 직원 안내·응답 버튼까지 실패시킬 수 있다. 반대로 사전 키 집합이 같다는 검사만으로 번역 누락을 검증할 수 없다. 목업에는 음성·기록이 기기에 저장된다는 취지의 개인정보 문구가 있으며, T1.2의 '목업 UI 문구 전체 + PRD 고지'를 그대로 구현하면 저장하지 않는다는 PRD 고지와 공존한다.

- **권장 수정안:** PRD와 목업 충돌 시 PRD 우선, 목업의 오래된 고지 교체를 명시한다. 검사에서 고정 한국어·상호·콘텐츠와 번역 대상 UI를 구분하고, 빈 번역/누락 키/원문 fallback을 검사한다. 3개 언어 전환 테스트는 고정 문구가 유지되는 것까지 확인한다.

### M-06 — 여러 task의 완료 기준이 없거나 기대값이 충분히 고정되지 않았다

- **위치:** T1.4(109~113행), T2.1~T2.6(149~168행), T4.1~T4.6(200~206행), T3.3(191~192행).
- **문제:** 화면 task에는 동작 목록만 있고 각각의 완료 조건이 없다. T1.4는 한 글자 틀림·숫자 차이 '테스트 통과'라고만 해 점수 분모·반올림·문맥별 수사 변환 기대값을 구현자가 임의로 선택할 수 있다. '2개'는 '두 개', '2인분'은 '이 인분'이어야 하며 일반 문장 '두 명이에요'도 사용한다. 사용자 task에는 증빙·수정 반영·확인 완료의 구분이 없다. QR 스캔만으로는 F-17의 시연 자료 삽입을 검증하지 않는다.
- **근거:** 0절은 모든 완료 조건 충족과 검토 미해결 0건을 체크 기준으로 삼는다. 자기 구현에 맞춘 테스트 또는 요청을 전달한 상태만으로는 이 체크의 의미가 일정하지 않다.
- **권장 수정안:** task별로 입력/행동/기대 결과와 증거 파일을 짧게 정의한다. 채점은 거리 정규화 공식·0~100 범위·반올림·단위별 수사·빈 결과·동점 약한 단어 처리를 고정한다. 사용자 task는 결과 수령, 앱 반영, 재검토 상태를 구분한다. QR은 실제 시연 자료 삽입·최종 URL 확인을 추가한다. T4.5는 '안내 없이 180초 이내'와 진행자 음성/심사위원 텍스트 경로를 합격 조건으로 둔다.

### M-07 — T1.3 수사 표는 로마자 연음 기준이 일관되지 않고 공기 검증이 빠져 있다

- **위치:** T1.3(90~107행).
- **문제:** 고유어 수사 한~아홉, 인분의 일~구 선택과 한국어 표기는 타당하다. 다만 연속해서 읽는 인분의 발음 안내에서 `il-inbun`, `yuk-inbun`, `chil-inbun`, `pal-inbun`은 연결 발음을 반영하는 기준과 맞지 않는다. 가타카나는 6·7·8을 `ユギンブン/チリンブン/パリンブン`으로 연결하면서 1은 `イルインブン`으로 분리해 일관되지 않다. 공기는 개와 같은 수사를 쓰지만 별도 9개 기대값 없이 18칸만 테스트한다.
- **근거:** PRD F-01은 개정 로마자 기반의 **발음 안내**다. 국립국어원 규정은 발음상 모음 앞의 ㄱ을 g, ㄹ을 r로 적도록 한다. 연결 발음 기준이면 1·6·7·8인분의 예시는 `irinbun`, `yuginbun`, `chirinbun`, `parinbun`이 된다. `il`·`yuk` 등 독립 수사 학습용 분절 표기를 의도했다면 그 정책을 별도로 명시해야 한다. [국립국어원 로마자 표기법 제2장](https://www.korean.go.kr/front/page/pageView.do?page_id=P000149&mn_id=99)
- **권장 수정안:** 독립 수사 열과 완성 구절 발음 열을 구분하고 실제 표시·TTS·테스트에는 완성 구절 기준을 사용한다. 1인분 가타카나는 연결 발음 근사안 `イリンブン`을 포함해 검수한다. 받침 뒤 개/공기의 된소리 및 가타카나의 모음 삽입 정도는 한국어 발음 검토와 일본어 사용자 검수로 확정하고, 근사 표기의 차이를 모두 오자로 판정하지 않는다. 개·인분·공기 총 27개 조합, 수량 경계, 여러 메뉴, 포장/매장, 3개 언어 뜻·단어 칩을 검증한다.
- **오탐 방지:** `여덟 / yeodeol / ヨドル`에서 b가 빠진 것은 오류가 아니다. 국립국어원은 여덟의 발음을 [여덜]로 안내한다. [국립국어원 상담 사례](https://www.korean.go.kr/front/mcfaq/mcfaqView.do?mcfaq_seq=6527&mn_id=62) 가타카나는 PRD가 허용한 근사 표기이므로 `ゲ/ケ` 같은 선택만으로 별도 결함을 세지 않았다.

### M-08 — phase E2E가 성공 기준의 음성 불가 완주·오프라인 준비·실제 음성을 충분히 입증하지 못한다

- **위치:** Phase 2 E2E(170~176행), Phase 3 E2E(194행), T4.3/T4.5(203~205행).
- **문제:** 실패 경로는 버튼 노출까지만 검사하고 그 버튼으로 주문·직원 응답까지 완주하는지는 보지 않는다. 성공 경로도 STT 목이므로 진행자 기기의 실제 듣기·말하기·채점 성공 증거가 아니다. 오프라인 시나리오는 최초 방문 뒤 곧바로 차단해도 되는지 준비 완료를 기다려야 하는지 불명확하다. SW가 제어하는 재방문/새로고침, 타일 실패 약도, 미방문 화면, 새 배포 캐시 갱신의 관찰 기준이 없다.
- **근거:** PRD 1.3의 여섯 성공 기준 중 로드 시간은 T3.2, 언어는 Phase 2에 대응하지만, 텍스트 완주·실제 음성·오프라인은 현재 시나리오만으로 판정할 수 없다. 리허설의 시간 측정은 자동 E2E와 별개로 필요하다.
- **권장 수정안:** API 없음/권한 거부 상태에서 음성을 거치지 않고 직원 응답까지 도달하는 E2E를 추가한다. 오프라인 준비 완료 확인 → 네트워크 차단 → 새로고침 → 미방문 코스/메뉴/문장 및 약도 확인을 넣고 캐시 갱신도 검증한다. 실제 진행자 음성 전 과정과 안내 없는 3분 완주는 Phase 4 수동 인수 증거로 명시해 자동 목 테스트와 구분한다.

### M-09 — 360~430px와 지원 브라우저 범위의 검증이 축소되어 있다

- **위치:** T2.0(145~146행), 0.1/Phase 2 E2E(26·170행), T3.2(188행), T4.3(203행).
- **문제:** 자동 검증은 390×844 하나, 실기기는 안드로이드 크롬·iOS 사파리라는 이름만 있다. PRD 7장의 360~430px, iOS 사파리 최신 2개 버전, 데스크톱 크롬·엣지 범위와 리포트 데스크톱 폭을 검증할 task가 없다. 공용 빈 화면의 대비/터치 검증만으로 실제 화면·색상·작은 아이콘까지 충족했다고 볼 수도 없다.
- **근거:** PRD 7장은 화면 범위와 브라우저를 명시한다. Lighthouse 90점은 모든 버튼 44px·모든 관련 텍스트 대비 4.5:1 조건과 동일하지 않다.
- **권장 수정안:** T3.2/T4.3에 360/390/430px 및 데스크톱 리포트, 지정 브라우저/실제 버전 매트릭스를 두고 결과를 기록한다. 가로 넘침·고정 바 겹침·터치 영역·대비는 완성 화면 기준으로 확인한다. 사용 가능한 실기기 버전이 부족하면 검증 미실시 항목을 명확히 남기고 사용자와 범위를 확정한다.

### M-10 — 허용 목록과 task별 push를 검증하는 안전 기준이 충분하지 않다

- **위치:** 0.3(34~36행), T0.1 완료 조건(45행), 0.2 병렬 규칙.
- **문제:** `git status`에 개인 자료가 보이지 않는다는 것은 원격으로 보낼 파일 목록이 안전하다는 뜻이 아니다. 이미 추적되어 깨끗한 파일은 status에 나오지 않으며, `app/`·`reviews/` 전체 허용은 그 안의 `.env`·산출물·개인 정보가 섞인 검토 자료까지 허용할 수 있다. 공유 dev에서 여러 worker가 task별 커밋·push하면 다른 작업의 staged 변경이나 아직 검토가 끝나지 않은 커밋이 함께 올라갈 수 있다.
- **근거:** 아직 이 폴더는 Git 저장소가 아니므로 현재 유출을 주장하는 지적은 아니다. T0.1에서 처음 만들 규칙과 6개 동시 작업의 향후 위험을 검토한 것이다. `.gitignore`는 추적된 파일을 자동 제거하지 않으며 push는 특정 task 파일이 아니라 커밋 이력을 전송한다.
- **권장 수정안:** 재귀 허용 패턴과 `node_modules`, `dist`, 테스트 산출물, 환경 파일 제외를 함께 설계한다. 최초 push 전 `git ls-files`와 staged diff의 전체 경로·내용을 확인하고, 승인된 소스·문서만 들어간 것을 증거로 남긴다. 공유 checkout에서는 coordinator 한 명이 task 소유 파일만 명시해 stage/commit/push하도록 정하고, 다른 task 변경이 포함되지 않았는지 확인한다. task.md 체크와 검토 결과도 같은 완료 단위로 기록한다.

## 최종 판정

계획 수정 후 재검토가 필요하다. 우선 배포 순환(H-01)과 최종 콘텐츠 반영·출시 순서(H-02)를 해소하고, 병렬 계약·소유권(M-01~03), 누락 동작과 검증 기준(M-04~10)을 해당 task에 반영하는 것이 적절하다. Phase 1의 화면 없는 단위 테스트 대체와 기존 검토 루프 자체는 별도 결함으로 계산하지 않았다.
