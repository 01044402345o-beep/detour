## H-01 — 전체 버튼 검사에서 7개 라우트와 상호작용 상태 누락

- 위치: `reviews/T3.2_measure.mjs:197` SCREENS, `:233` auditScreens, `reviews/T3.2_contrast.mjs:47`, `reviews/T3.2_metrics.md:4,103,123`.
- 문제: 6개 화면의 초기 상태만 검사하고 “모든 버튼 44px”, “5개 모두 통과”로 결론 낸다. 접근성·대비 검사도 동일한 범위 제한을 받는다.
- 근거: 앱 `app/src/router/routes.ts`에는 13개 라우트가 있으나 practice/result/reply/phrases/saved/settings/report가 검사 목록에 없다. 장소도 성심당 1개만 연다. `ReportSheet`, `SwitchPlaceSheet`, 설정 초기화 시트를 여는 동작이 없으며 `app/src/ui/Sheet.tsx`는 닫힌 상태에서 null을 반환하므로 내부 버튼을 검사할 수 없다. 코스는 타일 오류/오프라인을 강제하거나 `.cmap[data-mode]`를 기록하지 않아 SVG 약도 검사 여부를 증명하지 못한다. 제공 원자료는 OSM 링크가 있는 타일 지도를 검사한 결과다. 따라서 숨은 시트를 제외한 것 자체가 아니라, 열어서 검사하는 별도 상태가 없다는 것이 문제다.
- 권장 수정안: 모든 라우트와 조건부 버튼이 나타나는 상태를 목록화하고 언어별 검사에 포함한다. 주문 유무, 다른 장소로 주문 전환, 제보·초기화 시트, 직원 응답, 음성 지원/미지원 상태, 타일 지도 및 강제 약도를 명시적으로 준비하고 상태 assertion을 넣는다. 각 상태의 검사 요소 목록과 크기를 저장한다. 누락 상태가 남으면 결론을 “측정한 상태에서 위반 0”으로 제한하고 완료 체크를 보류한다.

## M-01 — DOM 삽입 시각을 화면 표시 완료 시각으로 사용

- 위치: `reviews/T3.2_measure.mjs:64–77,160–185`, `reviews/T3.2_metrics.md:25,40–54`.
- 문제: MutationObserver에서 루트 요소 높이가 양수이면 첫 화면으로 기록한다. 이는 실제 paint나 첫 화면 주요 콘텐츠 표시를 확인하지 않는다. opacity/visibility, 이미지·폰트 및 후속 콘텐츠 준비도 확인하지 않는다.
- 근거: 첫 방문 원자료의 firstScreenMs는 874/872/881ms인데 FCP는 892/896/896ms다. 즉 “첫 화면 표시” 기록이 첫 픽셀이 그려지는 시점보다 이르다. LCP도 500ms 대기 뒤의 관측값일 뿐 후속 갱신 종료를 확인하지 않는다. 지금 데이터의 FCP/LCP 역시 3초 미만이므로 실제 성능 실패를 주장하는 지적은 아니다.
- 권장 수정안: 현재 값은 DOM-ready 보조 지표로 이름을 바꾼다. 화면 표시 판정에 필요한 요소·자산과 paint 기준을 먼저 정의하고, 그 조건 이후 렌더 프레임 및 FCP/LCP/필름스트립으로 확인한다. 최종 관측 시점도 기록한다. 같은 캐시 없음·Fast 4G 조건에서 3회 원자료와 중앙값을 갱신한다.

## M-02 — incomplete 대비 재계산 결과와 최종 통과 판정의 연결 부족

- 위치: `reviews/T3.2_contrast.mjs:58–145`, `reviews/T3.2_contrast.json` contrast[*].nodes, `reviews/T3.2_metrics.md:84–100`.
- 문제: 요소 전체 사각형의 픽셀 5백분위를 통과 기준으로 쓰면 실제 글자 뒤 배경의 최소 대비를 보장하지 못한다. 반대로 테두리·다른 요소 픽셀은 거짓 미달을 만든다. 글자를 없애는 전역 CSS는 currentColor를 쓰는 배경·테두리·SVG도 바꿀 수 있다. 추출한 opacity는 계산에 사용하지 않으며 조상 opacity도 합성하지 않는다. 이 계산은 보조 탐색으로는 유용하지만 최종 대비 판정 근거로 충분하지 않다.
- 근거: JSON에는 총 494개 노드, `okP5:false` 61개가 남는다. 예를 들어 선택 언어 배지 p5=1, 홈 번호 p5=1, 지도 번호 p5=1, 영어 menu-bm 한국어 이름 p5=3.32다. 문서는 CSS 토큰 표로 이를 통과 처리하지만 노드별 실제 배경·겹침·합성·제외 사유와 최종 판정 매핑을 보존하지 않는다. 일부 잡음 설명은 타당할 수 있으나 494개 전체가 해결되었다는 재현 가능한 증거가 없다. 또한 스크립트는 큰 글자 3:1을 허용하지만 PRD 7장의 명시 기준은 대비 4.5:1이다. 별도 합의 없이 완화하면 안 된다.
- 권장 수정안: 원본 incomplete를 유지하고 각 selector에 최종 판정·실제 전경/배경·합성 후 대비·증거를 연결한다. 단색 배경은 실제 computed style과 조상 합성을 계산하고, 그라데이션·지도·겹침은 글자가 놓인 영역의 최악 배경으로 판정한다. 가려진 노드는 가림을 해소한 상태에서 재검사한다. 로고 예외와 비활성 요소 등 제외는 명시적으로 분류하고, 해결하지 못한 항목은 통과 대신 미확인으로 남긴다. PRD의 4.5 기준 또는 승인된 예외를 사용한다.

## M-03 — 고정 빌드를 식별할 수 있는 내용 증거 없음

- 위치: `reviews/T3.2_metrics.md:9–18`, `reviews/T3.2_measure.mjs:34,109–112,338–358`, `reviews/T3.2_results.json` 최상위 메타데이터.
- 문제: HEAD와 변경 파일명 목록은 있으나 미커밋 내용과 생성된 빌드를 고정하는 해시가 없다. 스크립트는 실행 시 공유 dist를 재빌드하고, 두 스크립트가 같은 빌드를 검사했는지도 확인하지 않는다. Lighthouse 전체 보고서도 공용 임시 경로 `t32-lh`에 덮어쓴다.
- 근거: 검토 시 HEAD는 문서와 동일한 cfc80974a08f2d812cefa8d1129840f5a20f4edb였다. 재빌드는 성공했으나 프리캐시 크기는 문서의 760.75 KiB와 다른 761.28 KiB였다. 첫 화면 JS의 파일명·gzip은 재현되므로 이 차이가 JS 성능 실패라는 뜻은 아니다. 이후 공유 작업 트리에 playwright.config.ts와 p3-offline.spec.ts 변경이 추가되고 dist/sw.js 읽기가 ENOENT가 되어 동시 작업 중 산출물 안정성도 확인할 수 없었다. 이 현상은 원 측정이 잘못됐다는 증거가 아니라 고정 식별자가 필요한 이유다.
- 권장 수정안: 빌드 입력(미커밋 diff와 새 소스 파일 포함) 및 dist 전체 파일 SHA-256 manifest, 도구 버전, 실행 설정을 측정 원자료에 남긴다. 동일한 고정 dist를 두 측정에 사용하고 시작/종료 해시 일치를 검증한다. Lighthouse 원본은 실행별 보존 경로로 출력하고 결과와 연결한다.

## L-01 — 숨김 판정이 작은 실제 버튼도 통과시킬 수 있음

- 위치: `reviews/T3.2_measure.mjs:205–225` touchCheck.
- 문제: 1×1 이하인 요소를 CSS 확인 없이 sr-only로 간주하여 무조건 통과시킨다. aria-hidden 조상도 시각적 숨김으로 간주하여 제외하지만 aria-hidden만으로는 화면이나 포인터에서 숨겨지지 않는다.
- 근거: `ok: hiddenClip || (...)`는 실제 1×1 버튼도 통과시킨다. `closest('[aria-hidden="true"], [inert]')`는 화면에 보이는 aria-hidden 버튼도 검사에서 뺀다. 현재 원자료에서 이 경로로 놓친 실제 요소를 확인한 것은 아니므로 Low다.
- 권장 수정안: 시각적으로 숨긴 네이티브 input만 대응 label의 실제 클릭 영역으로 대체하고 일반 버튼은 크기를 그대로 판정한다. aria-hidden과 시각적 숨김을 구분하며 제외한 요소와 사유도 원자료에 남긴다.

## 확인한 정상 사항 및 재현 범위

- `cd app; npm run build` 성공(tsc + Vite 8.3.8 + PWA). 소스나 측정 원자료를 수정하지 않았으며 이 보고서만 작성했다. 빌드 산출물 생성은 요청된 재현 절차에 따른 것이다.
- 빌드 직후 기존 JSON의 첫 화면 청크를 직접 읽어 gzip level 9로 재계산했다. 첫 방문 105,475 B, 홈 114,268 B가 정확히 재현되었다. index, 공통 ui, 해당 화면, PWA 등록/workbox 청크가 포함되고 홈에는 data 청크가 더해진다. 원자료의 virtual_pwa-register는 604 B이며 문서의 605 B는 사소한 오기다. 합계 자체는 맞다.
- 청크 수집은 “첫 화면까지”가 아니라 화면 대기 후 추가 1.5초까지다. SW는 차단하여 sw.js와 프리캐시 전송은 제외된다. 이를 페이지 진입 JS 예산으로 정의하면 현재 합계는 타당하지만, 실제 첫 접속 전체 네트워크 비용으로 표현하면 안 된다. 외부 script가 dist에 없을 때 null을 0으로 더하는 처리도 추후에는 미확인으로 표시해야 한다. 현재 수집 목록에는 null이 없다.
- 네트워크 설정은 latency 165ms / download 1,012,500 B/s / upload 168,750 B/s이고, CDP 캐시 비활성 및 SW 우회 호출이 내비게이션 전에 있다. 성능은 각 시나리오 새 컨텍스트 3개를 사용한다. 재방문은 언어 저장을 먼저 수행한 뒤 캐시를 비활성화한 홈 진입이다. 원자료의 중앙값 874ms·867ms는 산술적으로 맞고 3개 표본 모두 3초 미만이다. 도구 실행 환경의 네트워크·CPU 조건을 기기 전반의 보장으로 확대해서는 안 된다.
- 원자료에서 18개 axe 실행의 violations 0, touchFails 0, 영어 6개 화면 Lighthouse 접근성 100은 문서와 일치한다. Lighthouse는 화면당 1회이며 3회 중앙값은 성능에만 적용한 것으로 문서에 구분되어 있다. 위반 0은 incomplete 해결 및 전체 상태 검사와 별개다.
- 전체 브라우저 스크립트 재실행은 하지 않았다. 문서에 임시 도구 폴더의 실제 경로가 없고 app 기준 `@axe-core/playwright`, `lighthouse`가 모두 MODULE_NOT_FOUND였으며, 공유 dist의 동시 변경도 확인했다. 따라서 브라우저 수치는 제공 JSON의 검산 및 코드 검토 결과로만 보고하며 독립 재현을 주장하지 않는다.
