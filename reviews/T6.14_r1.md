## M-01 — 발화 오류 뒤 남은 큐가 살아 있어 표시와 실제 소리가 어긋난다

**위치:** `app/src/speech/guideTts.ts:110`, `:183`~`:199`.

모든 문장을 미리 `speak()`에 넣지만 중간 발화의 오류는 `finish(run, 'error')`로만 처리한다. `finish()`는 모든 발화의 콜백을 제거하고 current를 비우며 큐는 취소하지 않는다. 따라서 첫 문장 실패 뒤 나머지를 계속 처리하는 엔진에서는 화면은 재생이 끝난 것으로 바뀌지만 뒤 문장이 계속 소리 나고 강조·종료 통지도 사라진다. `canceled`를 외부 취소로 간주하는 분기 역시 실제 엔진 오류와 구분되지 않을 수 있다.

**확인:** 원본 TS를 메모리에서 변환해 A/B/C 큐에 첫 문장 `synthesis-failed`를 전달했다. 결과는 `ended:["error"]`, 잔여 큐 `["B.","C."]`, 잔여 콜백 전부 null이었다(파일 생성 없음). 실제 WebKit 소스도 `handleSpeakingCompleted()`에서 오류 이벤트 뒤 다음 큐 항목을 시작하는 구조다. [WebKit 구현](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/speech/SpeechSynthesis.cpp)

**수정:** 자기 run의 오류 종료 시 남은 자기 큐를 정리하고, 취소 이벤트의 재진입·늦은 이벤트가 새 요청을 취소하지 않게 요청 소유권을 확인한다. 여러 문장을 큐에 넣고 중간 실패를 내는 테스트에서 큐·콜백·UI 정지를 함께 검증한다. 현재 오류 테스트는 한 문장뿐이어서 이를 놓친다.

## M-02 — 목록에 음성이 있어도 실제 합성 실패는 아무 안내 없이 끝난다

**위치:** `app/src/ui/GuidePlayer.tsx:75`~`:88`, `:120`; `app/src/speech/guideTts.ts:31`~`:46`.

`onEnd('error')`가 정상 완료와 동일하게 재생 표시와 현재 문장만 지운다. 안내는 `no-voice`/`unsupported`에만 있어서 음성이 목록에 있지만 `network`, `voice-unavailable`, `synthesis-failed` 등으로 실패하면 사용자는 무음인 이유나 다음 행동을 알 수 없다. 특히 선택 순위는 localService를 사용하지 않고 Google/Online/Natural 이름을 우대한다. 로컬 일본어 음성과 원격 Google 일본어 음성이 함께 있을 때 원격 음성이 선택되는 것을 직접 확인했다. 연결 실패 시 사용 가능한 로컬 음성을 활용하거나 실패를 설명할 경로가 없다.

음성 목록 존재와 발화 성공은 다르며 네트워크·음성 사용 불가 오류는 API에 정의되어 있다. [MDN 오류 종류](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesisErrorEvent/error)

**수정:** 실패 상태와 번역된 재시도/원고 읽기 안내를 표시한다. 원격 음성 실패 시 로컬 음성을 선택해 사용자가 다시 시도할 수 있도록 하거나 상황에 맞는 로컬 우선 정책을 둔다. 무조건 자동 재시도해서 사용자 활성화를 잃지 않도록 한다. 목 엔진의 error 종료에 대한 UI 테스트가 필요하다. 오프라인 음성 전면 보장을 요구하는 지적이 아니라, 실제 실패를 정상 종료로 숨기는 문제다.

## M-03 — 늦게 생기거나 사라진 음성에 맞춰 안내가 갱신되지 않는다

**위치:** `app/src/ui/GuidePlayer.tsx:55`~`:66`, `:75`~`:88`; `app/src/speech/guideTts.ts:129`~`:146`.

GuidePlayer는 마운트/언어 변경 때 한 번만 init 결과를 저장한다. init은 2초 뒤 voiceschanged 구독을 제거한다. 이후 음성이 로드되거나 설치되어 `play()`가 실제로 해당 음성을 선택해도 화면에는 계속 “일본어/중국어 음성이 없음”이 남는다. 반대로 처음 ready였다가 음성이 사라져 lang만 지정하는 경우에는 필요한 안내가 나오지 않는다. 같은 화면에서 팝업을 닫았다 다시 열어도 상태를 재확인하지 않는다.

**재현 순서:** 일본어 음성 없는 상태로 화면 진입 → 2초 지나 no-voice → 일본어 음성 목록 추가 → 가이드 열기/재생. 엔진은 새 음성을 선택하지만 UI는 이전 no-voice다.

**수정:** 사용자 탭에서 동기 play를 유지하면서 최신 voiceState를 반영하고, 필요하면 init/voiceschanged로 이후 갱신한다. 기존 한국어 ListenButton의 재생 후 refresh 패턴도 참고할 수 있다. 2초 뒤 음성이 추가되는 경우와 음성이 제거되는 경우를 테스트한다.

## M-04 — 으능정이 안내가 미확인 운영시간을 말하면서 예시 정보 고지를 생략한다

**위치:** `app/src/data/guides.ts:213`~`:245`; `app/src/data/guides.test.ts:43`.

으능정이 원고는 EN “open all day”, JA “一日中歩けて”, ZH “全天都可以逛”로 종일 이용 가능하다고 안내한다. 원본 `downtown.json`의 eun은 `verified:false`, `hours:"00:00–24:00"`이며 데이터 전체에 운영시간은 현장 확인 전 예시라고 명시되어 있다. 그런데 세 언어 모두 예시 정보 안내가 없고 테스트는 “거리(주문·가격·시간 없음)”이라는 사실과 다른 주석으로 해당 장소를 제외한다. 팝업 동안 배경 화면의 확인 전 안내도 가려지므로 F-19의 말로도 고지한다는 조건을 충족하지 못한다.

**수정:** 해당 원고에도 운영·이용 정보가 미확인 예시라는 짧은 안내를 넣고 테스트 예외를 없앤다. 또는 종일 이용 가능이라는 미확인 단정을 제거하고 남은 현장 안내의 고지 범위를 명확히 한다.

## L-01 — 일본어 예시 정보 고지의 「例の情報」가 부자연스럽고 의미가 모호하다

**위치:** `app/src/data/guides.ts:67`, `:134`, `:164`, `:267`.

「例の情報」는 보통 “그/전에 말한 정보”로 읽혀 sample information의 뜻을 명확히 전달하지 못한다. 특히 모든 음식점에 공유되는 FOOD_NOTE에서 반복된다. “掲載しているメニューや価格は参考例で、現地ではまだ確認できていません”처럼 풀어 쓰고 기존 화면의 「現地確認前・参考情報」와 의미를 맞추는 편이 자연스럽다. 현재 원고 테스트가 `/例の情報/` 자체를 요구하므로 수정할 때 이 문자열에 묶인 검사도 바꿔야 한다.

## L-02 — 언어 변경 때 중단 문장 번호가 남아 새 언어 중간부터 이어진다

**위치:** `app/src/ui/GuidePlayer.tsx:68`~`:80`, `:104`~`:107`.

언어 변경 cleanup은 stop만 호출하며 stopped 콜백은 cur를 보존한다. 팝업을 유지한 채 언어가 바뀌면 새 언어 글에서 “이어 듣기”를 눌러 이전 언어의 문장 번호부터 시작한다. 언어별 배열 길이도 같다는 계약이 없어 의미가 다른 대목을 건너뛸 수 있다. 파일 주석의 “언어가 바뀌면 … 처음부터”와 다르다. 현재 일반 사용자 언어 변경은 Settings 이동으로 언마운트되므로 우선순위는 L이다.

**수정:** 언어 전환 시 cur를 초기화하고 새 언어 첫 문장부터 재생되는지 테스트한다. 현재 테스트는 stop 호출 여부만 본다.

## L-03 — 대표 메뉴 데이터가 인기 순위·방문 동기로 확대되어 있다

**위치:** `app/src/data/guides.ts:33`, `:88`, `:343`, `:357`.

성심당 “Most visitors come for …”/“大多数人是冲着…来的”, 수연분식 “一番人気”/“最受欢迎”는 대표 메뉴라는 앱 데이터보다 강한 주장이다. `signature:true`는 방문객 대다수의 동기나 판매/인기 1위를 입증하지 않는다. 원고의 사실 기반 원칙에 맞게 “대표 메뉴/名物/招牌” 정도로 표현하면 추가 자료 없이 자연스러운 가이드 말투를 유지할 수 있다. 이 지적은 음식 설명 자체가 틀렸다는 뜻은 아니다.

## 브라우저 실동작 한계와 후속 확인

사용자 클릭 안에서 await 없이 문장들을 큐에 넣는 점, stop/new play의 이전 run 종료를 1회로 제한하는 점, 늦은 취소 콜백을 제거하는 점은 타당하다. 다만 목 테스트는 실제 Chrome/Safari/Android의 오디오 엔진을 구동하지 않는다. `cancel(); resume(); speak()` 순서만으로 모든 OS/브라우저의 취소 직후 재생 성공을 보증할 수 없다. 이 순서 자체를 근거 없이 확정 버그로 올리지는 않았다.

한국어 tts.ts와 가이드는 같은 전역 speechSynthesis를 사용하지만 각자 current를 가진다. 서로 선점한 경우 상태 정리는 브라우저의 interrupted/canceled 이벤트에 의존한다. 현재 테스트는 직접 synth.cancel을 호출할 뿐 두 실제 어댑터의 양방향 선점·실기기 이벤트 차이를 검증하지 않는다. 수정 후에는 가이드→한국어/한국어→가이드, 빠른 멈춤·이어 듣기·속도 변경, 화면 숨김/복귀를 함께 확인해야 한다.

휴대폰 JA/ZH 실제 소리 확인은 task에 명시된 사용자 확인 항목으로 남긴다. 목록 2초 이내/이후 도착, 해당 언어 음성 미설치, 원격 음성 연결 실패, Safari 및 Android Chrome에서 마지막 문장까지 재생되는 경우를 포함해야 한다. 현재 캡처의 음성 없음 안내와 작성자 보고만으로 “일본어·중국어 소리가 난다”는 조건은 실증되지 않았다.
