## M-01 — 이벤트 저장 경계가 원문·추가 필드를 제거하지 않음

- **위치:** `app/src/store/useAppStore.ts:155–163,256–257`, `app/src/domain/events.ts:28–46,158–174`.
- **문제:** `logEvent`가 입력 객체를 그대로 spread하고, 복원은 객체를 재구성하지 않는 `filter(isAppEvent)`다. 선언 타입에 transcript가 없다는 것만으로 원문 미저장이 보장되지 않는다. TypeScript도 추가 속성이 있는 변수를 함수에 넘기는 구조적 할당을 허용한다. reports 복원 역시 추가 필드를 보존한다.
- **근거:** `{type:'practice_done',src:'phrase',transcript:'PRIVATE_RECOGNITION_TEXT'}`를 기록하면 persist JSON에 해당 문자열이 남았다. 같은 객체에 `t`를 더하면 복원 검사도 통과한다. `screen`·각 ID도 임의 문자열이므로 화면 경로나 인식 문자열을 잘못 전달하면 저장된다. 이는 T1.6/F-15/7장의 인식 원문 미기록 요구를 저장 경계에서 지키지 못하는 경로다.
- **권장 수정안:** 이벤트 종류별 허용 필드만 새 객체로 구성하는 정제 함수를 기록·복원 양쪽에 적용하고 reports도 재구성한다. 화면 식별자는 고정된 화면 키 계약을 사용하고, 장소·문장 ID는 데이터 ID 계약으로 제한한다. STT 결과 객체의 추가 필드와 원문이 저장/재복원되지 않는 테스트를 추가한다.

## M-02 — 시작 시 용량 초과면 읽을 수 있는 기존 상태도 유실됨

- **위치:** `app/src/store/safeStorage.ts:25–34,44–57`.
- **문제:** 시작 시 probe 쓰기가 실패하면 local 참조를 버린다. 용량 초과는 기존 값 읽기까지 막는 오류가 아닌데도 아직 비어 있는 메모리만 읽게 된다.
- **근거:** `getItem(STORAGE_KEY)`는 기존 `lang:'ja'`·북마크 JSON을 반환하고 `setItem`만 QuotaExceededError를 던지는 저장소에서 새 store의 언어가 `null`로 복원됐다. 기존 데이터는 원본 저장소에 그대로 읽을 수 있었다. 현재 테스트는 쓰기 실패 시 예외가 없다는 점만 검증한다.
- **권장 수정안:** 읽기 가능성과 쓰기 가능성을 분리해, 쓰기 불가여도 기존 key를 읽어 메모리에 복사한 후 메모리 쓰기를 사용한다. 읽기까지 실패한 경우에만 빈 상태로 시작한다. 가득 찬 저장소에 기존 언어·북마크·주문이 있는 시작 시나리오를 추가한다.

## M-03 — 메모리 대체 후 초기화해도 다음 실행에 삭제한 기록이 되살아남

- **위치:** `app/src/store/safeStorage.ts:37–39,59–77`, `app/src/store/useAppStore.ts:269–270`.
- **문제:** 도중 쓰기 실패 시 local 참조를 영구히 버리므로 이후 `clearEvents`/`resetData`는 메모리만 갱신한다. 원본 localStorage에는 이전 개인정보 없는 이용 기록·제보·저장 상태가 그대로 남고, 다음 실행에 다시 복원된다. 메모리 대체의 휘발성 자체와 별개로 사용자가 완료했다고 인식한 초기화가 취소되는 문제다.
- **근거:** local에 place_view 1건 저장 → 다음 쓰기부터 용량 오류 → `resetData()` → 쓰기 가능 상태로 새 wrapper/store 생성 시 과거 place_view 1건이 복원되는 것을 재현했다. 이 경우 local의 `removeItem`은 정상 동작한다.
- **권장 수정안:** 쓰기 실패 후에도 삭제/재시도를 위한 원본 저장소 핸들은 유지한다. 최소한 전체 초기화는 원본 key 삭제까지 시도하고, 기록만 초기화할 때는 정리된 최신 상태를 원본에도 재저장할 수 있어야 한다. 영구 반영 실패를 호출 측에서 구별할 수 있는 결과도 제공한다. 대체 이후 초기화→새 wrapper로 재실행하는 테스트를 추가한다.

## M-04 — 손상된 선택 필드가 이벤트 검사를 통과해 리포트를 중단시킴

- **위치:** `app/src/domain/events.ts:137–147,158–174`, `app/src/store/useAppStore.ts:163`.
- **문제:** phrase_play/practice_done/staff_shown은 src만 검사하고 선택 필드인 phraseId/placeId/score의 타입·범위를 검사하지 않는다. 따라서 `isAppEvent`의 타입 보장이 성립하지 않는다.
- **근거:** `{type:'phrase_play',src:'phrase',phraseId:{raw:'text'},t:2}`가 통과한다. 정상 phraseId 이벤트 뒤에 이 이벤트를 넣고 `topPhrases`를 호출하면 동률 정렬에서 `a.phraseId.localeCompare is not a function`이 발생한다. persist로 복원된 손상 데이터가 F-16a 리포트 화면을 깨뜨릴 수 있다.
- **권장 수정안:** 존재하는 선택 ID는 문자열, score는 유한한 0~100 숫자인지 검사한다. 잘못된 이벤트를 버리거나 명시적으로 정제한 뒤 사용한다. 숫자/객체 phraseId, 잘못된 placeId, 범위 밖 score, 손상 데이터 복원 후 실제 지표 계산 테스트를 추가한다. M-01의 필드 제거와 이 항목의 필드 값 검증을 함께 구현할 수 있다.

## M-05 — 다른 장소의 setTakeout 호출이 현재 장소의 매장 고정을 해제함

- **위치:** `app/src/store/useAppStore.ts:191–192,243`.
- **문제:** 수량 변경은 currentPlaceId를 확인하지만 setTakeout은 전달받은 장소만 검사한다. 단일 boolean 설계에서는 다른 장소의 호출이 현재 주문의 설정을 바꾼다.
- **근거:** `switchPlace({id:'gwc',takeout:false})` 다음 `setTakeout({id:'ssd',takeout:true},true)`를 호출하면 currentPlaceId는 gwc인데 takeout은 true가 된다. Phase 2에서 확인 대기 중 대상 장소의 토글이나 이전 화면 콜백을 연결하면 이 경로가 열릴 수 있다. 현재 테스트는 항상 같은 장소 인자로만 호출한다.
- **권장 수정안:** setQty처럼 현재 장소 ID와 일치할 때만 변경하고 성공 여부를 반환한다. 문장 생성 시에는 별도로 `effectiveTakeout`을 반드시 거친다. 다른 장소/확인 대기/전환 취소 상태에서 호출하는 테스트와 매장 전용 장소의 실제 주문 문장 테스트를 추가한다.

## M-06 — 손상 복원 시 장바구니와 현재 장소 관계를 복구하지 않음

- **위치:** `app/src/store/useAppStore.ts:131–147,227–231,284`, `app/src/store/useAppStore.test.ts`의 ‘모양이 틀린 저장값은 걸러서 복원’ 테스트.
- **문제:** cart와 currentPlaceId를 각각 정제해 주문이 있지만 현재 장소가 null이거나 다른 장소인 상태를 허용한다. switchPlace는 currentPlaceId의 주문만 확인하고 전체 cart를 비우므로 살아남은 주문이 확인 없이 삭제된다.
- **근거:** `{cart:{ssd:{m1:2}}}`를 persist state로 복원하면 currentPlaceId는 null이다. 이어 SSD로 전환하면 `{needsConfirm:false}`와 빈 cart가 나온다. 기존 손상값 테스트도 currentPlaceId 없는 cart 복원을 허용하지만 이후 액션을 검증하지 않는다.
- **권장 수정안:** 복원 시 단일 활성 주문 불변식을 복구한다. 비어 있지 않은 장소가 하나면 currentPlaceId를 그 장소로 복구하고, 다중/불일치 상태는 명시한 복구 정책을 적용한다. 전환 시 남아 있는 다른 장소 주문도 확인 대상에서 누락되지 않게 한다. 손상값 복원→전환→취소/확인까지 검증한다.

## 지표·설계 판단과 Phase 2 연결 조건

- **이벤트/상한:** 요구한 6종이 모두 정의돼 있고 append 및 복원 모두 최신 배열 항목 500개로 제한한다. clearEvents와 resetData가 있으며, reports는 별도 배열이다. 500건 제한은 events 요구이므로 reports가 500건으로 제한되지 않는 것 자체는 위반으로 세지 않았다.
- **추가 방문 비율:** 분모는 anchor place_view를 포함한 세션 수, 분자는 그 첫 열람 이후 다른 place_view가 존재하는 세션 수다. 중복 anchor는 분모를 늘리지 않으며 다른 장소를 먼저 본 경우는 분자에서 제외한다. 30분 이상 이벤트 간격에서 분리하고 정렬하므로 현재 정의 및 경계 테스트에 맞는다. 빈 분모는 null이다.
- **세션 표시:** 실제 활동의 관찰치는 기록된 이벤트이므로 Phase 2가 화면/장소/문장 활동을 빠짐없이 기록해야 한다. 500건 절단으로 세션 앞부분이 사라질 수 있으므로 내 기기 리포트는 보관된 기록 범위의 값으로 설명해야 한다. 전체 기간 사용자 방문률이나 실제 방문 인증으로 표시하면 안 된다.
- **anchorPlaceId 인자화:** 순수 계산 함수의 재사용·테스트를 위해 타당하다. Phase 2의 ‘성심당’ 지표 호출부는 실제 데이터의 성심당 ID인 `ssd`를 두 함수에 동일하게 전달해야 한다. 임의 현재 장소 ID를 전달해 놓고 성심당 비율이라고 표시하면 정의가 달라진다.
- **다음 장소/문장:** nextPlaceDistribution은 세션마다 최초 다른 장소 1개를 세고 topPhrases는 phraseId가 있는 phrase_play만 센다. 다음 장소 분포의 정규화 분모와 ‘많이 쓴 문장’을 ‘재생 횟수’로 보여 줄지 화면 계약에 명시해야 한다. 주문 문장은 phraseId가 없어서 이 순위에서 제외된다. 현재 PRD가 이 세부 집계 방식을 확정하지 않았으므로 결함으로 단정하지 않았다.
- **단일 takeout:** task.md는 장소별 맵을 요구하지 않고 F-05는 전환 시 주문 비우기를 요구하므로, 단일 활성 주문과 단일 boolean 조합은 타당하다. 목업 `mockup/index.html:479,494,620,652,757`은 장소별 값이며 ssd 기본값도 true이지만 store 기본값은 false다. 포장 가능 장소 사이에는 이전 선택이 승계되고 매장 전용 장소를 거치면 false가 유지되므로 장소별 선택 기억은 제공하지 않는다. 이는 명시 요구 위반이 아니라 화면 이식 시 알아야 할 차이다. 목업의 `takeout[pid]` 접근을 그대로 복사하면 안 된다.
- **현재 장소만 cart 수정:** 다른 장소 주문이 섞이는 것을 막는 판단은 타당하다. Phase 2는 장소 상세 라우팅과 switchPlace를 연결하고, needsConfirm 상태에서 현재 주문 UI를 유지한 채 확인/취소를 처리해야 한다. 초기 직접 진입도 먼저 장소를 설정해야 하며 setQty/increment의 false를 무시하면 버튼이 무반응으로 보인다. M-05·M-06을 보완하면 불변식이 더 명확해진다.
- **포장 문장 방어:** effectiveTakeout 자체는 올바르지만 현재 buildOrderSentence는 boolean만 받으므로 자동 적용되지 않는다. Phase 2 주문/직원/연습 화면은 같은 장소 기준의 effectiveTakeout 결과를 문장 생성에 전달해야 한다. 실제 store→문장 생성 연결 테스트가 필요하다.
- **F-13~F-16a:** 북마크 토글/persist 및 종류 제한 제보 저장+report_sent 생성은 정상이다. 초기화 시 언어 유지도 정상이다. 내 기기 제보 건수는 reports 기준으로 읽어야 500건 이벤트 절단과 분리된다. 예시 데이터는 현재 store에 섞이지 않으며, 예시/내 기기 리포트 분리 표시는 Phase 2에서 검증할 사항이다.

## 테스트 충분성

41개 테스트는 정상 상태 변경, 전환 확인/취소, 수량 제한, takeout 강제, 북마크, 이벤트 상한, 지표 분자·분모, 정확히 30분 경계, 기본 persist와 실패 대체를 적절히 다룬다. 다만 기존 데이터가 있는 시작 시 quota, 대체 후 삭제의 재실행 지속성, 원문/추가 필드 제거, 선택 필드 손상 후 실제 집계, 다른 장소 takeout 호출, 관계가 깨진 cart 복원은 빠져 있다. 각 항목의 재현을 회귀 테스트로 추가한 뒤 T1.6 완료를 판단하는 것이 적절하다.
