## R2 해결 확인

### R2-M-01 자동 잠금 회수 경쟁 — 해결

- `app/scripts/lockDir.mjs`의 `acquireLock`에는 `tryReclaim`·회수 mutex·오래된 남의 잠금을 rename/삭제하는 경로가 없다. 살아 있는 PID·죽은 PID·owner 없는 오래된 잠금 모두 읽고 기다리며, deadline 이후 `ELOCKTIMEOUT`으로 종료한다. CLI는 이를 종료 코드 4로 변환하고 소유 PID·시각(없으면 unknown owner·폴더 시각), 다른 패치가 없을 때 `--break-lock`을 쓰라는 안내를 출력한다.
- 남아 있는 삭제·이동은 자기 토큰 확인 뒤 해제, 방금 생성한 디렉터리의 owner 쓰기 실패 정리, 명시적으로 호출한 수동 `breakLock`이다. 정상 획득 대기자가 다른 소유자의 잠금을 지우거나 옮기는 경로는 없다. 자동 회수가 없어 현재 소유자가 해제 전까지 자기 디렉터리를 유지하며, 오래된 토큰의 늦은 해제는 현재 토큰과 다르면 거부된다.
- 수동 `--break-lock`은 살아 있는 PID를 거부(코드 5), 종료된 PID의 잠금을 삭제(0), 잠금이 없으면 no lock(0)으로 처리한다. owner가 없으면 60초 이하에서는 거부하고 60초를 넘겨야 삭제한다. 패치 파일을 함께 주면 사용법 오류(2)다. PID 확인의 EPERM은 살아 있는 것으로 취급한다.
- 이 수동 명령은 **coordinator가 다른 패치 작업이 없을 때 실행한다는 승인된 운영 조건** 아래 평가했다. 임의의 병렬 수동 정리까지 상호 배제를 보장하는 명령은 아니다. `task.md:373`에 코드 4 보고와 coordinator의 수동 정리 조건이 명시되어 있고 CLI 주석·안내와 일치한다.
- 잠금 테스트 17개는 남은 잠금 대기 중 rename/rm 호출 0회, 토큰 해제, 늦은 해제, 수동 정리, EPERM/EACCES/EBUSY의 제한된 재시도 및 원인 보존을 검사한다. CLI 테스트는 실제 프로세스에서 코드 4·5와 안내, 죽은 PID 수동 삭제 후 적용, 서로 다른 두 패치의 동시 적용 결과 보존을 검사하며 모두 통과했다. 타입 선언도 현재 API와 일치한다.

### R2-M-02 으능정이 전경 얼굴 — 해결

- `app/public/photos/euneungjeongi.webp`(1200×797, 157,162 B)를 직접 열었다. R2에서 지적한 앞쪽 검은 겉옷 인물과 바로 오른쪽 밝은 상의 인물의 얼굴에 추가 흐림이 보이며, 눈·코·입 등 식별에 쓸 만한 뚜렷한 얼굴 특징을 발견하지 못했다. 나머지 보행자 얼굴도 최종 배포 해상도에서 추가 지적할 뚜렷한 특징을 발견하지 못했다.
- `photos.ts`의 `changes: blurred(18)`과 CREDITS의 `18 areas`가 일치한다. CREDITS는 review·세 언어 alt·원본 고지·사용처와 변경 사진의 동일 라이선스 공유 문구를 포함하며, 생성 결과와 파일의 정합성 테스트가 통과했다. 18개 처리 좌표 자체를 독립적으로 다시 센 것은 아니다.
