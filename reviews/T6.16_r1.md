## M — 수정 요청

### M-01. 움직임 줄이기를 켰다 끄면 해제한 blob URL과 준비 상태를 재사용한다

- 위치: `app/src/screens/Lang/IntroStage.tsx:51–67, 115–126`.
- 영상 재생 → OS reduced-motion 켜기 → 끄기. 켤 때 cleanup이 URL을 revoke하지만 `src`, `ready`는 그대로다. 끄면 새 fetch 완료 전에 이전 URL로 video를 다시 만들고 `usable=true`로 판정한다. 이 요소의 오류나 play 거부가 `failed=true`를 설정하면 이후 새 URL이 도착해도 실패 상태가 복구되지 않는다. 새 src를 넣어도 usable 값이 같으면 재생 effect가 다시 실행되지 않는 경로도 있다.
- Orca 내 실제 Chromium에서 기존 빌드를 열어 재현: 처음 video on → `set media reduced-motion reduce`에서 video 없음 → `set media light`로 reduce=false 복귀 후에도 video 없음/data-video=off. 소스의 관련 로직도 동일하다.
- 요청: 로드 세대별로 src/ready/failed를 관리하고, 새 소스의 canplay 전에는 usable로 알리지 말 것. 해제한 URL을 렌더하지 말고 이전 세대의 오류·promise 결과를 무시할 것. 설정 왕복 테스트가 필요하다.

### M-02. 정상적인 일시정지가 이전 play promise를 취소해도 영구 실패로 취급한다

- 위치: `app/src/screens/Lang/IntroStage.tsx:80–101`.
- `play()` 직후 아직 promise가 pending인 동안 사용자가 일시정지하면 `pause()`가 해당 재생 요청을 AbortError로 종료할 수 있다. 현재 catch는 요청의 유효성·취소 이유와 무관하게 `setFailed(true)`를 호출한다. 빠르게 정지/재생하거나 설정 변경으로 video가 교체되는 경우에도 오래된 catch가 현재 영상을 제거할 수 있다.
- 결과: 사용자가 정상적으로 정지했을 뿐인데 이후 재생 버튼이 영상 대신 정지 그림 타이머만 재생한다. 느린 디코딩/모바일에서 드러날 수 있는 경쟁이며, 이번 검토에서는 코드 경로로 확인했다.
- 요청: effect cleanup에서 재생 요청을 무효화하고 현재 요청의 실제 재생 거부/미디어 오류만 fallback으로 처리할 것. deferred play promise → pause → 이전 promise reject → resume 순서의 회귀 검사를 추가할 것.

### M-03. 구간 끝을 넘긴 경우 현재 프레임을 그대로 멈춰 다른 장면과 설명이 불일치한다

- 위치: `app/src/screens/Lang/IntroStage.tsx:87–95`.
- 100ms interval은 실행 간격의 보장이 아니다. 탭 선택 후 백그라운드 타이머 제한이나 메인 스레드 지연이 생기면 영상은 경계 너머까지 진행할 수 있다. 현재 코드는 `pause()`만 하고 선택 구간 안으로 시간을 되돌리지 않는다. 0.2초 여유는 이를 막지 못한다.
- 실제 Chromium 기존 빌드에서 Order 선택 후 4.8초간 메인 스레드를 지연시켰다. 콜백 재개 뒤 **currentTime=9.360519, paused=true, scene=order**가 됐다. 즉 직원 영상에서 주문 설명으로 멈췄다. 기존 빌드는 보고서에 적힌 여유 조정 전일 수 있으나, 현재 소스도 overshoot를 보정하지 않아 같은 결함이 남는다.
- 요청: 지연 뒤에도 최종 정지 프레임이 선택 구간 안에 있도록 시간 clamp/seek를 수행할 것. 숨김 상태에서는 구간 재생 정지 정책도 정하고 테스트할 것. 가짜 시간만 이동시키는 테스트도 경계 초과 후 pause 호출뿐 아니라 최종 currentTime을 검사해야 한다.

### M-04. 영상이 늦게 준비될 때 fallback 장면에서 일시정지하면 영상과 설명이 영구히 어긋날 수 있다

- 위치: `app/src/screens/Lang/IntroStage.tsx:73–85`, `app/src/screens/Lang/index.tsx:105–110`.
- 재현 순서: 초기 fetch/canplay를 4.4초 넘게 지연 → 부모 fallback 타이머로 Order 설명 표시 → 일시정지 버튼 클릭 → 영상 준비 완료. 사용자가 탭을 고르지 않았으므로 seekToken=0이다. 준비된 video는 0초에서 시작하고 seek effect는 건너뛰며, paused effect는 pause만 한다. 결과적으로 코스 첫 프레임과 주문 설명이 함께 유지된다.
- 자동 모드에서도 준비 직후 최대 한 poll 동안 앞서 진행한 설명과 0초 영상이 불일치하고 코스로 역행한다. 핵심 수정 대상은 paused 상태의 지속적 불일치다.
- 요청: 정지 그림에서 영상으로 넘어갈 때 현재 선택 장면/일시정지 상태를 명시적으로 인계할 것. 지연 로드 중 fallback 전환·pause·canplay 순서를 검사할 것.

## L — 보완 요청

### L-01. 원본 코드 사본에 MIT 저작권·허락 고지 본문이 없다

- 위치: `intro-film/CREDITS:3–10`, `intro-film/src/*`.
- CREDITS의 코드 MIT / 문서 CC BY-NC + 영상 제작 추가 허락 구분은 공식 LICENSE와 부합한다. 직접 만든 영상은 상업 용도도 가능하며 영상 자체에 크레딧이 필수라는 문제는 아니다. 다만 복사한 엔진 소스에 MIT 저작권·허락 고지를 보존해야 하는데, 현재 CREDITS는 라이선스명/저장소 링크만 적고 원본 폴더에도 LICENSE 파일이나 해당 본문이 없다.
- 요청: 엔진 사본에 적용되는 원본 저작권·MIT 본문을 원본 폴더에 보존하고, 사용한 upstream 버전/커밋과 추가 허락 링크를 기록할 것. 렌더된 영상에 CC BY-NC가 그대로 적용된다고 표기할 필요는 없다.
- 확인 근거: [공식 LICENSE](https://github.com/lemomo-ai/lemo-opuscar/blob/main/LICENSE), [공식 MIT 본문](https://github.com/lemomo-ai/lemo-opuscar/blob/main/LICENSES/MIT.txt). 원본 영화/사진/음성 재사용이 아니라 코드 렌더라는 현재 범위로 판단했다.

### L-02. 매체 수명과 실제 로더 검사가 빠져 위 경쟁들을 놓친다

- 위치: `app/src/screens/Lang/Lang.test.tsx:12–16, 317–430`.
- load/release를 전체 mock하므로 fetch 실패·빈 blob·MIME 보정·revoke·늦은 완료를 실제로 검증하지 않는다. video 테스트의 play는 즉시 resolve하고 pause는 아무 상태도 바꾸지 않는다. StrictMode 이중 effect, 동적 reduced-motion, onError, 지연 play 취소를 검사하지 않으며 언마운트 테스트도 timer 수만 검사한다.
- 요청: 로더의 독립 테스트와 늦은 resolve/reject·URL 해제 횟수·StrictMode 재마운트/언마운트 검사를 추가할 것. 임의 currentTime setter는 원래 descriptor를 저장해 복구할 것(`restoreAllMocks`는 직접 defineProperty한 값을 복원하지 않는다).
- 삭제한 테스트는 대부분 제거된 SVG 구조/색/애니메이션에 묶여 있어 삭제 자체는 타당하다. 언어 선택·저장·이벤트·탭 계약 검사는 유지됐다. 기존 E2E는 언어 선택/진입을 확인하지만 신규 영상 상태 기계를 검증하지 않으므로 E2E 81개 통과만으로 모바일 영상을 입증하지는 못한다.

### L-03. 진행 막대는 영상 시간과 별개인 4.4초 CSS 애니메이션이다

- 위치: `app/src/screens/Lang/index.tsx:174–181`, `lang.css:119–140`.
- 영상 준비가 늦어지거나 구간 끝/중간에서 재생을 재개하면 막대는 처음부터 4.4초를 재지만 실제 영상의 남은 장면 시간은 다르다. 예를 들어 Order 구간 끝에서 전체 재생을 누르면 막대가 거의 비어 있는 상태에서 Staff로 넘어간다.
- 요청: 영상 사용 중에는 currentTime의 구간 내 진행률로 막대를 표시하거나 재생 재개 시 offset을 인계할 것. fallback만 기존 CSS 타이머를 사용하면 된다.

## 기타 검토 사항

- 접근성: 장식 전체 aria-hidden, 이미지 alt 빈 문자열, muted·playsInline, 탭의 aria-selected/controls와 키보드 이동, 수동 선택 시 polite/자동 재생 시 off, 44px 터치 영역·흰 초점 표시가 유지된다. 정적 reduced-motion 진입 시 영상 fetch/재생·자동 전환을 하지 않는다. 글자색은 기존 토큰을 유지하고 공용 대비 검사도 통과했다. 동적 설정 복구는 M-01을 해결해야 한다.
- 오프라인: 추가 4파일 **967,080B(약 0.967MB)**. MP4는 일반 2MiB 사전 캐시 파일 제한보다 작다. 기존 dist/sw.js에서 영상·정지 그림 3개 revision 항목을 확인했다. `PRECACHE_STATUS`는 전체 manifest를 matchPrecache로 확인하므로 이 자산도 준비 완료 판정에 포함된다. 영상 다운로드 실패/지연은 최초 SW 설치와 준비 완료를 지연시키지만, 누락 자산을 준비 완료로 오판하는 새 경로는 발견하지 못했다. 새 빌드 산출물 확인은 coordinator 검증에 포함할 것.
- 모바일: 전체 fetch → blob URL은 캐시 영상 Range 응답 의존을 줄이며 현재 파일 크기는 약 0.93MB다. muted/playsInline과 거부 fallback도 있다. 다만 실제 디코더/저전력 모드 검증은 하지 않았다. StrictMode 최초 effect는 두 fetch를 시작할 수 있지만 alive 가드가 늦게 생성된 URL을 revoke한다. 네트워크 요청 자체는 abort하지 않아 언마운트 후 완료까지 전송이 남고, 실패로 video가 제거돼도 blob은 effect cleanup 전까지 유지된다. 현재 크기만으로 심각한 메모리 결함이라고 단정하지 않았다.
- SVG 제거: app/src에서 옛 scenes import·장면 CSS 클래스·lang-screen--still 사용은 발견하지 못했다. `lang.turnScreen` 번역 키는 작업 보고대로 미사용 상태로 남아 있다. 실행 오류는 아니다.
- 요청에 언급된 `app/src/i18n/patches/T6.16.json`은 **존재하지 않는다**. 이번 diff는 번역 키/문구를 추가하지 않고 기존 T6.1 사전을 사용하므로 기능상 누락으로 판정하지 않았다.
