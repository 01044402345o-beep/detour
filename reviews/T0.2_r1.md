# T0.2 앱 골격 검토 R1

- 검토일: 2026-11-23. 기준: `task.md` T0.2와 Phase 1 공유 계약, `prd.md` v0.3 7·8·8.1절.
- 대상: `app/` 소스·설정·설치된 의존성 및 생성된 빌드. 소스·설정·lock 파일을 수정하지 않았다. 허용된 build 실행으로 무시 대상인 `app/dist/`가 생성됐다.
- 결과: 기본 검사 4종은 통과했다. 다만 Phase 1에 넘길 실패 상태 계약과 골격 테스트에 수정할 항목 2건이 있다. audit moderate 4건은 아래에서 발생 경로와 실질 위험을 별도로 평가했다.

## 1. 미해결 항목

### M-01 — STT 미지원 상태만 실패 대응 액션 계약에서 빠져 있다

- **위치:** `app/src/types.ts:135`, `app/src/types.ts:141`.
- **문제:** `denied`·`no-speech`·`timeout`·`network`·`aborted`·`error`에는 `actions: { retry, showStaff }`가 있지만, `unsupported`는 `{ status: 'unsupported' }`뿐이다. `task.md` T1.5는 모든 실패 상태에 두 선택지를 제공하도록 하고, F-08과 Phase 2 E2E는 API 미지원에서도 직원 화면까지 완주하게 한다. 공유 타입대로만 구현하면 이 분기에는 공통 fallback 액션이 없다.
- **확인:** 파일을 만들지 않는 TypeScript 메모리 컴파일에서 `if (s.status === 'unsupported') s.actions.showStaff()`를 검사하자 TS2339(`actions`가 없음)를 재현했다. 현재 앱에는 음성 화면이 없으므로 전체 타입 검사 통과가 이 누락을 잡지는 못한다.
- **영향:** T1.5와 이후 UI가 미지원만 별도 계약으로 처리하거나, 공유 타입을 다시 수정해야 한다. 계약 확정 단계에서 미지원 경로를 명시하는 편이 맞다.
- **수정안:** `unsupported`도 공통 실패 액션을 갖도록 하거나, 실패 액션을 상태 바깥의 공용 어댑터 계약으로 분리해 미지원에서도 두 선택지에 접근할 수 있게 정한다. 지원하지 않는 기기의 retry가 어떤 안내를 하는지도 구현 단계에서 같은 계약으로 처리한다.
- **닫힘 기준:** 미지원 및 기존 6개 실패 상태 모두에서 직원 화면 전환과 재시도 선택지를 타입 계약으로 표현할 수 있어야 한다.

### M-02 — 수사 구현이 완료되면 기존 골격 테스트가 반드시 실패한다

- **위치:** `app/src/App.test.tsx:18`~20, `app/src/domain/numerals.ts`.
- **문제:** ‘시그니처가 존재한다’는 테스트가 실제로는 `toNative(1)`과 `toSino(1)`이 `T1.3` 오류를 던지는 것을 요구한다. T1.3이 정상 구현해 각각 `한`·`일`을 반환하면 이 테스트는 실패한다. 구현을 미룬 stub 자체는 T0.2 범위에 맞지만, 미구현 상태를 계속 유지해야 통과하는 기대값은 후속 task와 충돌한다.
- **영향:** T1.3 소유는 도메인 모듈과 대응 테스트이며 `App.test.tsx`는 아니다. 정상 구현 후 전체 테스트/CI를 통과하려면 소유 범위 밖 골격 테스트를 별도로 고쳐야 한다. Phase 1 실제 모듈 연결 검사에도 같은 문제가 남는다.
- **수정안:** T0.2에서는 함수 export·함수 타입 존재만 확인하거나 해당 임시 assertion을 제거한다. 수사 반환값 검증은 T1.3이 소유하는 `numerals.test.ts`에서 검수표로 수행한다. 실제 수사 구현을 지금 앞당길 필요는 없다.
- **닫힘 기준:** 수사 함수가 명세대로 반환하도록 바뀌었을 때도 T0.2 테스트가 그대로 통과하며, 수사 동작의 정확성은 T1.3 테스트가 검증한다.

## 4. 의존성·audit 위험도 판단

버전은 직접 의존성을 정확한 버전으로 고정하고 lock 파일을 둔 상태다. 설치된 패키지의 engine/peer 계약을 확인했으며 현재 Node·Vite·Vitest·TypeScript·ESLint 조합에서 충돌을 찾지 못했고 기본 검사도 통과했다. CI는 T0.3에서 이 조합의 Node 요구사항을 충족하는 버전으로 고정하면 된다.

audit 4건은 독립적인 브라우저 취약점 4개가 아니다. 확인된 경로는 다음과 같다.

`vite-plugin-pwa@2.0.0 → workbox-build@7.4.1 → glob@11.1.0 → minimatch@10.2.6`

| 원인 advisory | 공식 설명·패치 버전 | 현재 경로 판단 |
|---|---|---|
| [GHSA-3g3m-2fjr-6pw4](https://github.com/advisories/GHSA-3g3m-2fjr-6pw4) | glob의 취소 이후 탐색이 계속되는 가용성 문제. 패치 14.0.2 | 설치된 Workbox `build/lib/get-file-details.js`는 빌드 산출물에 `globSync`를 호출하며 AbortSignal을 전달하지 않는다. 현재 이 호출에서 시간 제한 취소 우회 조건을 사용하지 않는다. |
| [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249) | 공격자가 제어한 패턴이 최적화 전처리에서 증폭되어 CPU·메모리를 소모할 수 있음. 패치 11.0.1 | 현재 패턴·탐색 대상은 PWA 빌드 설정/산출물이며 앱 방문자가 glob 패턴을 입력하는 경로는 없다. |

**프로젝트 위험도 판단:** 개발·CI 빌드 도구의 제한된 가용성 위험으로, 현재 정적 데모 골격을 막을 High/Medium 결함으로 추가 집계하지 않는다. 이 판단은 단순히 devDependency이기 때문만은 아니며, 위 호출 형태와 신뢰된 빌드 입력에 근거한 추론이다. 공격자가 빌드 패턴·파일 트리를 제어하는 환경에는 같은 판단을 적용할 수 없다.

`npm audit --omit=dev`는 0건이고 해당 Node 빌드 라이브러리는 앱 런타임 의존성에 속하지 않는다. Workbox 런타임 SW 파일이 생성된다는 사실과 `workbox-build`의 glob 취약점은 구분한다. audit가 제시하는 `vite-plugin-pwa@1.1.0` 변경은 현재 2.0.0에서의 major 변경이므로 자동 강제 수정은 권하지 않는다. 호환되는 상위 릴리스 또는 검증된 override를 적용할 때 빌드와 PWA 업데이트 검증을 함께 수행하면 된다. 이번에는 의존성을 바꾸지 않았다.

## 5. 결론

T0.2의 실행 기반·데이터 모델·스타일·배포 경로는 대체로 요구사항을 충족한다. Phase 1 시작 전에 M-01·M-02를 판정·수정하고 재검토해야 하며, 현재 미해결은 **Medium 2건**이다.
