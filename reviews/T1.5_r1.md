검증: `cd app; npx vitest run src/speech` — **2 files / 46 tests passed**. 추가로 TypeScript를 메모리에서 변환하여 STT 콜백 재진입을 재현했습니다(파일 생성 없음). Android Chrome·iOS Safari 실기기는 실행하지 않았으며, 아래 브라우저 관련 평가는 공식 문서/API 계약 대조입니다. 단위 테스트 통과를 실기기 호환성 통과로 보지 않습니다.

## M-01 — 상태 알림 중 dispose해도 인식이 새로 시작되고 타이머가 재생성됨

- **위치:** `stt.ts:154–162,184–186`, `stt.test.ts`의 dispose 테스트.
- **문제:** `set()`은 외부 `onState`를 동기 호출하지만 반환 후 세션 유효성을 다시 확인하지 않습니다. `requesting` 알림에서 화면 정리로 `dispose()` 또는 `cancel()`을 호출하면 `detach()`가 아직 시작 전인 인식기를 abort하고 핸들러를 제거한 뒤, 원래 `start()`가 돌아와 `r.start()`를 실행합니다. 화면을 떠난 뒤 마이크 인식을 시작하고 이후 종료 이벤트도 관찰하지 못하는 경로입니다. `listening`/`processing` 알림에서 정리하면 정리 직후 다시 8초 타이머를 만듭니다.
- **근거:** 메모리 실행 결과 `dispose during requesting notification: startedAfterDispose=1, abortedBeforeStart=1, handlersDetached=true`; `dispose during listening notification: timersAfterDispose=1`. 기존 테스트는 이벤트 처리가 완전히 끝난 뒤 dispose하므로 이 순서를 검증하지 않습니다. 브라우저 이벤트 간 병렬 실행 문제가 아니라 공개 콜백의 동기 재진입 문제입니다.
- **권장 수정안:** requesting 알림 후 `live()`·`disposed`·현재 상태를 확인한 뒤 start합니다. listening/processing 알림 후에도 같은 확인을 하거나 알림 전에 타이머를 설치하여 콜백의 정리가 마지막 작업이 되게 합니다. 각 알림에서 cancel/reset/dispose하는 테스트를 추가하고, 시작 횟수 및 남은 타이머 0을 확인합니다.

## M-02 — requesting에 종료 기한이 없어 시작 서비스 지연이 무한 대기로 남음

- **위치:** `stt.ts:134–138,154–157,184–186`; `stt.test.ts`의 “권한 요청 대기(requesting)는 타임아웃하지 않는다”.
- **문제:** requesting은 실제 권한 팝업 대기뿐 아니라 `start()` 호출부터 서비스의 `onstart`까지 모든 지연을 포함합니다. 이미 권한을 승인한 기기라도 서비스가 시작 이벤트·오류·종료 이벤트를 내보내지 않으면 영원히 requesting이며, start 재호출도 차단됩니다. 실패 상태의 retry/showStaff 역시 나오지 않습니다.
- **근거:** 위 테스트는 60초 동안 이벤트가 없을 때 requesting 유지를 명시적으로 통과시킵니다. Web Speech의 start 이벤트는 권한 승인 이벤트가 아니라 인식 서비스가 듣기 시작한 이벤트입니다. 따라서 이 구간 전체를 “사용자가 권한을 결정 중”이라고 볼 수 없습니다. 실제 모바일에서 반드시 발생한다고 단정하는 항목이 아니라, 이벤트 미도착 시 fallback이 없는 확정된 코드 경로입니다. [Web Speech 이벤트 계약](https://webaudio.github.io/web-speech-api/#speechreco-events)
- **권장 수정안:** 권한 응답을 성급히 끊지 않으려는 의도는 유지하되 requesting에도 별도의 유한 watchdog을 두고 timeout과 두 선택지로 종료합니다. 별도 기한을 쓰려면 계약에 명시하고, “권한 미결정”, “권한은 있으나 서비스 시작 무응답”, cancel/dispose 이후 타이머 정리를 검증합니다. UI에서 requesting 중 취소·직원 화면 이동을 항상 허용하는 것도 필요합니다.

## M-03 — 최초 2초 탐색 결과가 영구 캐시되어 뒤늦게 사용 가능한 한국어 음성을 반영하지 못함

- **위치:** `tts.ts:79–91,95–104,146–151`; `tts.test.ts`의 “init은 한 번만 찾는다”.
- **문제:** 첫 탐색이 no-korean-voice로 끝나면 리스너가 제거되고 `pending`은 해결된 Promise로 계속 남습니다. 2초 이후 한국어 음성이 로드되거나 사용자가 설치해도 `init()`·`speak()` 모두 다시 찾지 않습니다. 공유 인스턴스를 쓰므로 화면 재진입으로도 복구되지 않고 F-07의 음성 없음 안내가 계속 잘못 표시됩니다. 선택했던 음성이 제거된 경우에도 이전 voice를 계속 지정합니다.
- **근거:** 재현 순서는 `init → 2000ms 경과 → 한국어 voiceschanged → init`이며 마지막 상태도 no-korean-voice입니다. 공식 계약에서 voiceschanged는 비동기 목록 준비뿐 아니라 설치·제거 때도 발생합니다. 최대 2초 기다리라는 요구는 이후 재탐색을 금지하는 요구가 아닙니다. [Web Speech 음성 목록 변경 계약](https://webaudio.github.io/web-speech-api/#tts-events)
- **권장 수정안:** 진행 중 탐색만 합치고, 완료 후 init/화면 복귀/사용자 발화 시 최신 목록을 동기적으로 재확인하도록 합니다. 계속 구독하는 방식을 택하면 명시적인 해제 수명주기를 둡니다. 2초 이후 한국어 등장과 기존 음성 제거를 테스트합니다. 발화 클릭 안에서 2초를 await하는 수정은 사용자 활성화를 잃을 수 있으므로 피합니다.

## L-01 — TTS cancel의 비동기 종료 통지가 테스트에 반영되지 않음

- **위치:** `tts.ts:107–108,115–123`; `tts.test.ts: MockSynth.cancel`, “onEnd는 끝나거나 오류일 때 호출”.
- **문제:** MockSynth.cancel은 카운터만 올립니다. 실제로 이전 발화 취소 시 이전 utterance의 error가 뒤늦게 올 수 있는데, 어댑터는 이를 새 발화 진행 여부와 무관하게 이전 onEnd로 전달합니다. 공유 재생 상태를 onEnd에서 해제하는 소비자는 새 단어 재생 중에 이전 콜백으로 상태를 종료할 수 있습니다. 현재 소비자 구현이 검토 범위에 없으므로 확정된 화면 장애 대신 API 계약/테스트 보완 항목으로 분류합니다.
- **근거:** TTS 오류에는 cancel에 따른 canceled/interrupted가 정의되어 있습니다. 기존 테스트는 두 발화를 만든 뒤 오래된 콜백을 직접 호출하여 호출 수만 확인하므로 이 순서의 UI 안전성을 검증하지 않습니다. [Web Speech 합성 오류 계약](https://webaudio.github.io/web-speech-api/#speechsynthesiserrorevent)
- **권장 수정안:** 콜백이 “해당 utterance 종료”인지 “현재 재생 종료”인지 문서화합니다. 후자라면 발화 세대 ID와 cancel 시 핸들러 무효화를 적용하고, 전자라면 취소/오류 이유나 발화 ID를 전달하여 소비자가 구분하게 합니다. 취소 직후 새 발화를 시작한 다음 이전 error를 전달하는 목 테스트를 추가합니다.

## 실제 API 및 테스트의 한계

- **userActivation 미지원으로 인한 영구 거부는 현재 코드에 없음.** `tts.ts:113`은 객체가 있을 때만 isActive를 검사합니다. undefined이면 발화를 시도하므로 구형 iOS에서 무조건 not-user-gesture가 되는 구현이 아닙니다. Safari의 User Activation API 도입은 16.4이며, 미지원 환경에서는 동기 클릭 핸들러에서 부르는 호출자 계약과 브라우저 정책에 의존합니다. undefined 환경에서 성공하는 테스트가 이미 있으나 그 의도를 명시하고, 실제 trusted tap과 자동 실행 거부를 기기에서 확인해야 합니다. [WebKit Safari 16.4 안내](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/)
- **접두사 탐지는 적절하나 실제 서비스 가용성과 다릅니다.** 표준 생성자 우선·webkit fallback을 확인하는 테스트는 유효합니다. Safari는 Siri와 같은 인식 엔진을 사용하며 기능 존재만으로 서비스가 사용 가능하다고 볼 수 없습니다. 구형 Safari의 Siri/Dictation 설정 관련 실패 사례도 공식 버그 트래커에 있습니다. 이를 모든 최신 iOS의 필수 조건으로 일반화하지 말고 서비스 거부/권한/오프라인 실패에서 직원 화면 이동을 실기기로 확인해야 합니다. [WebKit 14.1 안내](https://webkit.org/blog/11648/new-webkit-features-in-safari-14-1/), [WebKit 이슈 225298](https://bugs.webkit.org/show_bug.cgi?id=225298)
- **STT 이벤트 정리:** result/error/timeout에서 핸들러를 먼저 해제하고 abort하며, `live()`가 이전 인스턴스를 걸러내는 구조는 적절합니다. result 뒤 end, error 뒤 end가 기존 결과를 덮지 않습니다. speechend 없이 result를 받는 테스트도 있어 고정 이벤트 순서를 전제하지 않습니다. 반대로 규격상 모든 이벤트 순서가 고정된 것은 아니므로 result보다 먼저 end하는 비정상 엔진 사례까지 지원한다고 주장할 근거는 없습니다. 그런 사례는 실제 추적 없이 확정 버그로 집계하지 않았습니다.
- **목의 범위:** continuous=false·interimResults=false이므로 첫 결과의 첫 후보를 쓰는 현재 최소 목은 일반적인 단발 인식 계약에 부합합니다. 다만 실제 results의 isFinal/resultIndex, nomatch, abort에 따라 예약된 error/end는 표현하지 않습니다. 늦은 이벤트 테스트도 이미 null이 된 핸들러를 호출하므로 대부분 이벤트 자체가 전달되지 않는 경로입니다. 캡처해 둔 이전 핸들러를 retry 후 직접 호출하는 테스트와 error→end, processing→end, 취소 시 이벤트 전달을 보완하면 세대 가드를 별도로 검증할 수 있습니다.
- **누수:** 일반 종료/reset/dispose에서 STT 타이머와 핸들러는 정리됩니다(M-01 재진입 예외). TTS 음성 탐색 리스너도 정상 완료 또는 2초 후 정리됩니다. bindAutoCancel의 해제 함수가 pagehide/visibilitychange를 제거하므로 누적 누수는 호출자가 해제하지 않을 때 발생하며, 어댑터 자체의 무조건 누수로 판단하지 않았습니다. 음성 탐색 중 cancel은 탐색까지 취소하지 않지만 잔여 수명은 최대 2초입니다.

수정 우선순위: M-01 수명주기 재진입 → M-02 requesting 종료 경로 → M-03 음성 목록 갱신. L-01은 공용 ListenButton 연결 전에 콜백 계약을 확정할 것을 권장합니다.
