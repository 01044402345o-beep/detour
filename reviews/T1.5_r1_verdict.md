## M-01 — STT 상태 알림 중 재진입 → **부분 타당, M 유지(requesting 경로)**

**근거 (코드 대조)**
- `stt.ts:184–186`: `set({status:'requesting'})`가 `onState`를 동기 호출한 뒤 무조건 `r.start()`. 콜백 안에서 `dispose()`/`cancel()`이 불리면 `detach()`가 `rec=null`·핸들러 제거·`abort()`를 하지만, `r`은 지역 변수이므로 `r.start()`가 그대로 실행됩니다. `try` 블록이 예외 없이 끝나면 아무 가드도 없습니다. 결과: **화면을 떠났거나 사용자가 취소한 뒤 마이크 인식이 시작**되고, 핸들러가 없어 이후 종료도 관찰하지 못함. F-08이 마이크 사용 전 고지를 요구하는 만큼 "취소 후 마이크 켜짐"은 개인정보·신뢰 측면 결함입니다. → M 유지.
- `stt.ts:156–157, 161–162`: `set()` 후 `armTimer(id)`. 콜백에서 dispose/cancel하면 정리 뒤 타이머가 다시 생기지만, 타이머 콜백은 `id === attempt`일 때만 `fail`하고 dispose/cancel은 `attempt++`를 하므로 **실제 동작은 no-op**입니다. 최대 8초 잔여 타이머일 뿐 상태 오염은 없음 → 이 부분은 L로 낮춤. 다만 수정 비용이 같으므로 함께 고칩니다.
- 현실성: React에서 `onState → setState`만 하면 cleanup은 동기 재진입이 아니지만, 소비자가 `onState`에서 곧바로 `cancel()`이나 라우팅(동기 unmount 아님)을 부를 가능성은 있고, 어댑터는 공개 콜백 재진입에 안전해야 합니다.

**수정 지침**
1. `start()`에서 `set({status:'requesting'})` 직후 `if (!live() || disposed) return;` 를 두고 그 뒤에 `r.start()`.
2. `onstart`/`onspeechend`: **`armTimer(id)`를 `set()`보다 먼저** 호출(콜백 안의 정리가 마지막 작업이 되게). 또는 `set()` 뒤 `if (!live()) return;` 후 armTimer. 둘 중 하나로 통일.
3. 테스트 (목에 `startCalls` 카운터 추가):
   - `onState`에서 status가 `requesting`일 때 `dispose()` → `startCalls === 0`, 상태 알림 추가 없음.
   - 같은 조건에서 `cancel()` → 최종 `aborted`, `startCalls === 0`.
   - `listening`/`processing` 알림에서 `dispose()`·`cancel()` → `vi.getTimerCount() === 0`.

## M-02 — requesting 종료 기한 없음 → **타당, M 유지**

**근거**
- `stt.ts:154–157`: requesting은 `start()` 호출부터 `onstart`까지 전부입니다. Web Speech `start` 이벤트는 "서비스가 듣기 시작함"이지 "권한 결정"이 아니므로, 권한이 이미 허용된 기기에서도 서비스 무응답이면 영원히 requesting입니다. `ACTIVE`에 포함되어 `start()` 재호출도 막힙니다.
- `stt.test.ts:337` "권한 요청 대기(requesting)는 타임아웃하지 않는다"는 이 무기한 대기를 의도로 고정하고 있습니다.
- F-08은 "무음·타임아웃·오류·취소는 모두 실패로 보고 재시도/직원에게 보여주기를 제시"를 요구합니다. 시연(T4.5)의 비상 시나리오는 "인식 실패 → 직원 화면"이며, 이 경로가 막히면 시연 진행이 끊깁니다. `cancel()`로 빠져나올 수는 있으나 UI가 requesting 중 취소 버튼을 보여 준다는 보장이 아직 없습니다.
- 권한 팝업을 8초로 끊지 않으려는 원래 의도는 타당하므로, **listening의 8초와 분리된 더 긴 기한**이 맞습니다.

**수정 지침**
1. `export const STT_REQUEST_TIMEOUT_MS = 15000;` 추가, `SttOptions.requestTimeoutMs?`로 주입 가능하게.
2. `set({status:'requesting'})` 직후(M-01 가드 뒤, `r.start()` 전) requesting 전용 타이머를 설치하고 만료 시 `fail('timeout')`. `onstart`에서 listening 8초 타이머로 교체(`armTimer`가 `clearTimer` 하므로 자연히 교체됨).
3. 파일 헤더 주석·`task.md`에 "requesting 15초 / listening 8초 / processing 8초"를 명시(task.md 문구는 coordinator가 반영 — 아래 '후속' 참조).
4. 테스트: 기존 `stt.test.ts:337`을 대체 → 14 999ms에 requesting, 15 000ms에 `timeout` + `retry`/`showStaff` 존재. 만료 전 `fireStart` 시 listening 8초로 재설정. requesting 중 cancel/dispose 후 타이머 0.
5. UI 측 요구(T2 연습 화면 담당에게 전달): requesting 동안에도 취소·직원에게 보여주기 버튼 노출. T1.5 범위 밖이므로 R2 미해결로 집계하지 않음.

## M-03 — 최초 2초 탐색 결과 영구 캐시 → **타당, M 유지** (음성 제거 시나리오는 부분)

**근거**
- `tts.ts:95–104`: `pending`이 한 번 생성되면 결과와 무관하게 재사용됩니다. 첫 탐색이 2초 안에 한국어 음성을 못 찾으면 `no-korean-voice`가 `getTts()` 공유 인스턴스(`tts.ts:146–151`)에 고정되어 새로고침 전까지 복구되지 않습니다.
- 안드로이드 크롬은 콜드 스타트에서 `getVoices()`가 비어 있다가 늦게 `voiceschanged`가 오는 경우가 있어, 진행자 시연 기기에서 **잘못된 "한국어 음성 없음" 안내가 계속 표시**될 수 있습니다(F-07 안내 조건 위반). `speak()`도 `voice`가 null이라 지정 음성 없이 `lang`만으로 재생합니다.
- 기존 음성 제거(설치 해제) 시나리오는 시연 중 현실성이 낮아 부분 타당이지만, 아래 동기 재확인으로 같이 해결됩니다.
- Codex 지적대로 `speak()` 안에서 2초를 await하면 사용자 활성화를 잃으므로 금지.

**수정 지침**
1. `refreshVoice()` (동기): `pickKorean(synth.getVoices())`로 `voice`·`state`를 갱신. 기존 `voice`가 현재 목록에 없으면(`voiceURI` 비교) 교체 또는 null.
2. `speak()` 시작부(사용자 탭 안, 동기)에서 `refreshVoice()` 호출 후 발화.
3. `init()`: 진행 중 탐색만 합치고, 완료된 결과가 `no-korean-voice`이면 `pending = null`로 비워 다음 `init()`이 다시 탐색(또는 먼저 `refreshVoice()`로 즉시 확인 후 필요 시 재탐색).
4. 상시 `voiceschanged` 구독은 해제 수명주기가 생기므로 이번에는 도입하지 않음(1·3으로 충분).
5. 테스트: `init → 2000ms 경과(no-korean-voice) → 한국어 음성 추가 → init` 결과 `ready`; 같은 상황에서 `speak()`가 새 음성을 `u.voice`로 지정하고 `getState() === 'ready'`; 선택 음성 제거 후 `speak()`는 제거된 voice를 지정하지 않음. 기존 "init은 한 번만 찾는다"(`tts.test.ts:93`)는 "진행 중 탐색은 합친다"로 의미를 좁혀 유지.

## L-01 — cancel 후 이전 발화의 늦은 error가 onEnd로 전달 → **타당, L 유지 (이번 라운드 수정)**

**근거**
- `tts.ts:115, 121–124`: `speak()`는 `synth.cancel()` 후 새 발화를 시작하지만 이전 utterance의 `onerror`(`canceled`/`interrupted`)는 크롬에서 비동기로 뒤늦게 옵니다. 이때 이전 `onEnd`가 새 발화 재생 중에 호출됩니다. 단어 칩(F-07 "단어 칩을 누르면 그 단어만 읽음")이나 공용 재생 표시가 onEnd로 "재생 끝"을 처리하면 새 발화가 재생 중인데 표시가 꺼집니다.
- `MockSynth.cancel`은 카운터만 올려 이 순서를 재현하지 않습니다(`tts.test.ts:166–174`는 직접 콜백 호출로 횟수만 확인).
- 소비자가 아직 없어 확정 장애는 아니므로 L 유지. 다만 T2.0 공용 ListenButton이 계약에 의존하므로 R2에서 확정합니다.

**수정 지침 (계약: "onEnd는 그 발화 요청당 정확히 1회, 선점·취소 시에는 즉시")**
1. 모듈 내부 `current: { u, onEnd, done } | null` 유지.
2. `finish(entry)`: `done`이면 무시, 아니면 `done=true`, `entry.u.onend = entry.u.onerror = null`, `entry.onEnd?.()`.
3. `speak()`: 새 발화 전에 `current`가 있으면 `finish(current)`(동기) → `synth.cancel()` → 새 entry를 `current`로. 새 utterance의 `onend`/`onerror`는 `entry === current`일 때만 `finish(entry)` 후 `current=null`.
4. `cancel()`: `current`가 있으면 `finish(current)`, `current=null`, `synth.cancel()`. (`bindAutoCancel` 경로도 동일하게 적용됨)
5. 헤더 주석에 계약 명시.
6. 테스트: MockSynth.cancel이 큐의 기존 utterance에 대해 **비동기(타이머/마이크로태스크)로 onerror('interrupted')** 를 쏘도록 확장 → `speak(A, onEndA)` → `speak(B, onEndB)` → 비동기 진행 후 `onEndA` 1회, `onEndB` 0회. `cancel()` 직후 `onEnd` 1회, 이후 늦은 error로 추가 호출 없음.

## 부가 항목

- **A-1 (nit, 권장)** `dispose()`가 마지막 `result` 상태(인식 원문)를 내부에 남김. `dispose()`에서 `state = { status: 'idle' }`(알림 없이)로 비워 "원문은 결과로만 반환" 원칙의 수명을 명확히. 테스트: dispose 후 `getState().status !== 'result'`.
- **A-2 (nit, 권장)** processing에서 결과 없이 `onend` → `no-speech` 테스트, error→end 순서에서 error 결과 유지 테스트를 추가. 세대 가드 검증을 위해 retry 전에 캡처해 둔 이전 핸들러를 retry 후 직접 호출하는 테스트 1건 추가.
- **Codex 표의 나머지 판정 동의:** 빈 결과→no-speech(F-09 부합), 한국어 음성 없어도 시도(F-07이 금지하지 않음, `started`는 "큐 제출" 의미로 주석 명시 권장), unsupported는 showStaff만(task.md v0.4 부합), userActivation 미지원 시 시도(구형 iOS 영구 거부 아님 — 현 구현 유지). 8초 단계별 적용으로 최대 ~16초가 되는 점은 헤더(`stt.ts:10`)에 이미 단계별로 명시되어 있어 결함 아님.
