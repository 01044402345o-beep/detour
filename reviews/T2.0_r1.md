### T2.0-R1-L01 — 제목 없는 Sheet가 이름 없는 dialog로 렌더링됨

- 위치: `app/src/ui/Sheet.tsx:11`, `:57`.
- 문제: title은 선택 사항이고 이를 생략하면 aria-labelledby도 사라진다. 별도 aria-label prop도 없으므로 공개 API가 허용하는 `<Sheet open onClose={...}>...</Sheet>`는 접근 가능한 이름이 없는 dialog를 생성한다.
- 근거: PRD 7장 접근성. 현재 모든 이름 검사는 title을 제공하는 경우뿐이며, 내용·닫기 버튼만으로 dialog의 이름이 자동 설정되지는 않는다.
- 권장 수정안: title을 필수로 만들거나, 제목 없는 형태에는 번역된 aria-label을 필수로 받는 타입을 정의한다. 두 형태의 접근 가능한 이름을 검사하고 사용 안내에도 계약을 적는다.

### T2.0-R1-L02 — 유효하지 않은 문장 입력을 주문 입력으로 조용히 변환

- 위치: `app/src/router/navState.ts:12`~`:15`, `app/src/router/navState.test.ts`.
- 문제: 타입상 허용되는 `phraseInput('phrase', '')`가 `{ src: 'order' }`를 반환한다. 이를 parsePhraseInput에 넘기면 정상 주문 입력으로 인정된다. 반면 `{ src: 'phrase', phraseId: '' }`를 직접 파싱하면 null이다. 동일한 잘못된 문장 선택이 helper 사용 여부에 따라 거절되거나 현재 주문으로 바뀌는 계약 불일치가 있다.
- 근거: T2.0 입력 상태 계약과 usage의 src 구분. 직원 화면에서는 src가 주문/요청 안내와 주문 항목 노출을 결정하므로 소스를 임의로 바꾸면 안 된다. 정상 데이터의 ID를 그대로 전달하는 경로에서는 발생하지 않는 경계 입력 문제이므로 Low로 분류한다.
- 권장 수정안: src를 보존하고 빈 phraseId는 명시적으로 거절한다(null 반환 또는 명시적 오류 등 일관된 정책). `{ src: 'order' } | { src: 'phrase'; phraseId: string }` 판별 유니온도 권장한다. 빈 ID 생성→파싱 경계를 테스트하고, 실제 ID 존재 여부 검증은 수신 화면/데이터 계층 책임임을 안내한다.

## 중점 검토 판정

### ListenButton / T1.5 계약 ①~④

- ① `useTtsState`는 마운트 시 init을 호출하고 resolve/reject 뒤 getState를 읽는다. alive 플래그로 언마운트 뒤 결과를 무시한다.
- ② click handler에서 speak를 직접 동기 호출한다. init을 await하거나 Promise 뒤에 발화를 연결하지 않는다. 콜드 스타트에서도 사용자 활성화 보존 계약에 맞는다.
- ③ 요청 번호를 speak 이전에 올리고 onEnd에서 일치 여부를 확인한다. 같은 버튼 재탭 시 이전 onEnd는 새 요청 표시를 끄지 않고, 다른 버튼의 선점은 이전 버튼 자신의 표시만 끈다. T1.5는 선점·cancel 시 이전 onEnd를 동기로 호출하고 이후 브라우저 end/error를 무시하므로 이 구현과 정합적이다.
- ④ **자기 요청이 활성인 경우에만 cleanup cancel을 실행하는 해석은 타당하다.** T1.5의 동기 종료 통지 때문에 선점된 버튼의 activeRef는 이미 0이다. 활성 버튼이 언마운트하면 cancel되고, 무관한 단어 칩 제거는 다른 버튼의 발화를 끊지 않는다. 단순히 모든 버튼 cleanup에서 전역 cancel을 호출하는 것보다 요청 소유권을 정확히 지킨다. App.tsx의 bindAutoCancel은 루트 effect 한 곳에서 등록하며 반환 해제 함수도 연결되어 있다. StrictMode의 개발용 setup→cleanup→setup은 구독 누수가 아니라 정상적인 effect 검증이다.
- 적용 전제: 화면 task들이 듣기를 이 공용 버튼으로 수행하고, 화면 이탈 시 해당 버튼을 언마운트해야 한다. 같은 화면 인스턴스에서 `/place/a`→`/place/b`처럼 파라미터만 바뀌면 unmount가 보장되지 않으므로, 그런 이동을 구현하는 화면은 key/cleanup으로 콘텐츠 교체 시 취소를 처리해야 한다. 이는 현재 placeholder에서 확인된 결함은 아니며 사용 안내에 명시하면 좋다.

### 라우트 / screen_view / 첫 실행

- 요구한 13개 경로가 PATHS·ROUTES·SCREENS에 있고, ScreenKey는 events.ts 타입을 사용한다. 화면별 lazy import와 빈 section placeholder를 확인했다.
- LangGate는 lang=null이고 /lang이 아닌 경우에만 replace 리다이렉트한다. 이때 logger를 렌더하지 않아 목적지 이전의 screen_view를 기록하지 않는다. /lang에서는 gate를 통과하고, 미등록 경로는 선택된 언어가 있으면 /로, 없으면 /lang으로 수렴한다. 현재 분기에서 리다이렉트 루프를 찾지 못했다.
- logger는 마지막 location.key를 ref로 기억한다. 일반 재렌더·언어 변경·StrictMode effect 재실행의 중복은 막고, 다른 경로를 거쳐 history back으로 돌아오는 방문은 다시 센다. 미등록 경로는 screenKey가 없어 기록하지 않는다. 현 구현/기존 테스트에서 이중 기록이나 알려진 정상 경로 누락은 발견하지 못했다.
- lazy 화면 로드 성공 여부가 아니라 라우트 진입을 기록하는 위치임을 유의한다. 실패한 청크까지 제외하는 의미의 '화면 표시 완료' 추적은 현재 구현의 보장 범위가 아니다. 후속 화면에서 screen_view를 따로 기록하지 말라는 usage 지침은 적절하다.
