### 1.1 배포 게이트 순환을 끊는 순서 (0.3절에 그대로 넣을 문안)

원칙: **배포가 없어도 확인할 수 있는 것은 모두 배포 전 로컬 `vite preview`(base `/detour/`)에서 검증한다. 배포 후 smoke에는 실제 Pages 환경에서만 확인할 수 있는 것만 남긴다.** task 체크는 [배포 전] 조건 기준이고, [배포 후] 조건이 있는 task만 smoke 뒤에 체크한다.

**공통 (모든 phase)**
1. [배포 전] phase의 모든 task가 [배포 전] 완료 조건을 충족하고 검토 미해결 0건이다. [배포 후] 조건이 없는 task는 이 시점에 체크한다.
2. [배포 전] coordinator가 `dev`의 후보 커밋 해시를 고정해 기록한다.
3. [배포 전] `npm run build`(base `/detour/`) 후 `vite preview`에서 phase E2E를 실행한다. 실패하면 원인 task로 돌아가 1부터 다시 시작한다.
4. [배포] 같은 커밋을 `main`에 병합·push → Actions가 Pages에 배포한다.
5. [배포 후] 배포 URL smoke: HTTPS 200, 콘솔 오류 0, 자산이 `/detour/` 경로로 로드되는지 확인한다.
6. [배포 후] smoke에 실패하면 `main`을 직전 커밋으로 되돌리고 원인 task로 돌아간다.
7. [배포 후] [배포 후] 인수 조건이 있는 task를 확인하고 체크한다.

**Phase 0 (최초 배포)**
- 0-a. [배포 전] T0.1 체크(원격 push). 저장소 Pages 소스를 'GitHub Actions'로 설정한다(`gh api -X POST repos/01044402345o-beep/detour/pages -f build_type=workflow` 또는 사용자가 Settings에서 설정).
- 0-b. [배포 전] T0.2 체크(build·test·lint·tsc 통과).
- 0-c. [배포 전] T0.3 [배포 전] 조건: workflow 파일의 lint·type·test·build 단계가 `dev` push에서 성공한다.
- 0-d. 공통 3 대체: build 성공.
- 0-e. 공통 4~6: 최초 배포 + smoke(200·콘솔 오류 0).
- 0-f. [배포 후] T0.3 [배포 후] 조건 "배포 URL에서 빈 앱이 열림(HTTPS)" 확인 → T0.3 체크.

**Phase 1·2**
- 공통 1~7을 그대로 따른다. Phase 1의 3단계는 "실제 모듈 연결 단위 테스트 + 타입 검사 + build 성공"으로 대신한다. smoke에는 SW 항목이 없다(R2-M-01).

**Phase 3 (PWA 후보)**
- 3-a. [배포 전] T3.1 구현. [배포 전] 완료 조건: preview에서 ① "오프라인 준비 완료" 표시 → 네트워크 차단 → 새로고침 → 미방문 화면 열림, ② **업데이트 토스트를 preview로 확인**한다(빌드 A preview 접속 → 빌드 B로 다시 build·preview → 새로고침 시 토스트 → 새 버전 적용). 배포가 필요 없으므로 T3.1은 이 시점에 체크한다.
- 3-b. [배포 전] T3.3 QR 생성(배포 URL은 고정값이므로 배포 전에 만들 수 있음)과 슬라이드 삽입. T3.1과 병렬이다. [배포 후] 조건(스캔)이 남으므로 아직 체크하지 않는다.
- 3-c. [배포 전] 빌드 고정 → T3.2 측정(preview에서 Fast 4G·캐시 없음 측정, 번들 리포트) → T3.2 체크.
- 3-d. 공통 3: preview에서 Phase 2 시나리오 + 오프라인 시나리오를 실행한다.
- 3-e. 공통 4~6. smoke에 Phase 3 항목을 추가한다: SW 등록(scope `/detour/`), 배포 URL에서 준비 완료 → 오프라인 새로고침.
- 3-f. [배포 후] T3.3 [배포 후] 조건: 슬라이드 화면의 QR을 실제 휴대폰으로 스캔 → 앱 열림 → T3.3 체크.

**Phase 4 (최종 콘텐츠, 27행보다 우선)**
- 4-a. [배포 전] T4.1·T4.2·T4.4 결과 수령 → 사용자 task 체크.
- 4-b. [배포 전] T4.1a 반영(R2-M-02 범위)과 검토 루프. 완료 조건에서 '배포'를 빼고, 미해결 0건이면 체크한다.
- 4-c. 공통 2~6(Phase 4 E2E = preview에서 Phase 2·3 시나리오 재실행 → 배포 → smoke, Phase 3 항목 포함).
- 4-d. [배포 후] T4.3: 4-c에서 배포한 커밋 해시를 기록하고 실기기 점검 → 체크.
- 4-e. [배포 후] T4.5: 같은 커밋 대상 리허설 → 체크. 리허설에서 수정이 생기면 4-b로 돌아간다.

**재검토 확인 기준(Codex 제시 기준과 같음):** 위 목록에서 어떤 [배포 전] 단계도 아직 수행하지 않은 배포의 결과를 요구하지 않는다. → 0-c·3-a·3-b·4-b는 모두 로컬·CI 결과만 요구한다.
