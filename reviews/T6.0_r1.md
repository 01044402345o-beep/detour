## M

### R1-M-01 오래된 잠금 회수와 해제가 다른 프로세스의 새 잠금을 지울 수 있음

- 위치: `app/scripts/i18n-patch.mjs:132-143`, 특히 :134·138-139.
- `stat`으로 오래됐다고 판정한 디렉터리를 소유자 재확인 없이 경로로 삭제한다. 오래된 잠금을 두 worker가 동시에 발견하면 A가 먼저 회수하고 새 잠금을 획득한 뒤 B의 기존 `stat` 결과에 따른 삭제가 A의 새 잠금을 지울 수 있다. B도 획득에 성공하여 두 writer가 동시에 사전을 읽고 쓰게 된다. 각자의 `finally` 역시 현재 소유자와 관계없이 같은 경로를 삭제한다.
- 살아 있는 writer가 중단/지연되어 60초를 넘기는 경우에도 소유자 생존 확인이나 heartbeat 없이 잠금을 빼앗는다. `owner`에 PID를 기록하지만 읽거나 비교하지 않는다. 결과는 서로 다른 패치의 갱신 유실 또는 언어별 서로 다른 최종 세대이며, 병렬 패치 적용의 핵심 잠금 계약에 어긋난다. 최종 직렬 재적용은 복구 기회이지 병렬 적용 중 상호 배제의 증거가 아니다.
- 확인: 파일을 만들지 않는 Node 메모리 fs stub으로 실제 `acquireLock`을 실행했다. B가 오래된 mtime을 관측한 직후 A가 새 잠금을 잡는 순서를 주입하자 `deleted:["A-fresh"], holder:"B"`가 나왔다. 실제 디스크에서 경쟁을 반복 재현한 것은 아니며, 원자적이지 않은 실행 순서의 결정적 재현이다.
- 수정 방향: 소유권·생존/갱신을 검증하는 잠금과 안전한 회수 절차를 사용하고, 해제도 자신이 획득한 잠금만 대상으로 한다. 두 회수자 경쟁, 살아 있는 소유자 지연, 이전 소유자의 늦은 해제, 서로 다른 두 패치 동시 적용을 회귀 검증한다. 현재 :170의 테스트는 소유자가 없는 오래된 디렉터리 하나만 검사한다.

### R1-M-02 잠금 접근/삭제 오류는 제한 시간 없이 busy loop가 됨

- 위치: `app/scripts/i18n-patch.mjs:137-148`.
- 내부 `catch`가 `ENOENT`뿐 아니라 `EPERM`·`EACCES`·`EBUSY` 등을 모두 삼키고 즉시 `continue`한다. 이 경로에서는 아래의 30초 timeout 검사와 100ms 대기를 전혀 실행하지 않는다. Windows에서 오래된 잠금 디렉터리나 그 파일이 잠겨 삭제가 거부되거나 stat 권한이 거부되면 CPU를 소비하며 끝나지 않고, 약속한 종료 코드 4도 나오지 않는다.
- 확인: 같은 메모리 fs stub에서 오래된 잠금 삭제에 지속적인 `EPERM`을 주입했다. timeout을 이미 만료된 값으로 설정해도 4회째까지 재시도되어 `reachedTimeout:false`였다. 프로브는 4회에 강제 종료했으며 실제 파일 권한이나 잠금은 변경하지 않았다.
- 수정 방향: 사라진 경로만 정상 경쟁으로 처리하고, 다른 오류는 원인을 보존해 실패하거나 제한된 대기/재시도를 한다. 모든 반복 경로에서 deadline을 검사한다. Windows 오류 코드별 제한 시간·대기·종료 동작 테스트를 추가한다.
