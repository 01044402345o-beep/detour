## 신규 문제

### T2.2-M-03 — 로딩 중 뷰를 바꾸면 이전 오류가 남아 정상 새 지도를 약도로 전환

- **위치:** `app/src/ui/map/LeafletMap.tsx:75–106` (`batchErrors`, `loading`·`load` 처리), `LeafletMap.test.tsx`의 두 번째 묶음 테스트.
- **문제:** `loading` 이벤트를 매번 새 뷰가 시작된다는 신호로 취급하지만, Leaflet은 이미 `_loading === true`인 동안 새로운 타일을 요청해도 `loading`을 다시 발생시키지 않는다. 이전 뷰에서 성공 1장과 오류 1장이 발생하고 나머지가 대기 중일 때 확대·축소하면, 새 뷰의 타일이 전부 성공해도 이전 `batchErrors`가 남아 `load`에서 `fail()`을 호출한다. `CourseMap`은 한 번 약도로 바뀌면 돌아오지 않으므로 사용자는 정상 지도까지 잃는다.
- **근거:** 설치된 `leaflet/src/layer/tile/GridLayer.js`의 `_update`는 `if (!this._loading)`일 때만 `loading`을 발생시킨다. `TileLayer.js`의 `_abortLoading`은 이전 확대 수준의 미완료 타일을 취소하지만 앱의 오류 카운터는 초기화하지 않는다. 기존 두 번째 묶음 테스트는 첫 묶음을 모두 성공시킨 뒤 확대하므로 두 묶음이 겹치는 상황을 검증하지 않는다.
- **파일 변경 없는 재현:** Node 표준입력에서 jsdom과 설치된 React Testing Library를 사용하고, 실제 `LeafletMap.tsx`를 TypeScript `transpileModule`로 메모리에서 컴파일했다. 실제 Leaflet 인스턴스에 기존 테스트와 동일한 358×288 크기 및 두 정류장을 제공했다. 네트워크를 호출하지 않고 이미지 load/error 이벤트를 주입했다.
  1. 초기 타일 6개 중 첫 타일 성공, 둘째 타일 실패, 나머지는 대기 → `onFail = 0`.
  2. `map.setZoom(map.getZoom() - 2, { animate: false })`로 새 뷰 생성.
  3. 새 타일 9개를 모두 성공 처리 → 새 `loading` 이벤트 **0회**, `load` 이벤트 **1회**, `onFail` **1회**. 현재 타일 9개 모두 정상 load 상태였는데 실패로 판정됐다.
- **관련 기한 문제:** 같은 이벤트 의미 때문에 로딩 중 뷰 변경 시 8초 기한도 새로 시작되지 않는다. 예를 들어 최초 요청 후 7.9초에 확대해 새 타일을 받기 시작하면 새 요청에 약 0.1초밖에 주지 않는다. 이 부분은 코드 흐름으로 확인했으며 별도 시간 재현은 하지 않았다.
- **권장 수정안:** Leaflet의 전역 로딩 구간과 현재 뷰의 유효 타일 집합을 구분한다. 타일별 좌표/확대 수준과 성공·오류·취소 상태를 추적하여 현재 화면에 필요한 타일의 실패만 판정하고, 뷰 변경 또는 취소·제거된 타일의 오래된 오류를 제외한다. 기한도 현재 유효 요청 집합 기준으로 관리한다. 단순히 moveend에서 카운터만 지우면 여전히 보이는 실패 타일까지 잊을 수 있으므로 피한다. 재요청 루프를 추가할 필요는 없다.
- **권장 회귀 검증:** 위 재현에서 새 뷰 전체 성공이면 `onFail = 0`이어야 한다. 로딩 중 줌 변경 후 새 뷰 pending에는 새 기한을 적용하고, 새 뷰에 실제 오류가 있으면 기존처럼 약도로 전환해야 한다. 이동 후에도 화면에 남은 실패 타일은 누락하지 않아야 한다.
