## 1. 사실 확인

**실제 콘텐츠 ID는 형식에 맞습니다.** `downtown.json`의 `id`·`*Id` 27개를 `ID_PATTERN`(`/^[a-z0-9][a-z0-9_-]{0,63}$/`)으로 검사한 결과, 어긋나는 것은 0개입니다(예: `ssd`, `eun`, `ssd-1`, `tw`, `downtown-halfday`). 따라서 지금 배포 데이터에서 `place_view`·`phrase_play`가 버려지는 일은 없습니다. Codex의 재현 1(`SSD-PHRASE`)은 "두 모듈의 계약이 다르다"는 지적으로 타당하지만, 지금 일어나는 결함은 아닙니다.

**screen 키는 실제로 위험합니다. Codex가 짚은 것보다 더 직접적입니다.**
- `task.md:202` T2.0 라우트 표는 `/lang`, `/`, `/place/:id`, `/order` 같은 **경로 문자열**입니다. 화면 task가 가장 자연스럽게 짜는 코드는 `logEvent({ type:'screen_view', screen: location.pathname })`인데, 이 값은 모두 `/`로 시작해 `ID_PATTERN`에 걸립니다. 그러면 **모든 screen_view가 조용히 버려집니다.**
- 그런데도 `AppEventInput.screen`이 `string`이라 타입 검사를 통과하고, `logEvent`는 `void`를 돌려줍니다. 호출하는 쪽은 실패를 알 방법이 없습니다.
- Codex의 재현 2는 코드 흐름과 맞습니다. 중간 screen_view가 버려지면 세션이 나뉘고, 그 결과 F-15의 추가 방문 비율 분자가 0이 됩니다. 시연 리포트(F-16a, 내 기기 기록)의 숫자가 틀리게 나오는 경로입니다.

**ID 형식 규칙과 폐기 정책 자체는 R1 판정 지침입니다** (`T1.6_r1_verdict.md:48`, `:52`). 구현은 지침대로 됐고, 결함은 판정자가 정한 계약에 **호출 측 계약(타입·반환값)**이 빠진 데 있습니다. 원문 저장을 막는 폐기 정책은 그대로 둡니다.

## 2. 심각도 — L 유지

- 아직 `logEvent`를 부르는 화면이 없고(`app/src`의 `.tsx`에서 검색 결과 0건), 콘텐츠 ID는 형식에 맞습니다. 지금 일어나는 장애가 아니므로 M으로 올리지 않습니다.

## 4. 수정 지침 (T1.6 R3)

1. **screen을 고정 키로 정합니다** (`events.ts`).
   - `export const SCREEN_KEYS = ['lang','home','course','place','order','practice','result','staff','reply','phrases','saved','settings','report'] as const;`, `export type ScreenKey = (typeof SCREEN_KEYS)[number];`. `task.md:202` 라우트 표의 13개와 1:1로 대응하고, `/`는 `home`, `/place/:id`는 `place`입니다.
   - `AppEventInput`의 `screen_view`는 `{ type:'screen_view'; screen: ScreenKey }`로 바꿉니다.
   - `toAppEvent`에서 screen은 `ID_PATTERN`이 아니라 `SCREEN_KEYS.includes`로 검사합니다. 형식 검사보다 강해서 `'hello'` 같은 임의 문자열도 막습니다(Codex 끝 단락의 주의점). 복원 경로에서도 같은 함수를 쓰므로 함께 적용됩니다.
   - placeId·phraseId는 지금처럼 `ID_PATTERN` 형식 검사를 유지합니다. 실제 콘텐츠 목록과 대조하는 검사는 events가 data에 의존하게 만들므로 이번에는 넣지 않습니다.
2. **`logEvent`가 boolean을 돌려주게 합니다.** 기록하면 `true`, 버리면 `false`. throw하지 않는 기존 정책은 유지합니다. `RecordSlice` 타입과 주석도 고칩니다. 실패 사유 코드는 이번에 넣지 않습니다(boolean과 테스트로 충분). 콘솔 진단도 넣지 않습니다. 넣게 되더라도 이벤트 종류와 필드 이름만 쓰고 값은 출력하지 않습니다.
3. **계약 테스트를 추가합니다** (`events.test.ts`).
   - `downtown.json`의 모든 `places[].id`와 `places[].phrases[].id`가 `isValidId`를 통과하는지 검사하고, 각 장소마다 `place_view`, 각 문장마다 `phrase_play`를 `toAppEvent`에 넣어 null이 나오지 않는지 확인합니다. 데이터에 형식이 틀린 ID가 생기면 이 테스트가 실패합니다.
   - `SCREEN_KEYS` 전부로 만든 screen_view가 통과하는지 확인합니다.
   - `screen:'/order'`, `screen:'hello'`, `phraseId:'SSD-1'`이면 null.
4. **store 테스트를 추가합니다.** 정상 이벤트이면 `logEvent`가 `true`를 돌려주고 1건이 늘어납니다. 잘못된 ID이면 `false`를 돌려주고 events가 바뀌지 않습니다. 잘못된 screen을 넘기는 테스트는 `as never` 같은 캐스트로 런타임 경로를 검증합니다. Codex 재현 2(0분 ssd → 20분 `order` → 40분 gwc 이면 비율 1)를 올바른 키로 회귀 테스트에 넣습니다.

## 5. Phase 2 이관 요구 (coordinator가 task.md에 반영 권장, T1.6 미해결 집계 제외)

- **T2.0:** 라우트 → `ScreenKey` 매핑을 한 곳(라우터 옆)에 두고 `screen_view`를 남깁니다. `location.pathname`을 그대로 넘기지 않습니다. `/place/:id`는 `screen:'place'`이고, 장소 ID는 별도의 `place_view`로 남깁니다.
- **T2.x 화면:** `placeId`·`phraseId`에는 `downtown.json`의 id만 넘깁니다. 한글 문장·인식 결과·메뉴명은 넘기지 않습니다. 성심당 리포트에는 anchor `ssd`를 넘깁니다(R1 판정 유지).
- **Phase 2 E2E 6번 보강:** 제보 건수뿐 아니라 "성심당 → 다른 정류장" 흐름을 거친 뒤 리포트의 내 기기 추가 방문 비율이 0이 아님을 확인하는 단계를 추가하면, screen·place 기록이 실제로 연결됐는지 검증됩니다(선택).
