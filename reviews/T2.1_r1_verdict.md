## T2.1-M-01 — 부분 타당, Medium → Low

**사실 확인 (타당한 부분)**
- `Lang/index.tsx:51–64`와 `Settings/index.tsx:44–57` 모두 `<button role="radio" aria-checked>`에 `onClick`만 있습니다. `tabIndex`·`onKeyDown`이 없고 네이티브 radio도 아닙니다. 그래서 세 버튼이 모두 Tab 순서에 들어가고, 방향키를 눌러도 아무 일이 일어나지 않습니다. 지적한 내용은 코드와 일치합니다.
- `role="radio"`를 붙이면 보조기술에 "라디오 그룹" 키보드 동작(그룹 안에서 방향키로 이동하고, Tab 진입점은 하나)을 약속하게 됩니다. 이 앱은 그 약속을 지키지 않습니다. 또한 PRD 7장의 지원 브라우저에 데스크톱 크롬·엣지가 있으므로, 키보드 사용자가 아예 없다고 볼 수는 없습니다.

**심각도를 낮춘 근거 (부당한 부분)**
- PRD 7장의 접근성 요구는 "터치 영역 44px 이상, 대비 4.5:1 이상, 글씨 크게"로 정해져 있습니다. 키보드 조작이나 WAI-ARIA 키보드 패턴은 명시된 요구가 아닙니다. T2.0·T2.1 완료 조건에도 없습니다. 검토 근거도 "PRD 7장 취지"라고만 적혀 있어, 명시 요구를 어긴 것은 아닙니다.
- 시연 기기는 터치 전용입니다. 터치나 모바일 화면 낭독기(VoiceOver·TalkBack 스와이프)로 쓰면 각 버튼을 누를 수 있고, 이름과 `aria-checked` 상태도 바르게 읽힙니다. 기능 손실은 없습니다.
- 키보드만 쓰는 사용자도 Tab과 Space/Enter로 모든 언어를 고를 수 있습니다. 조작이 막히지는 않고, 기대와 다르게 동작할 뿐입니다.
- 따라서 시연·요구사항 기준으로는 Low입니다. 다만 고칠 범위가 화면 두 곳이고 분량이 작습니다. 그대로 두면 "ARIA를 잘못 썼다"는 인상이 남으므로 T2.1 안에서 고치는 것으로 판정합니다.

**수정 지침 (T2.1 worker)**
1. **권장안: 네이티브 radio로 바꾸기.** 두 화면 각각 `<label className="lang-opt">` 안에 `<input type="radio" name="lang-choose"|"set-lang" value={code} checked={on} onChange={() => setLang(code)} className="sr-only">`를 둡니다. 이렇게 하면 브라우저가 방향키 이동, 끝↔처음 순환, 선택 항목 하나로만 Tab 진입하는 동작을 맡습니다. 네이티브 radio는 방향키로 이동하는 순간 선택도 함께 바뀌므로 "선택 즉시 언어 전환"(F-01)과 맞습니다.
   - 바깥 컨테이너는 `role="radiogroup"` 대신 `<fieldset>`+`<legend>`를 쓰거나, 지금처럼 `role="radiogroup" aria-labelledby`를 유지합니다. 버튼의 `role="radio"`·`aria-checked`는 삭제합니다.
   - 숨김 input의 스타일은 화면 CSS(`lang.css`·`settings.css`) 안에 둡니다. 공용 `sr-only` 유틸이 이미 있으면 그것을 쓰고, 없으면 화면 CSS에 직접 정의합니다. 공용 styles에 새로 추가하지 않습니다(T2.0 소유).
   - 포커스 표시는 `label:has(input:focus-visible)` 또는 `.lang-opt:focus-within`으로 옮깁니다. 44px 최소 높이(`--touch`), 선택 스타일(`--on` 클래스), `lang` 속성, `data-testid`는 유지합니다. 테스트가 testid로 클릭하므로 label이나 input 중 한 곳에 testid를 두고, 테스트 쿼리를 그에 맞춥니다.
2. **대안: roving tabindex.** 마크업을 바꾸기 어려우면 선택 항목만 `tabIndex={0}`, 나머지는 `-1`로 둡니다. `onKeyDown`에서 ArrowDown/ArrowRight는 다음 항목, ArrowUp/ArrowLeft는 이전 항목으로 이동하고 끝에서 처음으로 순환하게 하며, 그 자리에서 `setLang`과 `focus()`를 실행합니다. 같은 로직이 두 화면에 중복되므로 화면 폴더 안의 작은 hook으로 공유해도 되지만, `app/src/ui/`에 넣지 않습니다(T2.0 소유).
3. **회귀 테스트 (두 화면 각각):** Tab으로 들어가면 선택된 언어에 포커스가 가는지, ArrowDown으로 다음 언어가 선택되고 화면 문구와 store가 바뀌는지, 마지막 언어에서 ArrowDown을 누르면 첫 언어로 순환하는지 확인합니다. 기존 클릭 테스트와 `aria-checked`(또는 `checked`) 상태 검사도 유지합니다. jsdom에서는 네이티브 radio의 방향키 이동이 재현되지 않습니다. 권장안 1을 택하면 방향키 테스트 대신 "`name`이 같은 radio 3개이고, 하나만 checked이며, change 시 setLang이 호출된다"를 검사하고, 방향키 동작은 브라우저 기본 동작에 맡긴다고 테스트 주석에 적으면 됩니다.

## T2.1-L-01 — 타당, Low 유지. 소유·수정 주체: T2.0 공용 UI

**사실 확인**
- `.ui-toast`(`ui.css:295–310`)는 `position:absolute; left:50%`이고 `width`·`right`를 지정하지 않았습니다. 절대 배치 요소의 shrink-to-fit 폭은 "포함 블록 폭에서 left를 뺀 값", 즉 프레임 폭의 절반이 상한입니다. 390px 프레임이면 약 195px입니다. `max-width:calc(100% - 32px)`는 상한일 뿐 폭을 확보해 주지 않습니다. `transform: translateX(-50%)`는 레이아웃 계산이 끝난 뒤에 적용되므로 폭에 영향을 주지 않습니다. Codex의 분석은 CSS 명세와 일치합니다.
- JA `home.soonToast`("近日公開 — デモでは旧都心のみ利用できます。")처럼 긴 문구가 두 줄로 접히는 원인은 이것입니다. EN·ZH 문구, 그리고 Settings의 `settings.resetDone` 등 다른 화면의 토스트도 같은 상한을 받습니다.
- Home은 `toast(t('home.soonToast'))`만 호출합니다(`Home/index.tsx:31`). 화면 쪽에서 원인을 만든 것은 없습니다. 내용이 잘리지 않고 두 줄 표시 자체도 허용되는 동작이라 Low가 맞습니다.

**소유·수정 주체**
- `app/src/styles/`와 `app/src/ui/Toast.tsx`는 task.md T2.0의 소유입니다. 따라서 **T2.0 공용 UI 수정 회차(coordinator가 배정)**에서 고칩니다. T2.1 worker는 화면 CSS에서 `.ui-toast`를 덮어쓰거나 문구에 줄바꿈을 넣어 우회하면 안 됩니다.
- T2.1 완료(체크) 판정에서 이 항목은 제외합니다.

**수정 지침 (T2.0 담당)**
1. `.ui-toast`에 `width: max-content;`를 추가하고, 기존 `max-width: calc(100% - 32px)`는 유지합니다. 그러면 폭은 내용 크기를 기준으로 정해지고, 프레임 폭에서 32px을 뺀 값을 넘으면 그 안에서 자연스럽게 줄바꿈됩니다. `left:50%`와 `translate(-50%)`(`@keyframes ui-toast` 포함)는 그대로 둬도 가운데 정렬이 유지되므로 keyframes는 고치지 않아도 됩니다.
   - 대안으로 `left:16px; right:16px; margin-inline:auto; width:fit-content`를 쓸 수도 있습니다. 이 경우 `transform`과 keyframes의 `-50%`도 함께 빼야 하므로 변경 범위가 더 큽니다. 1안을 권장합니다.
2. `white-space: nowrap`은 쓰지 않습니다. 긴 문구는 여러 줄 표시를 허용합니다.
3. 검증: EN·JA·ZH의 `home.soonToast`와 `settings.resetDone`을 360·390·430px 폭에서 캡처합니다. 짧은 문구는 한 줄, 긴 문구는 좌우 16px 여백 안에서 줄바꿈되는지 확인합니다. 데스크톱(430px 프레임 가운데 정렬)에서도 토스트가 프레임 밖으로 넘치지 않는지 확인합니다. 단위 테스트는 jsdom이 레이아웃을 계산하지 않으므로 추가할 필요가 없습니다. 캡처로 대신합니다.
