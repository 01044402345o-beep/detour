## 2. 기존 미해결 사항

### H-01 — task 완료와 phase 배포 게이트의 순환이 남았다

- **위치:** 14·27행, 46~51행, T0.3 84행, T3.1 218행, T3.3 223~225행.
- **남은 문제:** 27행은 phase의 모든 task가 체크된 뒤 E2E를 실행하도록 한다. 그런데 T0.3은 main 배포, T3.1은 새 빌드 배포 후 업데이트 적용, T3.3은 main 배포 확인과 실제 QR 스캔이 완료 조건이다. 이 조건들을 먼저 만족시켜야 task 체크가 가능하고, 체크해야 배포 전 E2E를 시작할 수 있어 순환한다. Phase 0의 86행은 E2E를 build 성공으로 대체하지만, T0.3을 체크하기 전에 배포 절차를 실행할 수 있다는 예외까지 정하지 않았다.
- **영향:** 작업자가 공통 규칙을 우회해 먼저 배포하거나, 이전 배포본으로 완료 처리할 수 있다. T3.3 전체 병렬 지정도 최종 PWA 빌드의 확인보다 앞선 배포 확인을 허용한다.
- **최소 수정:** 27행의 진입 조건을 ‘배포 전 구현·검토 조건 충족’으로 바꾸고 배포 후 인수 항목은 smoke 이후 체크하도록 분리한다. T0.3 초기 배포, T3.1 캐시 업데이트, T3.3 최종 QR 스캔을 배포 후 인수 항목으로 명시하고, T3.3은 QR 생성만 병렬로 둔다. Phase 4는 이미 적힌 특별 순서가 공통 규칙보다 우선함을 명시하면 된다.
- **재검토 기준:** 최초 배포, PWA 후보 배포, 최종 콘텐츠 배포 각각을 ‘선행 조건 → build/preview 검사 → 배포 → 인수 → 체크’로 나열했을 때, 아직 하지 않은 배포가 선행 체크 조건에 등장하지 않아야 한다.

## 3. v0.2에서 새로 생긴 문제

### R2-M-01 — service worker 구현 전 phase에도 등록 성공을 요구한다

- **위치:** 50행, 86행, 152행, 214~218행.
- **문제:** 새 공통 smoke는 `service worker 등록`을 무조건 요구하고, 괄호의 ‘Phase 3부터’는 오프라인 시나리오에만 붙어 있다. 하지만 SW 구현은 T3.1이다. Phase 0에는 별도 smoke 문구가 있으나 Phase 1·2에는 예외가 없어, 계획대로 구현한 정상 빌드도 배포 smoke에서 실패한다.
- **영향:** 존재하지 않아야 할 기능 때문에 정상 배포를 되돌리거나, PWA를 앞 phase로 임의 이동해야 한다. 이는 R1 판정의 배포 절차를 반영하면서 생긴 단계 적용 범위 문제다.
- **수정안:** ‘모든 phase: HTTP 200·콘솔 오류 0 / Phase 3 이후: SW 등록·오프라인 검사 추가’로 적용 시점을 명확히 한다. Phase 1은 152행의 실제 모듈 검사와 build가 E2E 대체 조건임을 배포 절차에서도 명시한다.
- **재검토 기준:** SW 없는 Phase 1·2 후보는 기본 smoke로 통과할 수 있고, Phase 3 이후에는 SW와 오프라인 실패를 잡아야 한다.

### R2-M-02 — 번역 검수 반영 대상이 UI 사전·문서 표로 좁아졌다

- **위치:** T1.1 98행, T1.3 107~126행, T4.2 236행, T4.1a 239~240행.
- **문제:** T4.2는 UI뿐 아니라 ‘문장 뜻, 가타카나 표기’를 검수한다. 그러나 새 T4.1a는 T4.2 결과를 `i18n/*.json`과 수사 검수표에만 반영하도록 적었다. 고정 문장의 뜻·가타카나·단어 뜻은 T1.1의 `downtown.json`에 있고, 생성 문장의 수사 표기는 T1.3 구현과 테스트에도 들어간다. 239행의 JSON 갱신은 T4.1 현장 결과에만 연결돼 있다.
- **영향:** 검수표와 UI 사전은 수정됐지만 실제 앱의 고정 문장 또는 생성 문장은 검수 전 표기를 계속 보여도 명시된 반영 항목을 모두 수행한 것으로 판단할 수 있다.
- **수정안:** T4.2 결과는 UI 사전, `downtown.json`의 해당 L10n·kana·words, 주문 생성/수사 구현과 대응 테스트 중 영향받는 곳에 모두 반영한다고 명시한다. 수정 필요 없는 파일까지 일괄 변경할 필요는 없다.
- **재검토 기준:** 고정 문장 번역 교정 1건과 생성 수사 가타카나 교정 1건이 들어왔을 때, 문서뿐 아니라 실제 앱 출력과 테스트 기대값까지 갱신하는 책임·경로가 정해져 있어야 한다.

### R2-M-03 — 새 lazy-import placeholder를 만드는 task가 해당 파일을 소유하지 않는다

- **위치:** 33행, T2.0 162·166·170행, 172~197행.
- **문제:** T2.0은 `screens/<이름>/index.tsx`를 lazy import하고 모든 라우트의 빈 화면 표시까지 완료해야 한다. 그러나 T2.0 소유는 ui·styles·App·라우터이며 screens는 없다. 화면 task는 T2.0 완료 후에만 시작한다. T0.2도 폴더 구조만 정할 뿐 해당 placeholder 모듈 생성을 명시하지 않는다.
- **영향:** T2.0이 소유권 규칙을 어기고 화면 파일을 만들거나, 아직 없는 모듈을 import해 타입/빌드·라우트 완료 조건을 만족하지 못한다. 라우트 경로를 정한 것 자체는 적절하며, 별도 통합 task가 필요한 문제는 아니다.
- **수정안:** T0.2에서 정해진 화면 경로의 placeholder를 생성하도록 명시하거나, T2.0에 초기 placeholder 생성 권한을 주고 완료 후 각 화면 task로 소유권을 넘긴다고 적는다.
- **재검토 기준:** T2.1~T2.6 시작 전에 모든 lazy import 대상 파일이 존재하며, 지정 소유권 안에서 T2.0의 타입 검사·빌드·빈 화면 표시를 완료할 수 있어야 한다.
