## M-01 — 저장 실패 시 업데이트가 메모리의 사용자 데이터를 잃게 함

- **위치:** `app/src/sw/pwa.ts:103–119` (등록 옵션 및 applyUpdate), 관련 `app/src/store/safeStorage.ts:28–30, 97–111`, `app/node_modules/vite-plugin-pwa/dist/client/build/register.js`의 `showSkipWaitingPrompt`.
- **문제:** 업데이트 적용은 저장 성공 여부를 확인하지 않고 `updateSW(true)`를 호출한다. 플러그인은 제어권 전환 시 `window.location.reload()`를 수행한다. 앱이 명시적으로 지원하는 localStorage 접근 거부/쓰기 실패 상태에서는 최신 주문·저장 항목·제보·기록이 메모리에만 있으므로 업데이트 한 번으로 소실된다. 업데이트 버튼에는 재로딩에 따른 데이터 손실 안내나 보류 조건이 없다.
- **근거:** safeStorage는 쓰기 재시도도 실패하면 최신 값을 메모리에만 유지하며 `mode='memory'`를 제공한다. 앱 store는 이를 내부 기본 저장소로 사용하지만 PWA 코드는 그 상태를 검사하지 않는다. `onNeedReload`도 지정하지 않아 플러그인의 기본 재로딩이 그대로 실행된다. 기존 A→B 검증은 정상 저장소에서 홈 화면을 업데이트하고 CSS 교체만 확인하며 사용자 데이터 전후 비교는 없다. 이는 소스에서 확인한 조건부 결함이며 브라우저로 저장 실패 조건을 재현한 결과는 아니다.
- **권장 수정안:** 영속 저장 가능 여부/최근 쓰기 성공 여부를 앱에 노출하고, 메모리에만 남은 데이터가 있으면 SW 교체를 보류한다. 재로딩 훅도 앱에서 관리해 다른 탭의 업데이트로 발생하는 제어권 전환에 대응한다. 데이터를 지키기 위해 음성·인식 원문을 새로 영속화해서는 안 된다. 정상 저장 모드와 저장 실패 모드에서 주문·저장·제보·기록 보존을 각각 검증하고, 진행 중 음성 연습은 안전한 시점으로 업데이트를 미룬다.

## M-02 — 업데이트 토스트가 기존 화면의 일반 토스트를 가림

- **위치:** `app/src/ui/Toast.tsx:32–38`, `app/src/sw/updateToast.css:3–15`, 관련 `app/src/styles/ui.css:295–314`.
- **문제:** 일반 알림과 업데이트 알림을 동시에 렌더링하지만 둘 다 동일한 `.ui-toast`의 `position:absolute`, `left:50%`, `bottom`을 사용한다. 업데이트 알림만 z-index 81이고 기존 알림은 80이라 새 버전 안내가 열린 동안 제보 완료·데모 초기화 완료 등의 기존 피드백을 덮는다. 업데이트 안내는 선택 전까지 유지되고 일반 알림은 2.4초 뒤 사라져, 사용자는 완료 알림을 확인할 기회를 잃는다.
- **근거:** `ReportSheet.tsx:45`의 제보 완료 및 `Settings/index.tsx:36`의 초기화 완료가 같은 ToastProvider를 사용한다. 새 CSS에는 일반 토스트와 겹치지 않게 하는 위치 이동/스택 레이아웃이 없다. DOM/CSS에 근거한 검토이며 실제 겹침 스크린샷은 이번 검토에서 생성하지 않았다.
- **권장 수정안:** 공통 토스트 컨테이너에서 세로로 쌓거나, 일반 알림이 표시되는 동안 업데이트 안내의 위치를 분리한다. 업데이트 안내가 열린 상태에서 제보 완료 알림과 초기화 완료 알림이 390px 폭에서도 읽히는지 검증한다.

## L-01 — 검증 실패를 프로세스 성공으로 반환

- **위치:** `reviews/T3.1_verify.mjs:233–243`.
- **문제:** 오프라인 화면 또는 업데이트 검증 예외를 catch에서 로그로만 처리한다. finally의 복구 빌드가 성공하면 `결과: FAIL`을 기록해도 Node 프로세스는 종료 코드 0으로 끝난다. 후속 자동화가 종료 코드로 판정하면 실패한 검증을 성공으로 처리할 수 있다.
- **근거:** `result`의 초기값은 FAIL이고 catch에서 재throw 또는 `process.exitCode` 설정이 없으며 finally 이후에도 실패 종료 처리가 없다. 현재 제출된 로그의 PASS를 부정하는 지적은 아니다.
- **권장 수정안:** 복구와 로그 저장을 마친 후 `result !== 'PASS'`이면 `process.exitCode = 1`을 설정한다. 의도적으로 화면 대기를 실패시켜 로그와 비정상 종료 코드가 함께 나오는지 확인한다.

## 검증 및 증거의 한계

- 직접 실행: `cd app; npm run build` 통과. Workbox 빌드의 inlineDynamicImports 폐기 예정 경고 1건 외 빌드 실패 없음.
- 직접 실행: `npx vitest run src/sw src/screens/Settings src/ui/Toast.test.tsx` — 실제 수집 5파일, 25테스트 통과. 마지막 Toast 경로는 별도 테스트가 수집되지 않았으므로 Toast 회귀를 검증했다고 주장하지 않는다.
- 기존 `T3.1_offline.md`, `T3.1_verify.mjs`, `T3.1_verify.log`를 대조했다. 로그에는 최초 미방문 화면 오프라인 접근, 전 화면 흐름, A→B 적용 PASS가 있다. 스크립트가 소스 CSS 및 기존 증거 파일을 임시 수정하므로 이번 읽기 전용 검토에서는 재실행하지 않았다.
- 기존 검증의 연습 성공은 STT mock 결과다. 실제 오프라인 음성인식 성공 증거가 아니며 실패→직원 화면 대체 흐름은 별도 실제 기기 검증 대상이다.
- 기존 스크립트는 실제 Cache Storage의 OSM/민감 데이터 부재, 이전 자산 제거, 사용자 데이터 유지, 여러 탭의 업데이트를 직접 assert하지 않는다. 앞 표의 해당 판단은 구현 검토에 근거하며 브라우저 실증으로 확대 해석하지 않았다.
- 0.3절 3-d의 Phase 2 전체 시나리오 재실행 증거는 이 오프라인 전용 로그만으로 대체할 수 없다. 빌드 고정 후 공통 E2E 및 3-e smoke는 coordinator 단계에서 별도로 확인해야 한다.
