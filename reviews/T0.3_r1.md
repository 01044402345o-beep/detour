# T0.3 CI·배포 골격 검토 R1

- 검토일: 2026-11-23. 대상: `.github/workflows/ci.yml`, `deploy.yml`(로컬 커밋 `18fceea`).
- 기준: `task.md` T0.3·0.3절 Phase 0, PRD 8장과 현재 Vite·HashRouter 설정.
- **정적 검토에서 수정이 필요한 결함은 발견하지 못했다. 원격 CI·Pages 실행 성공은 아직 확인하지 못했으므로 T0.3 전체 완료 판정은 아니다.**
- 원격 workflow push가 인증 권한 부족으로 거부됐고 사용자 권한 갱신을 기다리는 상태라는 전달 내용을 전제로 한다. 원격 설정 변경·push·workflow 실행은 하지 않았다.

## 1. 설정 검토

| 항목 | 확인 결과 |
|---|---|
| CI 트리거 | dev/main push와 pull_request. T0.3의 dev push 검증 및 PR 검증에 대응한다. |
| CI 단계 | `app/`에서 npm ci → lint → typecheck → test → build. 실패한 단계 뒤에 계속 진행하는 옵션이 없으며 build 자체도 타입 검사를 포함한다. |
| CI 권한 | `contents: read`. 배포 권한을 CI에 주지 않는다. |
| CI concurrency | `ci-${{ github.ref }}`에 cancel-in-progress=true. 같은 브랜치/PR의 이전 검증을 취소하고 최신 변경을 검사한다. Pages 그룹과 이름이 달라 CI가 배포를 취소하지 않는다. |
| 배포 트리거 | main push 및 수동 dispatch. 일반 작업 dev push로는 자동 배포되지 않는다. 수동 재실행도 승인·검증된 main 후보를 대상으로 하는 기존 배포 절차 안에서 사용해야 한다. |
| 배포 권한·환경 | contents:read, pages:write, id-token:write와 github-pages 환경, 배포 URL output을 설정했다. deploy는 `needs: build`로 artifact 생성 성공 뒤 실행한다. |
| 배포 concurrency | `pages`, cancel-in-progress=false. 실행 중인 배포를 새 push로 끊지 않는 구성이다. |
| npm 캐시 | 두 workflow 모두 `cache: npm`, `cache-dependency-path: app/package-lock.json`. lock 파일은 존재한다. `defaults.run.working-directory: app`은 run 단계에 적용되며 action 입력 경로를 `app/app/...`로 바꾸지 않는다. |
| artifact | build는 app에서 실행되어 `app/dist`를 만들고 upload action은 루트 기준 `app/dist`를 사용한다. upload/deploy의 기본 artifact 이름도 `github-pages`로 일치한다. |
| base·manifest | Vite base 및 manifest start_url·scope는 `/detour/`. 앞선 T0.2 실제 빌드에서도 `/detour/assets/...`와 `/detour/manifest.webmanifest` 출력이 확인됐다. |
| Pages 설정 | T0.1a에서 build_type=workflow를 설정하는 전제다. base를 로컬에서 명시했으므로 metadata를 읽는 configure-pages 단계가 없다는 이유만으로 결함으로 세지 않는다. |

GitHub 공식 Pages 문서의 배포 요구사항인 pages/id-token 권한, build 의존성, 배포 환경·URL 설정과 대응한다. [GitHub Pages custom workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)

## 2. 액션 버전·Node 확인

release 페이지뿐 아니라 workflow가 실제 참조하는 major 태그의 `action.yml`도 읽어 확인했다.

| 참조 | 확인 |
|---|---|
| `actions/checkout@v7` | 공식 v7 태그 존재. event의 ref/SHA를 기본 checkout하며 action 실행 런타임은 node24. [공식 정의](https://raw.githubusercontent.com/actions/checkout/v7/action.yml) |
| `actions/setup-node@v7` | 공식 v7 태그 존재. node-version·cache·cache-dependency-path 입력 지원. action 실행 런타임은 node24. [공식 정의](https://raw.githubusercontent.com/actions/setup-node/v7/action.yml) |
| `actions/upload-pages-artifact@v5` | 공식 v5 태그 존재. path 입력과 기본 github-pages artifact 이름 확인. [공식 정의](https://raw.githubusercontent.com/actions/upload-pages-artifact/v5/action.yml) |
| `actions/deploy-pages@v5` | 공식 v5 태그 존재. 기본 artifact_name=github-pages, page_url output 확인. [공식 정의](https://raw.githubusercontent.com/actions/deploy-pages/v5/action.yml) |

**‘Node 26 LTS’ 표기는 검토일 기준 맞다.** Node 공식 일정의 v26은 2026-10-28 LTS 진입, 2027-10-20 maintenance 전환이다. 따라서 2026-11-23에는 Active LTS 기간이다. [Node 공식 릴리스 일정](https://raw.githubusercontent.com/nodejs/Release/main/schedule.json)

setup-node action 자체의 node24 런타임과 앱 명령에 설치하는 Node 26은 다른 개념이므로 모순이 아니다. T0.2 검증에서 로컬 Node 26으로 build/test/lint/typecheck가 통과했고 설치된 도구의 engine 조건에도 맞았다. 다만 hosted Ubuntu에서의 npm ci·실행은 실제 CI로 확인해야 한다.

## 3. HashRouter와 검증 게이트

HashRouter는 화면 경로를 서버에 전달하지 않는 URL hash에 둔다. `/detour/#/place/id`를 새로고침해도 서버 요청 대상은 `/detour/`이므로 앱의 정상 hash URL에 별도 SPA `404.html` 복사가 필요하지 않다. `/detour/place/id` 같은 비-hash URL까지 지원한다는 뜻은 아니다. [React Router HashRouter](https://reactrouter.com/api/declarative-routers/HashRouter)

CI와 deploy는 별도 workflow라 main에서 CI가 끝날 때까지 deploy가 기다리는 구성은 아니다. 그러나 현재 task는 **동일 후보의 dev CI·로컬 build/phase E2E를 먼저 통과시킨 뒤 main으로 올리는 coordinator 게이트**를 명시한다. 이 절차를 준수하는 현재 설계에서 별도 workflow라는 사실만으로 순환 의존 또는 누락 결함을 새로 세지 않는다.

## 4. 남은 실제 인수 조건

정적 검토 미해결은 0건이다. 권한 갱신 후 dev push의 4개 검사 성공 → 동일 후보 main 배포 → HTTPS 200·콘솔 오류 0·`/detour/` 자산 로드와 빈 앱 표시 확인이 남는다. Phase 0에는 SW 등록 검사를 추가하지 않는다.

이번에는 원격 CI 실행이나 YAML 전용 정적 검사기를 실행하지 못했다. 로컬 YAML 파서 시도는 설치된 모듈이 없어 수행되지 않았으며 의존성을 설치하지 않았다. 따라서 이 보고서는 설정·공식 액션 정의 대조 결과이고, GitHub runner 검증을 대체하지 않는다. 작성한 파일은 이 보고서와 별도 요청된 `task_review_v04.md`뿐이다.
